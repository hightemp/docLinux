Эта страница описывает текущую реализацию песочницы (sandbox) в Flatpak, то, как мы хотим, чтобы она работала, а также что нужно изменить в окружении Linux, чтобы это работало.

Flatpak использует вспомогательную программу `flatpak-bwrap` (заимствованную из проекта atomic — [bubblewrap](https://github.com/projectatomic/bubblewrap)) для настройки песочницы. `flatpak-bwrap` требует capabilities `CAP_SYS_ADMIN` и `CAP_NET_ADMIN`. Для этого он может либо использовать непривилегированные пользовательские namespace, либо быть установленным setuid root — в этом случае он получит нужные capabilities, а затем вернётся к реальному идентификатору пользователя.

## Текущая песочница Flatpak

> СОВЕТ: выполните `flatpak run --command=bash REF`, где REF — имя установленного приложения, например org.gnome.Recipes, чтобы исследовать песочницу приложения Flatpak.

Текущая стандартная настройка песочницы Flatpak такова:

  * Все процессы работают от имени пользователя и без каких-либо capabilities.
  * Все процессы работают во временном (transient) systemd user scope с именем `flatpak-$appid-$pid`.
  * Пространство имён файловой системы, где:

```text
* `/` — приватный tmpfs, невидимый больше нигде. В него выполняется pivot_root, так что это новый `/`, а все остальные монтирования с хоста отключаются (unmount) от namespace.
* `/usr` — bind-монтирование рантайма
* `/app` — bind-монтирование приложения
* `$HOME/.var/app/$APPID` — bind-монтирование хранилища данных, доступного для записи, отдельного для каждого приложения и пользователя
* `/proc` показывает только процессы в песочнице приложения
* `/sys` — доступное только для чтения bind-монтирование хостового `/sys`
* `/dev` содержит
  * `/dev/full`, `/dev/null`, `/dev/random`, `/dev/urandom`, `/dev/tty` и `/dev/zero`
  * `/dev/shm` — приватный tmpfs
* `/run/user/$uid` настроен, и `$XDG_RUNTIME_DIR` указывает на него
* шрифты хоста bind-монтируются в `/run/host/fonts`
* `/etc` содержит
  * passwd и group, bind-монтированные с хоста
  * machine-id, bind-монтированный с хоста
  * `resolv.conf` — симлинк на `/run/user/$pid/flatpak-monitor/resolv.conf`
  * на всё остальное из `/usr/etc` из `/etc` ведут симлинки
* Все монтирования nosuid
* Все монтирования nodev, кроме:
  * `/dev`
  * `/dev/pts`
* Все монтирования доступны только для чтения, кроме:
  * корневого tmpfs (например, для подкаталога tmp и временного home)
  * `/var`
  * `/proc` (кроме `/proc/sys`, `/proc/sysrq-trigger`, `/proc/irq` и `/proc/bus`, которые только для чтения)
  * `/dev/pts`
  * `/dev/shm`
```

  * Seccomp используется для отключения ненужных системных вызовов.
  * Приватное pid-пространство имён с минимальным процессом init, собирающим зомби-процессы.
  * Установлен `PR_SET_NO_NEW_PRIVS`, так что `execve()` никогда не сможет поднять привилегии для любого потомка.
  * Наблюдатель-монитор, который завершается, когда pid 2 (начальный процесс) приложения завершается, и возвращает его код завершения.
  * Приватное user-пространство имён.
  * Приватное ipc-пространство имён.
  * Приватное сетевое пространство имён только с ipv4-устройством loopback.
  * Доступен сокет session dbus, проходящий через фильтрующий прокси. Приложению разрешено владеть собственным app id и суб-именами на шине, а также разрешено общаться только с `org.freedesktop.DBus`.
  * Установлены переменные окружения:

```c
   PATH=/app/bin:/usr/bin
   LD_LIBRARY_PATH=/app/lib
   XDG_CONFIG_DIRS=/app/etc/xdg:/etc/xdg
   XDG_DATA_DIRS=/app/share:/usr/share
   XDG_RUNTIME_DIR=/run/user/$pid
```

Есть также активируемый через dbus сервис (flatpak-session-helper) в пользовательской сессии (вне песочницы), который отслеживает `/etc/resolv.conf` и `/etc/localtime` и копирует их в `/run/user/$uid/flatpak-monitor/` при каждом их изменении. Если этот каталог смонтирован в песочницу, изменения системных настроек передаются приложению.

Опционально есть флаги для:

  * Добавления доступного для чтения и записи (nosuid, nodev) bind-монтирования из системного $HOME (заменяющего симлинк `/var/home`).
  * Добавления доступных для чтения и записи bind-монтирований в несистемные места в системном / (такие как `/opt`, `/src`, `/media` и т. д.).
  * Разрешения дополнительных суб-bind-монтирований в `/app` и `/usr`.
  * Взятия advisory read-lock на файл `.ref` в каждой bind-монтированной файловой системе — это можно использовать, чтобы определить, использует ли какое-то приложение ещё эти файлы. Блокировка принадлежит pid 1, поэтому будет освобождена, когда последний процесс приложения умрёт.
  * Использования сетевого namespace хоста.
  * Использования ipc namespace хоста (полезно для поддержки XShm).
  * Сделать `/app` доступным для записи (полезно при сборке приложений).
  * Сделать `/usr` доступным для записи (полезно при сборке рантаймов).
  * Сделать /run/user/$uid bind-монтированием сокетов:

```text
* system dbus
* session dbus
* пользовательский демон pulseaudio
* wayland-композитор
* unix domain socket X11
```

  * Bind-монтирования каталога `/run/user/$uid/dconf`, если домашний каталог виден пользователю.
  * Bind-монтирования `run/user/$uid/flatpak-monitor` для получения обновлений `resolv.conf` и `localtime`. Это также устанавливает переменную окружения `TZ`, чтобы glibc подхватил новый localtime.
  * Bind-монтирования хостового `/dev/dri`.

## Дополнительная изоляция, которую мы хотим

Есть несколько вещей, которые мы могли бы делать для дальнейшей изоляции приложений, но пока не делаем.

### dbus

Политики kdbus были спроектированы, чтобы разрешать политики по имени (или по имени с шаблоном): can-own, can-see, can-talk-to.

Хорошей политикой была бы такая, при которой приложения могут владеть собственным id как именем, а также видеть и общаться с шиной и несколькими dbus API, которые мы считаем «безопасными».

Поскольку kdbus не состоится, мы сейчас приближённо реализуем возможности политик kdbus с помощью фильтрующего D-Bus-прокси, но это добавляет лишние накладные расходы на каждое D-Bus-сообщение.

### SELinux

Если бы мы могли запускать песочницу каждого приложения в собственном контексте SELinux, это бы значительно снизило риск выхода из песочницы. Надеемся, это не так сложно, по крайней мере для приложений без доступа к домашнему каталогу или другим файлам хоста, поскольку число разрешённых взаимодействий между песочницей и хостом очень мало.

## Необходимые изменения в хосте

Чтобы иметь полноценную песочницу для десктоп-приложений, нужен целый ряд изменений. Вот список некоторых из известных мне:

  * Нужен wayland-композитор в сессии и отсутствие доступа к X-серверу из песочницы. X полностью небезопасен, и мы не можем позволять приложениям его использовать.
  * Нам нужен сервис, поддерживающий арбитраж веб-камер, чтобы приложение могло получить доступ к камере, не прибегая к (небезопасному) прямому доступу к устройству. Начальная работа есть здесь: <https://github.com/wmanley/pulsevideo>
  * Нам нужно добавить поддержку джойстиков в wayland. Текущее предложение, по-видимому, — некоторый кастомный wayland-протокол для получения списка джойстиков: вы просите открыть один из них и получаете fd устройства ввода, который композитор может отозвать, когда приложение теряет фокус. Это также требует кода в SDL2 для его использования.
  * Нам нужно понять, как лучше всего обеспечить поддержку смарт-карт в песочнице.
  * Нам нужно понять, как лучше всего обеспечить поддержку сканеров в песочнице.
  * У Allison есть планы по новому бэкенду gsettings для использования в песочнице, который видит только разрешённую ему конфигурацию, и в котором все модификации/чтения проходят через сессионный сервис, применяющий, например, lockdown и значения по умолчанию.

## Порталы

Когда у вас есть идеально изолированное приложение, вы можете запускать «тривиальные» приложения вроде игры, но если вы хотите запускать обычные десктоп-приложения, вам нужно начать открывать «безопасные» способы взаимодействия приложения с системой. Ранее мы использовали для этого имя «Порталы» (Portals). Вот для чего у нас уже есть порталы:

  * Открытие файлов или иного содержимого из домашнего каталога пользователя
  * Сохранение вновь созданных или ранее открытых файлов
  * Написание письма по почте
  * Получение геолокации
  * Открытие URI

А вот для чего у нас их пока нет:

  * Шаринг содержимого из приложения. Например, выделить текст и «поделиться в twitter».
  * Установить будильник
  * Доступ к календарю или контактам
  * Сделать снимок (вероятно, с веб-камеры)

Есть некоторые начальные наработки по [пользовательскому опыту Порталов для GNOME](https://wiki.gnome.org/Design/Whiteboards/ApplicationSandboxing).
