# Выбор адреса по умолчанию. Часть 2

Источник: [Default Address Selection Part 2](https://linux-hacks.blogspot.com/2008/07/default-address-selection-part-2.html)

varun · 26 июля 2008

Наконец я нашёл время закончить давно ожидаемое продолжение. В этой статье я хотел бы дать представление о реализации алгоритма выбора адреса в ядре. Диаграммы в этой статье нарисованы мной лично с помощью примитивных инструментов :-). Пожалуйста, не обращайте внимания на низкое качество.

Прежде чем продолжить, хочу предупредить читателей, что я не буду разбирать полный алгоритм выбора адреса. Выбор адреса по умолчанию (Default Address Selection) в основном делится на:

* **Выбор адреса источника (ядро)**
* **Выбор адреса назначения (glibc — getaddrinfo())**

Эта статья в основном сосредоточена на выборе адреса источника, выполняемом в ядре. Поэтому мы будем считать, что выбор адреса назначения уже сделан, и сосредоточимся на выборе адреса источника. Картинка ниже показывает очень общую блок-схему выбора адреса назначения.

[![](https://blogger.googleusercontent.com/img/b/R29vZ2xl/AVvXsEiID6lUBhDxNorv1cJxRKwv0XYn0X392wNyAUltDJCPIlKwCuK2gp6wpZFW2eH3lcFQ0nYEjPNszWAXGheDwlnn2AhDiOGVEhhUsWIBENMKdj2IdERHxj3LYwmIUEk2XaZRVIQgNDqe6BQo/s400/snapshot5.png)](https://blogger.googleusercontent.com/img/b/R29vZ2xl/AVvXsEiID6lUBhDxNorv1cJxRKwv0XYn0X392wNyAUltDJCPIlKwCuK2gp6wpZFW2eH3lcFQ0nYEjPNszWAXGheDwlnn2AhDiOGVEhhUsWIBENMKdj2IdERHxj3LYwmIUEk2XaZRVIQgNDqe6BQo/s1600-h/snapshot5.png)

Из блок-схемы ясно, что выбор адреса назначения выполняется с помощью glibc. Причина в том, что приложение должно определиться с адресом назначения до того, как оно попадёт в сетевой стек. Например, браузер (приложение) может подключиться либо по IP-адресу, либо по интернет-адресу (google.com), который нужно разрешить через DNS. Если это последний случай, то есть вероятность, что DNS-запрос вернёт несколько IP-адресов. Если это так, сортировку придётся выполнить в вызове разрешения DNS. Когда адрес назначения выбран, запрос на «формирование пакета» попадает в ядро, как показано на блок-схеме. Ядро затем ищет в таблице маршрутизации ( базе прямой информации о маршрутизации — forwarding information base, FIB) маршрут к адресу назначения. Если в таблице нет допустимой записи, вызывающему приложению возвращается ошибка «No Route To Host». Если мы попали в яблочко при поиске маршрута, ядру нужно найти подходящий адрес источника. Это делается в вызове fib6_rule_action(). На этом выбор адреса назначения заканчи_**вается.

**Алгоритм выбора адреса источника:**

В функции fib6_rule_action() вызывается функция поиска адреса источника ipv6_get_saddr(). Именно на этом этапе мы начинаем анализ алгоритма. Блок-схема ниже поясняет поток кода.

Как видно, блок-схема разделена на две небольшие части для простоты объяснения. Алгоритм начинается с инициализации типа, scope и label адреса назначения. Это нужно, чтобы сравнивать эти значения с эквивалентными значениями адреса-кандидата источника. Список адресов-кандидатов источника — это все IPv6-адреса во всех интерфейсах системы.

Теперь у нас есть множество адресов источника, и из этого списка нужно окончательно выбрать правильный адрес источника. Для каждого адреса ведётся механизм подсчёта очков, чтобы в итоге выбрать победителя. Адрес с наивысшим счётом станет выбранным кандидатом. Очки начисляются за прохождение каждого правила. Каждое правило по порядку объясняется ниже. Помните: по мере прохождения каждого правила мы продолжаем выбрасывать кандидатов из множества кандидатов, чтобы в конце концов прийти к правильному адресу источника.

**Правило 0: Локализовать множество кандидатов-источников для адреса назначения, который является link/site-local.**
Это значит: если адрес назначения является либо link-local, либо site-local адресом, то адрес источника должен быть выбран из того же канала (link), что и исходящий интерфейс. Это снижает вероятность того, что какой-либо глобальный адрес будет назначен адресом источника для адреса назначения, являющегося link-local.

**Правило 1: Предпочесть тот же адрес.** Если адрес источника равен адресу назначения, выбрать этот адрес как предпочтительный.
Пример:
SA: 2001::1
SB: 2001::2
Dest Address : 2001::1
**Select: 2001::1**

**Правило 2: Предпочесть тот же scope.** Выбрать адрес источника со scope выше, чем у адреса назначения.
Пример:
If Scope(SA) < Scope(SB) : If Scope(SA) < Scope(D), prefer SB

[![](https://blogger.googleusercontent.com/img/b/R29vZ2xl/AVvXsEic3R5QKnrUD120igdRqROvvq2nw6ad9CUSLGux7R8T3lmqsjP_5w1yeqS__3WG7cebrraQSnMG7ciCYVoIMOG3LIEL2xoM0h2XyqLoiKoZO-f-afhVgs0yuSk4yt59T4H__tbKbTInlqTY/s400/snapshot7.png)](https://blogger.googleusercontent.com/img/b/R29vZ2xl/AVvXsEic3R5QKnrUD120igdRqROvvq2nw6ad9CUSLGux7R8T3lmqsjP_5w1yeqS__3WG7cebrraQSnMG7ciCYVoIMOG3LIEL2xoM0h2XyqLoiKoZO-f-afhVgs0yuSk4yt59T4H__tbKbTInlqTY/s1600-h/snapshot7.png)

**Правило 3: Избегать устаревшего (deprecated) адреса.** В группе из двух адресов-кандидатов источника с равным scope один оказался устаревшим — избегать этого адреса.
Пример:
Src Address 1 : 2001::1
Src Address 2 : 2001::2 (deprecated)
**Select :: 2001::1**

**Правило 4: Предпочесть домашний адрес.** Если адрес-кандидат источника SA1 является одновременно и домашним (home), и адресом ухода (care-of), предпочесть его адресу-кандидату источника SA2, который является только адресом ухода. С другой стороны, если SA1 — домашний адрес, а SA2 — адрес ухода, то предпочесть SA1. Другими словами, домашнему адресу даётся более высокий приоритет. Я не тестировал этот случай, так как в моём ядре не включена поддержка mobile ipv6. Поэтому я пропущу пример для этого случая. Если кто-то тестировал — дайте знать :-).

**Правило 5: Предпочесть исходящий интерфейс.** Это правило совершенно простое. Если исходящий интерфейс, используемый для отправки к адресу назначения, известен, кандидаты для выбора адреса источника должны принадлежать только этому интерфейсу. Если SA — из интерфейса eth0, а SB — из интерфейса eth1, и интерфейс, используемый для отправки пакетов к назначению, — eth0, то предпочесть SA. Если у интерфейса несколько подходящих кандидатов, перейти к следующему правилу.
Пример:
eth0: 2001::1 eth1: 2001::2 ;
Dest : eth0: 2002::5
**Select : 2001::1**

**Правило 6: Предпочесть метку (label).** Это правило выбирает адрес источника из множества кандидатов на основе значения метки. Пользовательская таблица меток поддерживается в ядре через netlink для сопоставления значений. Значение метки адреса назначения должно совпасть со значением метки любого из кандидатов источника. Если есть совпадение, адрес источника выбран, иначе множество кандидатов передаётся следующему правилу. Значения меток может изменять и задавать администратор с помощью команды «ip».
Пример:
Label Table:
SrcA 2001::1 3
SrcB 2001::2 4
SrcC 2001::3 5
Dest fec0::3 4
**Select : 2001::2**

**Правило 7: Предпочесть публичный адрес.** Это правило тоже довольно простое. Если SA — публичный адрес, а SB — временный (temporary), предпочесть SA. Это независимо от назначения. В RFC сказано, что должен быть предоставлен API, позволяющий приложению обратить это предпочтение. На момент написания этой статьи такого API в Linux нет.
Пример:
SA fec0::1 configured by "ip -6 addr add fec0::1 dev eth0"
SB fec0::2 configured by radvd (temporary address)
**Select: fec0::1**

**Правило 8: Предпочесть самый длинный совпадающий префикс.** Последнее правило — совпадение по самому длинному префиксу из возможных. Это последняя возможность сузить выбор адреса источника. Из списка адресов источника выполняется сопоставление префиксов, чтобы увидеть, у какого источника самый длинный префикс, похожий на назначение.
Пример:
SA: 2001:3fff:2e33:6fff::1
SB: 2001:3fff:2e33:23ff::2
Dest: 2001:3fff:2e33:23ff::3
**Select: 2001:3fff:2e33:23ff::2**

Если все правила пройдены, а кандидат-источник так и не удалось выбрать, Linux просто берёт последний адрес из итогового списка потенциальных адресов источника.
Пример:
SA: 2001::1
SB: 2001::2
SC: 2001::3
**Select: 2001::3**

ПРИМЕЧАНИЕ: SA, SB… и Src A, Dest/D — это адрес источника A/B и адрес назначения. Простите, что использовал эти обозначения без предупреждения.
