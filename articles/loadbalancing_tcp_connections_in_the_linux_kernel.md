# Балансировка TCP-соединений в ядре Linux

Источник: [Loadbalancing TCP connections in the Linux kernel](https://blog.domainmess.org/post/so_portreuse/)

20 декабря 2023 · Linux

В поисках способа сделать Linux-приложение пригодным для плавающих обновлений (rolling upgrades) я искал способ перехватить уже занятый TCP-порт. Я выяснил, что некоторые версии netcat умеют это делать, и это также работало, когда я использовал функцию проброса портов в Docker. Поэтому я начал разбираться, как это работает и что из этого можно извлечь.

## SO_REUSEPORT

Оказывается, в Linux начиная с версии 3.9 существует механизм ядра, предназначенный именно для такого рода задач: несколько приложений или потоков должны слушать одну и ту же комбинацию адрес:порт. Если опция сокета `SO_REUSEPORT` установлена до того, как приложение выполнит bind, другие процессы с тем же UID могут подключиться к тому же порту. Многие программы поддерживают это — как правило, когда работу нужно распределить между несколькими процессами. Один из примеров — [модуль mpm](https://httpd.apache.org/docs/trunk/mod/mpm_common.html#listen) веб-сервера Apache.
`SO_REUSEPORT` не следует путать с опцией `SO_REUSEADDR`. Прекрасное объяснение их различий и использования в других операционных системах можно найти на [StackOverflow](https://stackoverflow.com/questions/14388706/how-do-so-reuseaddr-and-so-reuseport-differ/14388707#14388707).

## Балансировка нагрузки

С переиспользуемыми портами есть одна проблема. Все сокеты, которые привязываются к одной комбинации адрес:порт, образуют группу, и ядро балансирует все входящие соединения по принципу round-robin. См. man-страницу [socket 7](http://web.archive.org/web/20231215214630/https://man7.org/linux/man-pages/man7/socket.7.html):

> _Для TCP-сокетов эта опция позволяет улучшить распределение нагрузки accept(2) в многопоточном сервере за счёт использования отдельного слушающего сокета для каждого потока. Это обеспечивает лучшее распределение нагрузки по сравнению с традиционными техниками, такими как использование единственного потока, выполняющего accept(2) и распределяющего соединения, или наличие нескольких потоков, конкурирующих за accept(2) на одном и том же сокете._

Для высокопроизводительного веб-сервера это имеет смысл, но не в том случае, когда я хочу передать входящие соединения новому процессу.

## Некоторые тесты

Чтобы проверить, как всё это себя ведёт, я создал конфигурацию Apache с `Listen 80 reuseport` и `ListenCoresBucketsRatio 2`. С такой конфигурацией Apache включает опцию `SO_REUSEPORT` на своём сокете. К сожалению, в Linux нет простого способа показать все опции сокета в человекочитаемом виде.
Я использовал [knetstat](https://github.com/veithen/knetstat), чтобы убедиться, что Apache работает правильно.

```text
$ cat /proc/net/tcpstat
Recv-Q Send-Q Local Address           Foreign Address         Stat Diag Options
     0      0 0.0.0.0:80              0.0.0.0:*               LSTN      SO_REUSEPORT=1,SO_REUSEADDR=1,SO_KEEPALIVE=0,TCP_NODELAY=0
```

Моя идея состояла в том, чтобы запустить два таких Apache, сымитировать аварийное состояние в одном из них и посмотреть, как распределится поток входящих соединений. Поэтому я выполнил следующее в качестве базовой симуляции:

```bash
# launch to Apaches, on after the other
docker run -d --name test1 --network host httpd:bookworm -v apache-test.conf:/etc/apache2/apache2.conf
docker run -d --name test2 --network host httpd:bookworm -v apache-test.conf:/etc/apache2/apache2.conf

# then get the PIDs from one of the containers
ps auxf | grep apache

# and pause all the processes to prevent them from answering on their socket
for i in $(seq 6031 6062); do kill -STOP $i; done
```

```bash
# then test the connection distribution with
for i in $(seq 1 100); do timeout 1 curl https://localhost -k -s -o /dev/null && echo worked || echo failed; done | sort | uniq -c
```

Результат выглядит примерно так:

```text
   46 worked
   54 failed
```

В итоге я понял, что это не совсем то, что я искал. Я хотел плавной передачи занятого сокета новому процессу, а `SO_REUSEPORT` больше подходит для балансировки соединений между несколькими процессами, отдающими одинаковое содержимое в целях оптимизации производительности.

## eBPF как обычно

Однако впоследствии я понял, что можно написать (e)BPF-программу и подключить её к группе сокетов, использующих один и тот же порт. В этом случае у вас есть полный контроль над распределением соединений, хотя это и не просто из-за возможного переупорядочивания сокетов. Приятный момент в том, что такую программу можно заменить во время работы без перезапуска собственно обслуживающего приложения. Man-страница [socket 7](http://web.archive.org/web/20231215214630/https://man7.org/linux/man-pages/man7/socket.7.html) говорит:

> _Для использования совместно с опцией SO_REUSEPORT эти опции позволяют пользователю задать классическую BPF-программу (SO_ATTACH_REUSEPORT_CBPF) или расширенную BPF-программу (SO_ATTACH_REUSEPORT_EBPF), которая определяет, как пакеты назначаются сокетам в группе reuseport. … Сокеты нумеруются в порядке их добавления в группу (то есть в порядке вызовов bind(2) для UDP-сокетов или в порядке вызовов listen(2) для TCP-сокетов). Новые сокеты, добавленные в группу reuseport, наследуют BPF-программу. Когда сокет удаляется из группы reuseport (через close(2)), последний сокет в группе перемещается на место закрытого сокета._

Полезно знать, но это всё равно не решает мою проблему %) Возможно, скоро я напишу об альтернативном решении.
