# Как вывести список файлов каталога с 8 миллионами файлов (но не с помощью ls)

Источник: [You can list a directory containing 8 million files! But not with ls.](http://be-n.com/spw/you-can-list-a-million-files-in-a-directory-but-not-with-ls.html)

Мне нужно было вывести список всех файлов в каталоге, но `ls`, `find` и `os.listdir` зависали. Вот моя история.

ПРИМЕЧАНИЕ: нет ни одной веской причины хранить 8 миллионов файлов в одном каталоге, но если у вас именно такая ситуация — вот ваше решение :-).

TLDR: напишите программу на C, которая вызывает системный вызов [getdents](http://www.kernel.org/doc/man-pages/online/pages/man2/getdents.2.html) напрямую, с большим размером буфера, и игнорирует записи с inode == 0.

**Почему ls не работает?**

`ls` и практически все остальные способы вывода списка файлов каталога (включая python os.listdir, find .) полагаются на libc `readdir()`. Однако `readdir()` за раз читает только 32K записей каталога, а это значит, что если у вас очень много файлов в одном каталоге (то есть 500M записей каталога), чтение всех записей займёт безумно долгое время, особенно на медленном диске. Для каталогов с большим количеством файлов придётся копнуть глубже инструментов, полагающихся на readdir(). Вам понадобится использовать системный вызов `getdents()` напрямую, а не вспомогательные методы из libc.

**Как быстро вывести список файлов каталога с 8 миллионами файлов**

Трюк в том, чтобы понять `getdents()` — низкоуровневый системный вызов, который читает записи каталога с диска и возвращает структуру данных записи каталога (dirent).

```text
GETDENTS (filehandle for directory entries, *directory entry pointer, number of bytes to read)
```

К счастью, man-страница содержит много подробностей и предоставляет исходный код на C для вывода списка всех файлов каталога. Прочитайте её [здесь](http://www.kernel.org/doc/man-pages/online/pages/man2/getdents.2.html) и скопируйте исходный код в файл, например listdir.c. Вам потребуются две модификации, чтобы быстро вывести список всех файлов каталога. Во-первых, увеличьте размер буфера с X до чего-то вроде 5 мегабайт.

```c
#define BUF_SIZE 1024*1024*5
```

Затем измените основной цикл, в котором выводится информация о каждом файле каталога, чтобы пропускать записи с inode == 0. Я сделал это, добавив

```c
if (dp->d_ino != 0) printf(...);
```

В моём случае мне были нужны только имена файлов в каталоге, поэтому я также переписал оператор printf(), чтобы он выводил только имя файла.

```c
if(d->d_ino) printf("%sn ", (char *) d->d_name);
```

Скомпилируйте её (ей не нужны никакие внешние библиотеки, так что это очень просто)

```bash
gcc listdir.c -o listdir
```

Теперь просто запустите

```bash
./listdir [directory with insane number of files]
```

И — вуаля — вы должны увидеть все файлы в вашем безумно большом каталоге :-). В моём случае я сделал

```bash
./listdir [directory with insane number of files] > output.txt
```

и затем использовал содержимое output.txt, чтобы обработать файлы, которые раньше было «невозможно перечислить».

**Почему мы вообще столкнулись с этой проблемой?**

Не вдаваясь в излишние подробности: нам было нужно простое хранилище данных, в котором можно было находить запись по ключу, добавлять значения к каждому ключу и уничтожать ключи старше определённого порога, выполняя при этом операцию очистки над сохранёнными значениями. Файловая система на самом деле отлично подходит для этого случая, пока не так много ключей активны одновременно. (то есть в файловой системе вывод списка всех ключей — самая медленная операция, так что если ключей немного, беспокоиться не о чем). Что-то сломалось и привело к сбою операции уничтожения по истечении срока. И вместо того чтобы хранить в каталоге небольшое количество файлов, мы начали генерировать множество записей, которые не очищались. В следующий раз, когда запустилась операция очистки, она уже не могла вывести список всех ключей за разумное время (читая по 32K записей каталога за раз). Это усугубило проблему и привело к состоянию, когда новые файлы создавались, но старые не очищались. Вскоре у нас было 8 миллионов файлов в одном каталоге. Мы смогли довольно быстро устранить первопричину, исправив баг в нашем «чистильщике» и создав новый каталог кэша, но у нас всё ещё оставалось 8 миллионов файлов, которые нужно было обработать. Имейте в виду, что речь идёт о временах порядка часов. (К счастью, эта проблема случилась на выходных, была быстро обнаружена и почти не повлияла на наших клиентов.) Один важный момент: на этом этапе мы понятия не имели, сколько файлов нужно обработать — всё, что мы знали, это что `ls` и `os.listdir()` оба зависали при попытке вывести список всех файлов каталога. Я спросил в IRC и попытался поискать в Google — без особого успеха. Другие люди сталкивались с этой проблемой раньше, но ни у кого не было хорошего решения. На самом деле, я помню, что много лет назад сталкивался с похожей проблемой при выводе списка почтовой очереди в Qmail, но понятия не имею, как мы её тогда решили. **Диагностика неизвестного**

Всякий раз, когда я вижу, что что-то зависает без отладочного вывода, я обращаюсь к `strace`. strace позволяет наблюдать системные вызовы, выполняемые во время работы программы, и увидеть, что происходит, когда никакого вывода не печатается. Я попробовал `strace find .`, `strace ls` и `strace python import os os.listdir(".")` — все эти функции дали практически одинаковый вывод strace: сначала они открывают файл, содержащий информацию о каталоге

```text
open(".", O_RDONLY|O_NONBLOCK|O_DIRECTORY|O_CLOEXEC) = 5
```

Затем они выполняют системный вызов getdents, который возвращает записи каталога

```text
getdents(5, /* 586 entries */, 32768)  = 32752
```

Мне понадобилось время, чтобы это понять, но в основном вызов `getdents` <http://www.kernel.org/doc/man-pages/online/pages/man2/getdents.2.html> выглядит так:

```c
int getdents(unsigned int fd, struct linux_dirent *dirp, unsigned int count);
```

где count — это на самом деле размер буфера (в данном случае 32K). Конечно, я заметил это только после того, как кто-то в IRC упомянул, что можно выполнить

```bash
ls -dl
```

чтобы увидеть размер файла, хранящего записи каталога. В моём каталоге я получил:

```text
drwxr-xr-x 2 root root 537919488 Jul 29 04:55 . (513M)
```

Сложив два и два, я понял, что причина, по которой вывод списка каталога длился вечно, была в том, что `ls` читал файл записей каталога по 32K за раз, а файл имел размер 513M. То есть для вывода списка каталога потребовалось бы около 16416 системных вызовов `getdents()`. Это очень много вызовов, особенно на медленном виртуализированном диске. Это и привело меня к решению выше: увеличить размер буфера чтения для getdents(), чтобы уменьшить количество системных вызовов и ускорить весь доступ к диску :-).

**Выводы:**

  1. Вывести список файлов каталога с 8 миллионами файлов — возможно.
  2. strace — ваш друг.
  3. Не бойтесь компилировать код и изменять его (чёрт возьми, простой C компилируется так быстро, что его можно было бы использовать как интерпретируемый).
  4. Нет ни одной веской причины хранить 8 миллионов файлов в каталоге :-), но это был хороший учебный опыт (и, возможно, хороший вопрос для собеседования).

**Приложение:**

После всего этого мне всё ещё было немного любопытно, откуда взялся размер буфера 32K в `ls`, так что я скачал исходники coreutils (содержат `ls`) и покопался в них. (ПРИМЕЧАНИЕ: это по большей части просто мои заметки, а не детальный анализ.) Поищите по коду, и вы найдёте, что `ls` вызывает `readdir()` с указателем на каталог.

```c
while (1) {
/* Set errno to zero so we can distinguish between a readdir failure and when readdir simply finds that there are no more entries. */
errno = 0;
next = readdir (dirp);
if (next)
```

`readdir()` определена в libc. Поэтому я продолжил поиск и скачал исходники libc, чтобы выяснить, как определяется размер буфера для `readdir()`. getdents() вызывается внутри readdir() (как и ожидалось)

```c
bytes = __GETDENTS (dirp->fd, dirp->data, maxread);
if (bytes <= 0)
```

А размер в байтах берётся из размера структуры записи каталога, то есть из `dirp->allocation`. Учитывая, что мы читали несколько записей, я почти уверен, что переменная maxread устанавливалась из `dirp->allocation`.

```c
/* Fixed-size struct; must read one at a time (see below). */
maxread = sizeof *dp;
#else maxread = dirp->allocation;
#endif
```

Если покопаться в

```text
sysdeps/unix/dirstream.h sysdeps/unix/opendir.c
```

можно увидеть, где устанавливается это значение. Однако оно определённо не меняется в зависимости от размера файла записей каталога. (Возможно, буфер стоило бы устанавливать динамически, исходя из размера файла записей каталога.) Наконец, чтобы узнать о трюке с пропуском удалённых файлов, я заметил строку:

```c
if (dp->d_ino == 0) ..
```

внутри `ls`, которая используется, чтобы отфильтровать удалённые файлы и не показывать их при выводе списка каталога.
