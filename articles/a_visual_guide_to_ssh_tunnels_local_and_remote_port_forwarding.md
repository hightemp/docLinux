SSH — [ещё один пример](https://iximiuz.com/en/posts/linux-pty-what-powers-docker-attach-functionality/) древней технологии, которая до сих пор широко используется. Вполне может оказаться, что изучение пары SSH-трюков в долгосрочной перспективе выгоднее, чем освоение дюжины Cloud Native-инструментов или фреймворков ИИ-агентов, которым суждено устареть в следующем квартале.

Одна из моих любимых частей этой технологии — SSH-туннели. Используя только стандартные инструменты и зачастую всего одну команду, вы можете добиться следующего:

  * Получить доступ к внутренним VPC-эндпоинтам через публичный EC2-инстанс.
  * Открыть порт `localhost` удалённой девелоперской VM в локальном браузере.
  * Выставить любой локальный сервер из домашней/приватной сети наружу, во внешний мир.
  * [Прокинуть отладочный порт вашего браузера к удалённому песочному кодинг-агенту](/docs/playground-recipes/coding-agent-with-browser-access).

И многое другое 😍

Но, несмотря на то что я использую SSH-туннели ежедневно, мне всегда требуется время, чтобы вспомнить правильную команду. Это будет Local или Remote туннель? Какие нужны флаги? Это _local_port:remote_port_ или наоборот? Поэтому я решил наконец разложить всё по полочкам, что вылилось в серию лабораторных работ и наглядную шпаргалку.

Замечание

Лабораторные работы в этом руководстве выполняются на прикреплённой площадке из четырёх хостов, соединённых в три сети:

  * `internal` — устройство в **домашней** сети `192.168.0.0/24` (коробка homelab, NAS, принтер). Недостижимо из **публичной** сети.
  * `local` — ваша рабочая станция. Находится одновременно в **домашней** `192.168.0.0/24` и **публичной** `203.0.113.0/24` сетях.
  * `remote` — публичный бастион / шлюз в **публичной** сети `203.0.113.0/24`, также подключённый к приватной сети **vpc** `172.16.0.0/24`.
  * `private` — внутренний сервис (база данных, кластер OpenSearch) в сети **vpc** `172.16.0.0/24`. Недостижим из **публичной** сети.

Вы можете выполнить `ssh` с `local` на `remote` по имени хоста или IP-адресу — ключ хоста `local` уже доверен на машине `remote`:

```bash
ssh remote
ssh 203.0.113.30
```

## Локальная переадресация портов

Начнём с той, что я использую чаще всего. Зачастую есть сервис, слушающий на `localhost` или приватном интерфейсе удалённой машины, куда я могу попасть только по SSH через её публичный IP. И мне отчаянно нужно получить доступ к этому порту с моей локальной машины. Несколько типичных примеров:

  * Доступ к приватной удалённой базе данных (MySQL, Postgres, Redis и т. д.) с вашего ноутбука с помощью любимого GUI-инструмента.
  * Использование браузера для доступа к веб-приложению, доступному только из приватной сети.
  * Доступ к порту контейнера с вашего ноутбука, не публикуя его на публичном интерфейсе сервера.

Все перечисленные сценарии решаются одной командой `ssh`:

```bash
ssh -L [local_addr:]local_port:remote_addr:remote_port [user@]sshd_addr
```

Флаг `-L` означает, что мы запускаем _локальную переадресацию портов_ (local port forwarding). Что это на самом деле значит:

  * На вашей локальной машине SSH-клиент начнёт слушать `local_port` (скорее всего, на `localhost`, но _зависит от настроек_ — [проверьте настройку `GatewayPorts`](https://linux.die.net/man/5/sshd_config#GatewayPorts)).
  * Любой трафик в этот порт будет перенаправлен на `remote_addr:remote_port`, доступного с удалённой машины, к которой вы подключились по SSH.

## Локальная переадресация портов через бастионный хост

Может быть неочевидно, но команда `ssh -L` позволяет переадресовывать локальный порт на удалённый порт на _любой машине_, не только на самом SSH-сервере. Обратите внимание, что `remote_addr` и `sshd_addr` могут как совпадать, так и нет:

```bash
ssh -L [local_addr:]local_port:remote_addr:remote_port [user@]sshd_addr
```

Удалённый SSH-сервер, используемый для доступа к приватным адресатам, обычно называется [_бастионом или jump-хостом_](https://en.wikipedia.org/wiki/Bastion_host). Вот как я визуализирую этот сценарий в голове:

Я часто использую этот трюк, чтобы вызывать эндпоинты, доступные с _бастионного хоста_, но не с моего ноутбука (например, используя EC2-инстанс с приватным и публичным интерфейсами для подключения к кластеру OpenSearch или любому другому сервису, развёрнутому целиком внутри VPC).

Лабораторная 2: локальная переадресация портов через бастион 👨‍🔬

Эта лабораторная воспроизводит схему с диаграммы выше. Целевой сервис работает на хосте `private` внутри импровизированной VPC-сети (`172.16.0.40:80`), а прежний хост `remote` выступает нашим публичным бастионом (jump-хостом), который может до него добраться.

У рабочей станции `local` нет маршрута в VPC, поэтому напрямую она общаться с хостом `private` не может. С локального хоста:

```bash
curl --connect-timeout 3 172.16.0.40:80  # private.vpc
```

```text
curl: (28) Connection timed out after 3002 milliseconds
```

Бастион `remote`, напротив, подключён к VPC и может достучаться до хоста `private`. Поэтому мы переадресуем локальный порт через бастион прямо к приватному сервису. С локального хоста:

```bash
ssh -f -N -L 8081:172.16.0.40:80 203.0.113.30
```

Проверяем, что работает — всё ещё на локальном хосте:

```bash
curl localhost:8081
```

```text
Hello from the private VPC host (172.16.0.40).
```

**Обратите внимание, что адресат переадресации (`172.16.0.40`) и SSH-сервер (`203.0.113.30`) — разные машины.** Бастион принимает соединение и открывает второй хоп к приватному хосту от нашего имени.

* * *

Чуть более многословный (но более явный и гибкий) способ добиться того же:

```bash
ssh -f -N -L localhost:8081:172.16.0.40:80 203.0.113.30
#            local          remote         via
```

## Локальная переадресация портов на loopback-порт через jump-хост

Трюк с бастионом из лабораторной 2 удобен, и его команду (относительно) легко запомнить, но у него есть существенное ограничение. В `ssh -L local_port:remote_host:remote_port bastion_host` SSH-сеанс завершается **на бастионе**, и бастион открывает второй хоп к `remote_host:remote_port`. Это работает, только пока приватный сервис привязан к _внешнему_ сетевому интерфейсу удалённой машины (т. е. бастион может достучаться до него _снаружи_).

Но сервисы могут быть привязаны и к `127.0.0.1` — административная консоль базы данных, метрический или профилировочный эндпоинт, отладочный порт приложения и т. д. Порт, привязанный к loopback, отвечает только на _собственном_ loopback хоста, так что ни бастион, ни кто-либо ещё в сети до него не доберётся. Переадресацию нужно разрешить **на самом удалённом хосте**.

Способ сделать это — использовать `remote_host` как целевой адрес в команде `ssh -L`, но когда удалённый хост достижим только через бастион, понадобится дополнительный флаг — `-J bastion_host`.

Вместо завершения SSH-сеанса на бастионе [`-J` (ProxyJump)](https://man.openbsd.org/ssh#J) прыгает _через_ бастион и завершает сеанс **на удалённом хосте**. Адресат `-L` тогда разрешается с точки зрения удалённого хоста, так что `localhost` означает собственный loopback удалённой машины:

```bash
ssh -J [user@]jumphost -L [local_addr:]local_port:localhost:remote_port [user@]remote_host
```

Бастион по-прежнему лишь передаёт байты для прыжка — ваш настоящий SSH-сеанс устанавливается между локальным и удалённым хостами, что и делает возможным доступ к loopback удалённой машины.

Так я добираюсь до локального отладочного или админского порта, который сервис привязывает к `127.0.0.1`. Хотя порт невидим для всей сети, одна команда `ssh -J ... -L` с моего ноутбука делает его доступным на локальном порту моей машины, как будто сервис работает прямо рядом со мной.

Лабораторная 3: локальная переадресация на loopback-порт через jump-хост 👨‍🔬

Эта лабораторная переиспользует топологию с бастионом из лабораторной 2, но на этот раз хост `private` также запускает второй веб-сервер, привязанный к его **loopback** на `127.0.0.1:9000` — представьте внутренний отладочный или метрический порт, который никогда не должен быть виден в сети.

Подход из лабораторной 2 переадресует на _внешний_ сетевой адрес приватного хоста. Бастион может открыть такой хоп, но на `172.16.0.40:9000` никто не слушает — отладочный порт живёт на loopback, а не на сетевом интерфейсе. Так что переадресация `-L 8082:172.16.0.40:9000` через бастион получила бы лишь connection refused.

Вместо этого нужно заставить SSH-сеанс «прыгнуть через» бастион (используя `-J bastion`) и завершиться **на хосте `private`**, переадресуя на `localhost:9000`, который хост `private` затем разрешает в собственный loopback. С локального хоста:

```bash
ssh -f -N -J 203.0.113.30 -L 8082:localhost:9000 172.16.0.40
#            jump host            target_port    target_host
```

Проверяем, что работает — всё ещё на локальном хосте:

```bash
curl localhost:8082
```

```text
Hello from the private VPC host's loopback-only debug port (127.0.0.1:9000).
```

## Удалённая переадресация портов

Другой популярный (но скорее обратный) сценарий — когда вы хотите ненадолго выставить локальный сервис во внешний мир. Конечно, для этого понадобится _публичный входящий шлюз (ingress-сервер)_. И хорошая новость в том, что любой публичный сервер с SSH-демоном может выступать таким шлюзом:

```bash
ssh -R [remote_addr:]remote_port:local_addr:local_port [user@]gateway_addr
```

Вышеприведённая команда выглядит не сложнее её аналога `ssh -L`. Но есть подводный камень...

**По умолчанию такой SSH-туннель позволит использовать в качестве удалённого адреса только localhost самого шлюза.** Другими словами, ваш локальный порт станет доступен только изнутри самого сервера-шлюза, что, скорее всего, не то, что вам на самом деле нужно. Например, я обычно хочу использовать публичный адрес шлюза как удаленный адрес, чтобы выставить свои локальные сервисы в публичный интернет. Для этого SSH-сервер должен быть настроен параметром [`GatewayPorts yes`](https://linux.die.net/man/5/sshd_config#GatewayPorts).

Вот для чего может использоваться удалённая переадресация портов:

  * Выставка девелоперского сервиса с вашего ноутбука в публичный интернет для быстрого демо.
  * Выставка вашего homelab в публичный интернет (для любых целей).
  * [Прокидывание отладочного порта вашего локального браузера к удалённому и/или песочному кодинг-агенту](/docs/playground-recipes/coding-agent-with-browser-access).

Сервис привязан к интерфейсу loopback, так что сейчас никто, кроме самой машины `local`, до него не доберётся. Попробуйте обратиться к нему с удалённой машины:

```bash
curl --connect-timeout 3 203.0.113.20:80  # local.public
```

```text
curl: (7) Failed to connect to 203.0.113.20 port 80 after 0 ms: Could not connect to server
```

Мы хотим выставить его через шлюз `remote` и потреблять с хоста `private`. Шлюз `remote` уже имеет `GatewayPorts yes` в своём `sshd_config`, так что мы можем попросить его слушать на всех его интерфейсах (`0.0.0.0`) и переадресовывать трафик обратно к нам. **Однако машине `local` нужно сначала установить туннель.**

С локального хоста запустите удалённую переадресацию портов:

```bash
ssh -f -N -R 0.0.0.0:8080:localhost:80 203.0.113.30
#            remote       local        via
```

Теперь локальный веб-сервис опубликован на интерфейсах шлюза. Подтвердим это с _третьей_ машины — хоста private, который может достучаться до шлюза `remote` через VPC:

```bash
curl 172.16.0.30:8080  # remote.vpc
```

```text
Hello from your local workstation (localhost-only service).
```

## Удалённая переадресация портов в домашнюю или приватную сеть

Подобно локальной переадресации портов, у удалённой есть собственный режим _бастиона/jump-хоста_. Но на этот раз роль jump-хоста играет машина с SSH-клиентом (например, ваш девелоперский ноутбук). В частности, это позволяет выставлять порты домашней (или приватной) сети, доступные с вашего ноутбука, во внешний мир через удалённый SSH-сервер, выступающий входящим шлюзом:

```bash
ssh -R [remote_addr:]remote_port:local_addr:local_port [user@]gateway_addr
```

Выглядит почти идентично простому удалённому SSH-туннелю, но пара `local_addr:local_port` становится адресом устройства в домашней сети. Вот как это можно изобразить на диаграмме:

Я обычно использую свой ноутбук как тонкий клиент, а реальная разработка происходит на удалённом сервере. Иногда такой удалённый сервер может находиться в моей домашней сети и не иметь доступа в интернет или иметь ограниченный доступ (для дополнительной изоляции). Вот тогда я и могу захотеть положиться на удалённую переадресацию портов, чтобы выставить сервис с домашнего сервера в публичный интернет, используя свой ноутбук — который имеет доступ и к внутреннему серверу разработки, и к удалённому SSH-серверу (шлюзу) — как jump-хост.

Лабораторная 5: удалённая переадресация из домашней/приватной сети 👨‍🔬

Эта лабораторная воспроизводит схему с диаграммы выше. Сервис, который мы хотим выставить, работает на хосте `internal` внутри изолированной домашней сети (`192.168.0.10:80`). Наша рабочая станция `local` имеет доступ к домашней сети, а также SSH-доступ к публичному шлюзу `remote`, так что она играет роль jump-хоста.

Хост `local` может добраться до сервиса `internal` через домашнюю сеть. С локального хоста:

```bash
curl 192.168.0.10:80  # internal.home
```

```text
Hello from the internal home-network host (192.168.0.10).
```

Снаружи, однако, устройство `internal` невидимо. Попробуйте обратиться к нему с удалённого хоста:

```bash
curl --connect-timeout 3 192.168.0.10:80  # internal.home
```

```text
curl: (28) Connection timed out after 3001 milliseconds
```

У хоста `remote` нет маршрута в домашнюю сеть, поэтому запрос просто истекает по таймауту.

Теперь с локального хоста **запустите удалённую переадресацию портов со шлюза `remote` на устройство `internal`**. Адресат переадресации (`192.168.0.10`) разрешается SSH-клиентом, т. е. с точки зрения хоста `local`:

```bash
ssh -f -N -R 0.0.0.0:8081:192.168.0.10:80 203.0.113.30
#            remote       local           via
```

Наконец, проверьте, что сервис из домашней сети стал доступен на шлюзе — с хоста private, который имеет доступ к шлюзу через VPC:

```bash
curl 172.16.0.30:8081  # remote.vpc
```

```text
Hello from the internal home-network host (192.168.0.10).
```

## Динамическая локальная переадресация портов

Этот режим переадресации менее прозрачен для клиентов, но и значительно гибче обычной локальной переадресации. Вместо привязки локального порта к единственному удалённому адресату (как делает `ssh -L`), **динамическая (локальная) переадресация портов** превращает SSH-клиент в локальный [SOCKS-прокси](https://en.wikipedia.org/wiki/SOCKS). Любое приложение, говорящее на SOCKS, может затем отправлять через него трафик, выбирая фактический хост и порт назначения _для каждого соединения_ — они будут переданы SSH-серверу, который разрешит адресата и установит соединение:

```bash
ssh -D [local_addr:]local_port [user@]sshd_addr
```

Когда используется флаг `-D`, SSH-клиент на вашей машине запускает SOCKS-прокси, слушающий на `local_port` (по умолчанию на `localhost`). Каждое соединение через прокси переадресуется на любой адрес, запрошенный SOCKS-клиентом, доступный с машины `sshd_addr`.

Другими словами, это как `ssh -L`, но вам не нужно заранее указывать единственный `remote_addr:remote_port`, потому что протокол SOCKS позволяет задать адресата в начале каждого соединения (несколькими дополнительными байтами, отправляемыми прямо перед полезной нагрузкой). Один (локальный) проксируемый порт даёт вам доступ к _каждому_ хосту и порту, достижимым с (удалённого) SSH-сервера.

Вот для чего может использоваться динамическая переадресация портов:

  * Вызовы API в приватной сети через бастион без отдельного туннеля на каждый сервис.
  * Просмотр внутренних веб-приложений в удалённой сети через единственный jump-хост.
  * Доступ к целому парку VPC-эндпоинтов с вашего ноутбука через один EC2-инстанс.

Совет

Используйте `ssh -f -N -D`, чтобы запустить SOCKS-прокси в фоне.

Лабораторная 6: использование SSH-туннелей для динамической переадресации портов 👨‍🔬

Это снова сценарий с бастионом из лабораторной 2, только на этот раз мы не будем привязывать туннель к единственному адресату.

Сначала убедимся, что мы не можем добраться до адресата `private` с локальной машины:

```bash
curl --connect-timeout 3 172.16.0.40:80  # private.vpc
```

```text
curl: (28) Connection timed out after 3002 milliseconds
```

Теперь на локальном хосте запустите SOCKS-прокси через хост `remote`:

```bash
ssh -f -N -D 1080 203.0.113.30  # remote.public
```

Если вы укажете `curl` на прокси, чтобы добраться до приватного VPC-сервиса, запрос пройдёт:

```bash
curl --socks5-hostname localhost:1080 172.16.0.40:80
#                      via            private.vpc
```

```text
Hello from the private VPC host (172.16.0.40).
```

Заметьте, что в отличие от `ssh -L`, клиент — в данном случае curl — должен уметь говорить на SOCKS (см. флаг `--socks5-hostname`).

Тот же SOCKS-прокси добирается до _любого_ хоста, доступного машине `remote`, — включая _второй_ VPC-хост — без установки отдельного туннеля; попробуйте обратиться к машине `private-2`:

```bash
curl --socks5-hostname localhost:1080 172.16.0.50:80
#                      via            private-2.vpc
```

```text
Hello from the second private VPC host (172.16.0.50).
```

С `ssh -L` доступ к обоим приватным хостам означал бы два отдельных туннеля (по одному на каждый `remote_addr:remote_port`). Один прокси `ssh -D` покрывает всю сеть за бастионом.

## Динамическая удалённая переадресация портов

Точно как у `ssh -L` есть динамический собрат в лице `ssh -D`, у команды `ssh -R` есть собственный динамический режим. Если убрать из `-R` фиксированный адресат и передать только порт, OpenSSH превращает сам **SSH-сервер** в SOCKS-прокси. Это точное зеркало `-D`: на этот раз прокси живёт на шлюзе, и каждое соединение через него туннелируется обратно к `ssh`-клиенту и разрешается с _его_ точки зрения:

```bash
ssh -R [bind_address:]port [user@]gateway_addr
```

Флаг `-R` **без адресата означает**:

  * На удалённом шлюзе SSH-сервер запускает SOCKS-прокси, слушающий на `port` (на `localhost` шлюза по умолчанию, либо на всех интерфейсах при `GatewayPorts yes`).
  * Каждое соединение через прокси туннелируется обратно к `ssh`-клиенту и переадресуется на любой адрес, запрошенный SOCKS-клиентом, достижимый со стороны клиента.

Это как обычный `ssh -R`, но вам не нужно заранее выбирать единственный `local_addr:local_port`. Один прокси на шлюзе выставляет _каждый_ хост и порт, достижимые с `ssh`-клиента, — например, целую домашнюю сеть.

Замечание

Удалённая динамическая переадресация требует OpenSSH 7.6 или новее на клиенте. Как и с обычным `ssh -R`, привязка прокси к не-loopback адресу на шлюзе требует `GatewayPorts yes` в его `sshd_config`.

Совет

Используйте `ssh -f -N -R`, чтобы запустить SOCKS-прокси в фоне.

Лабораторная 7: использование SSH-туннелей для удалённой динамической переадресации 👨‍🔬

Это снова сценарий с домашней сетью из лабораторной 5 — мы хотим выставить устройства, доступные только хосту `local`, через публичный шлюз `remote`, — но на этот раз один прокси покрывает их все.

Сначала убедимся, что мы не можем добраться до хоста `internal` с приватной машины:

```bash
curl 192.168.0.10:80  # internal.home
```

```text
curl: (7) Failed to connect to 192.168.0.10 port 80 after 0 ms: Could not connect to server
```

Теперь с локального хоста превратите шлюз `remote` в SOCKS-прокси и установите с ним туннель:

```bash
ssh -f -N -R 0.0.0.0:1080 203.0.113.30  # remote.public
```

Чтобы перепроверить связность, с хоста private снова используйте прокси шлюза, чтобы добраться до домашнего устройства `internal`:

```bash
curl --socks5-hostname 172.16.0.30:1080 192.168.0.10:80
#                      via              internal.home
```

```text
Hello from the internal home-network host (192.168.0.10).
```

Тот же прокси добирается до всего, что доступно `ssh`-клиенту (`local`), — включая его собственный loopback-сервис:

```bash
curl --socks5-hostname 172.16.0.30:1080 127.0.0.1:80
#                      via              local's localhost
```

```text
Hello from your local workstation (localhost-only service).
```

## Резюме

Краткое резюме и пара мнемоник, которые помогут запомнить команды SSH-туннелирования:

  * **Локальная переадресация портов** (`ssh -L`) делает удалённый сервис доступным на локальном порту.
  * **Удалённая переадресация портов** (`ssh -R`) делает локальный сервис доступным на удалённом порту.
  * **Динамическая локальная переадресация** (`ssh -D`) превращает локальный `ssh`-клиент в SOCKS-прокси.
  * **Динамическая удалённая переадресация** (`ssh -R` без адресата) превращает сервер `sshd` в SOCKS-прокси.
  * Локальная переадресация (`ssh -L`) подразумевает, что именно `ssh`-клиент начинает слушать новый порт.
  * Удалённая переадресация (`ssh -R`) подразумевает, что именно сервер `sshd` начинает слушать дополнительный порт.
  * Слово **local** может означать либо **машину SSH-клиента**, либо внутренний хост, доступный с неё.
  * Слово **remote** может означать либо **машину SSH-сервера (sshd)**, либо любой хост, доступный с неё.
  * Мнемоники: _ssh **-L** **l**ocal:remote_ и _ssh **-R** **r**emote:local_, и именно левая сторона открывает новый порт.
