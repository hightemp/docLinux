# SSH port forwarding для начинающих

Нирали (Nirali) · 24 января 2021 · 13 мин чтения

Эксперименты с пробросом портов SSH с использованием Docker

Проброс портов через SSH (port forwarding) позволяет клиенту получить доступ к сервисам, работающим на стороне сервера, или серверу — к сервисам, работающим на стороне клиента, по защищённому SSH-туннелю, установленному между клиентом и сервером.

Существует три типа проброса портов:

1. Локальный (Local)
2. Удалённый (Remote)
3. Динамический (Dynamic)

Динамический проброс портов широко не используется. В этом посте я буду описывать эксперименты, использующие только локальный и удалённый проброс портов.

## Предварительные требования

* Базовое понимание использования SSH
* Базовое понимание Docker

## Основы проброса портов SSH

### Что такое локальный проброс портов?

Локальный проброс портов позволяет SSH-клиенту настроить слушающий порт на клиентской машине, который перенаправляет весь входящий трафик сервису в сети SSH-сервера через установленную SSH-сессию с сервером.

![](/images/8fe0608fdf835dfd427cf3ac7b87fc66.png)

Изображение Эрика (Erik) со StackExchange.

### Как пробросить локальные порты с помощью SSH?

Синтаксис для проброса локальных портов с помощью CLI-клиента ssh следующий:

```text
ssh -L "$local_listener:$server_side_listening_service" <other ssh options> $destination_server
```

local_listener и server_side_listening_service могут быть либо TCP-портом, либо Unix-сокетом.

### Применения локального проброса портов

* Для доступа к сервисам (вроде почтовых серверов и веб-сайтов) в защищённых безопасных сетях, которые в противном случае блокируются межсетевыми экранами.

* Для защиты небезопасных сервисов путём туннелирования трафика через SSH-сессию от клиента к jump-хосту или от клиента к целевому серверу.

### Что такое удалённый проброс портов?

Удалённый проброс портов позволяет SSH-клиенту настроить слушающий порт на SSH-сервере, который перенаправляет весь входящий трафик сервису в сети клиента через установленную SSH-сессию с сервером.

![](/images/c3445834aa0d705357bc30b826471148.png)

Изображение Эрика (Erik) со StackExchange.

### Как пробросить удалённые порты с помощью SSH?

Синтаксис для проброса удалённых портов с помощью CLI-клиента ssh следующий:

```text
ssh -R "$remote_listener:$client_side_listening_service" <other ssh options> $destination_server
```

remote_listener и client_side_listening_service могут быть либо TCP-портом, либо Unix-сокетом.

### Применения удалённого проброса портов

* Для доступа к сервисам (вроде FTP и VNC) в сети клиента или внешней сети вроде интернета, которые в противном случае блокируются межсетевыми экранами для внутренних сервисов.

Заметьте, что в одном вызове ssh-клиента может быть настроено несколько опций локального и удалённого проброса.

## Экспериментальная установка

![](/images/54f07e9e03535e6cc27a51bddeaefea4.png)

На диаграмме выше показана установка, которую я использовала для своих экспериментов. Бастионный сервер (bastion) имеет по одному интерфейсу в каждой из сетей, поскольку он используется как точка входа из внешней сети во внутреннюю.

На всех четырёх компьютерах работают следующие сервисы:

* TCP-сервер на порту 80 — это сервис, к которому будут подключаться проброшенные порты.

* Unix-сокет по пути /var/run/mysock.sock — это ещё один сервис, к которому будут подключаться проброшенные порты.

* Демон sshd, работающий на TCP-порту 22.

Компьютеры client1 и client2 идентичны во всех отношениях. В моих экспериментах client1 считается первичным клиентом, который подключается к SSH-серверу, а client2 — это дополнительный хост во внешней сети.

### Создание dockerfile и docker-compose файла

Шаги для настройки SSH-сервиса в docker можно найти в официальной документации Docker «Dockerize an SSH service». SSH-сервер настроен на разрешение входа пользователя root с паролем.

Я добавила инструкции для установки некоторых дополнительных утилит в Dockerfile на случай, если мне понадобится отладка внутри контейнера.

В каждом контейнере есть два пользователя:

* root с паролем toor. Доступ к файлу сокета ограничен только пользователем root.

* user с паролем resu.

Окружение можно настроить, выполнив следующую команду:

```bash
docker-compose up --build --remove-orphans --force-recreate
```

## Эксперимент 1: тестирование сценариев локального проброса портов

### Цель

* Узнать, как ведёт себя локальный проброс портов.

* Понаблюдать за состоянием сетевых соединений в различных сценариях локального проброса портов.

Согласно man-странице ssh, локальный проброс портов должен использоваться следующим образом.

![](/images/966ee4d14a64a9b000c00eefa0589810.png)

Источник: http://manpages.ubuntu.com/manpages/xenial/man1/ssh.1.html

### Дизайн

Требования: сессия всегда остаётся установленной между client1 и bastion для всех сценариев.

Входные данные:

Удалённые сервисы:

```text
host = nil
port = 8080

host = localhost = 127.0.0.1 (loopback-интерфейс)
port = 80

host = bastion = 172.28.1.2 (ethernet-интерфейс)
port = 80
(bastion может разрешаться в любой из IP его ethernet-интерфейсов)

host = 172.28.0.2 (другой ethernet-интерфейс bastion)
port = 80

host = *
port = 80

host = server = 172.28.0.3 (ethernet-интерфейс)
port = 80

host = google.com
port = 80

remote_socket = /var/run/mysock.sock
```

Локальные слушатели:

```text
bind_address = nil
port = 8080

bind_address = localhost = 127.0.0.1 (loopback-интерфейс)
port = 8080

bind_address = client1 = 172.28.1.4 (ethernet-интерфейс)
port = 8080

bind_address = *
port = 8080

bind_address = client2 = 172.28.1.5 (ethernet-интерфейс)
port = 8080

local_socket = /tmp/listener.sock

bind_address = nil
port = 99

bind_address = nil
port = 0
```

Пользователи для подключения к bastion: root, user

Пользователи для запуска команды ssh на клиенте: root, user

### Процедура

1. docker exec в каждый контейнер, чтобы наблюдать состояние сетевых соединений.

2. Чтобы подключиться из client1 к bastion, выполните exec в client1:

```bash
docker exec -it client1 bash
```

3. Протестируйте простое ssh-соединение с bastion или client2:

```bash
ssh bastion
или
ssh client2
```

4. Чтобы наблюдать состояние сетевых соединений, выполните exec в каждый контейнер и запустите одну из следующих команд:

```text
watch netstat -na                    — не позволяет прокручивать историю
while sleep 2; do echo; date; netstat -na; done    — позволяет прокрутку истории
```

5. Установите фоновое ssh-соединение с bastion с локальным пробросом портов, выполнив следующую команду на client1. Переменные в угловых скобках — это заполнители:

```bash
ssh -L <local_listener_options>:<remote_service_options> -f <user>@bastion sleep 60
```

Сессия переводится в фон, чтобы позволить подключение к настроенному локальному слушателю с помощью того же shell.

6. Составьте сценарии на основе входных данных из предыдущего раздела, подставляя их в команду выше. Для каждого сценария подключитесь к локальному слушателю с помощью nc и зафиксируйте наблюдения.

* Чтобы подключиться к TCP-локальному слушателю, выполните nc localhost 8080 и nc client1 8080.

* Чтобы подключиться к Unix-сокету локального слушателя, выполните nc -U /tmp/listener.sock.

Если вы хотите попробовать эти сценарии сами, сейчас хорошее время, чтобы остановить чтение и сделать собственные наблюдения.

### Важные результаты и выводы

**Изменение удалённых сервисов**

* Удалённый хост не может быть nil. Это приводит к ошибке connect failed: Name or service not known.

* Когда удалённый хост — localhost или любой из ethernet-интерфейсов bastion, сервис на соответствующем интерфейсе bastion получает перенаправленный трафик. Когда хост — server или google.com, трафик перенаправляется сервису, работающему на server или google.com соответственно. Чтобы подключиться к google.com с помощью nc, направьте вывод printf "HEAD / HTTP/1.0\r\n\r\n" в его stdin.

* Когда удалённый хост — *, сервис получает трафик на loopback-интерфейсе.

* Подключение к удалённому сокету завершается неудачей, когда пользователь — user, поскольку у user нет прав на чтение файла сокета.

**Изменение локальных слушателей**

* Когда bind_address равен nil, интерфейсом по умолчанию для слушателя является loopback-интерфейс, т.е. после выполнения ssh -L 8080:localhost:80 -f bastion sleep 60 nc localhost 8080 подключается, но nc client1 8080 — нет. Если опция -o GatewayPorts=yes передана команде ssh, bind_address равный nil создаёт слушателя на всех интерфейсах.

* Когда bind_address — localhost или client1, локальный слушатель доступен на соответствующем интерфейсе bind_address. Когда bind_address — *, слушатель доступен на всех интерфейсах.

* Логически неверно иметь bind_address, который не находится на одном из интерфейсов машины, поскольку невозможно создать слушающий сервис на интерфейсе другой машины, не находясь физически внутри другой машины. Следовательно, если bind_address установлен в client2, проброс портов завершается неудачей.

* Я добавила этот случай просто для подтверждения моего понимания проброса портов. Поскольку удалённым сервисом может быть любой сервис, доступный из сети сервера, пользователь, скорее всего, предположит, что то же самое верно для локального слушателя и что слушатель также может быть настроен на любой машине, доступной из сети клиента.

* Когда слушатель — это сокет, повторное использование сокета приводит к ошибке bind, например Address already in use. Чтобы преодолеть это, используйте флаг опции -o StreamLocalBindUnlink=yes в команде ssh.

* Man-страница sshd_config утверждает, что добавление строки StreamLocalBindUnlink yes в файл /etc/ssh/sshd_config на сервере также должно решить проблему. Однако для меня это не сработало.

* Также заметьте, что завершение процесса sshd на bastion для его перезапуска остановит контейнер. Чтобы любые изменения конфигурации вступили в силу, перезапустите контейнер bastion после завершения процесса sshd или запустите новый демон sshd на другом порту с помощью /usr/sbin/sshd -D -p 2222.

* Файл сокета слушателя, созданный процессом ssh, принадлежит пользователю, который запустил ssh. Поэтому команда ssh -o StreamLocalBindUnlink=yes -L /tmp/listener.sock:localhost:80 bastion -f sleep 20 завершится неудачей при подключении к локальному сокету, если она выполняется пользователем user, а файл сокета ранее уже был создан пользователем root.

* Вывод netstat -na показывает несколько слушающих Unix-сокетов по одному и тому же пути, когда сокет переиспользуется в течение короткого интервала, и несколько TCP-соединений с одним и тем же портом в состояниях TIME_WAIT и LISTEN, когда порты переиспользуются в течение короткого интервала. Эти соединения автоматически удаляются, когда фоновое ssh-соединение завершается.

* Непривилегированный пользователь не может привязаться к привилегированному порту. Поэтому user на client1 не может создать слушателя на порту 99.

* Привязка к порту 0 не разрешена. Это приводит к ошибке Bad local forwarding specification '0:localhost:80'.

**Другие наблюдения**

* Любая комбинация локальных слушателей и удалённых сервисов может использоваться, как упомянуто в man-странице ssh.

## Эксперимент 2: тестирование сценариев удалённого проброса портов

### Цель

* Узнать, как ведёт себя удалённый проброс портов.

* Понаблюдать за состоянием сетевых соединений в различных сценариях удалённого проброса портов.

Согласно man-странице ssh, удалённый проброс портов должен использоваться следующим образом.

![](/images/9fdaa0a1e0e2107edff5b29533257844.png)

Источник: http://manpages.ubuntu.com/manpages/xenial/man1/ssh.1.html

### Дизайн

Требования: сессия всегда остаётся установленной между client1 и bastion для всех сценариев.

Входные данные:

Локальные сервисы:

```text
host = nil
port = 8080

host = localhost = 127.0.0.1 (loopback-интерфейс)
port = 80

host = client1 = 172.28.1.4 (ethernet-интерфейс)
port = 80

host = *
port = 80

host = client2 = 172.28.1.5 (ethernet-интерфейс)
port = 80

host = google.com
port = 80

local_socket = /var/run/mysock.sock
```

Удалённые слушатели:

```text
bind_address = nil
port = 8080

bind_address = localhost = 127.0.0.1 (loopback-интерфейс)
port = 8080

bind_address = bastion = 172.28.1.2 (ethernet-интерфейс)
port = 8080

bind_address = bastion = 172.28.0.2 (другой ethernet-интерфейс bastion)
port = 8080

bind_address = *
port = 8080

bind_address = server = 172.28.0.3 (ethernet-интерфейс)
port = 8080

remote_socket = /tmp/listener.sock

bind_address = nil
port = 99

bind_address = nil
port = 0
```

Пользователи для подключения к bastion: root, user

Пользователи для запуска команды ssh на клиенте: root, user

### Процедура

1. Выполните шаги с 1 по 3 из процедуры эксперимента 1.

2. Установите ssh-соединение с bastion с удалённым пробросом портов, выполнив следующую команду на client1. Переменные в угловых скобках — это заполнители:

```bash
ssh -R <remote_listener_options>:<local_service_options> <user>@bastion
```

Сессия теперь не переводится в фон, поскольку слушатель находится на сервере и может быть протестирован изнутри ssh-сессии.

3. Составьте сценарии на основе входных данных из предыдущего раздела, подставляя их в команду выше. Для каждого сценария подключитесь к слушателю с bastion с помощью nc.

* Чтобы подключиться к TCP-слушателю, выполните nc $bastion_ip 8080.

* Чтобы подключиться к слушателю Unix-сокета, выполните nc -U /tmp/listener.sock.

Если вы хотите попробовать эти сценарии сами, сейчас хорошее время, чтобы остановить чтение и сделать собственные наблюдения.

### Важные результаты и выводы

**Изменение локальных сервисов**

* Хост для клиентского сервиса не может быть nil. Это приводит к ошибке connect failed: Name or service not known.

* Когда клиентский хост (удалённый для сервера) — localhost, или любой IP ethernet-интерфейса client1, client2 или google.com, трафик сервера перенаправляется соответствующему хосту.

* Когда хост — *, сервис получает трафик на loopback-интерфейсе.

* Подключение к клиентскому сокету /var/run/mysock.sock с bastion успешно выполняется обоими SSH-пользователями — root и user — при условии, что пользователь root на client1 запустил ssh-процесс для подключения к bastion. Если client1 входит как user user для установления сессии удалённого проброса портов с bastion, подключение к сокету завершится ошибкой Permission denied для любого пользователя, вошедшего в bastion.

**Изменение удалённых слушателей**

* Когда bind_address — nil, localhost, любой из IP ethernet-интерфейсов bastion, server или *, слушатель всегда находится на loopback-интерфейсе bastion. Это упомянуто в man-странице.

* TCP-слушающие сокеты на сервере будут привязаны только к loopback-интерфейсу. Указание удалённого bind_address будет успешным только если опция GatewayPorts включена на сервере.

* Когда GatewayPorts yes установлено в /etc/ssh/sshd_config на bastion (заметьте, что изменения конфигурации требуют перезагрузки демона sshd или запуска нового сервиса на порту, отличном от 22), это заставляет все удалённые пробросы портов привязываться к wildcard-адресу, т.е. конфигурация bind_address игнорируется, и слушатель доступен на всех интерфейсах на настроенном порту.

* Когда GatewayPorts clientspecified установлено в /etc/ssh/sshd_config на bastion, bind_address равный nil по умолчанию означает localhost, bind_address равный bastion позволяет настроить слушателя на обоих его ethernet-интерфейсах, любой конкретный IP bastion создаёт слушателя на соответствующем интерфейсе, а * по умолчанию означает wildcard-адрес.

* Нелогично создавать слушателя на другой машине, поэтому bind_address не может быть установлен в server.

* Когда слушатель — это сокет, повторное использование сокета приводит к ошибке. Установка флага опции -o StreamLocalBindUnlink=yes в команде ssh, как в случае локального проброса портов, не решает проблему. Добавление строки StreamLocalBindUnlink yes в файл /etc/ssh/sshd_config на bastion решает её.

* Файл сокета слушателя принадлежит пользователю, который использовался для подключения. Поэтому команда ssh -R /tmp/listener.sock:localhost:80 user@bastion завершается неудачей при подключении к сокету, если файл сокета ранее уже был создан пользователем root.

* Непривилегированный пользователь не может привязаться к привилегированному порту. Поэтому user на bastion не может иметь слушателя на порту 99.

* Привязка к порту 0 приводит к динамически выделенному слушающему порту на bastion с сообщением, похожим на Allocated port 46307 for remote forward to localhost:80, выводимым на stdout.

**Другие наблюдения**

* Любая комбинация удалённых слушателей и локальных сервисов может использоваться, как упомянуто в man-странице ssh.

## Эксперимент 3: проброс портов через jump-серверы

### Цель

* Узнать, работает ли и как работает проброс портов через сессии jump-хоста, понимая, какие сетевые соединения создаются.

* Сравнить проброс с bastion с прямым пробросом с сервера (которым может быть либо сам bastion, либо сервер, подключённый к bastion).

### Дизайн

Требования: сессия должна быть установлена между client1 и server (через bastion).

Тестовые случаи:

Локальный проброс портов

* слушать на TCP-порту — перенаправлять на TCP-порт
* слушать на TCP-порту — перенаправлять на удалённый сокет
* слушать на локальном сокете — перенаправлять на TCP-порт
* слушать на локальном сокете — перенаправлять на удалённый сокет

Удалённый проброс портов

* слушать на TCP-порту — перенаправлять на TCP-порт
* слушать на TCP-порту — перенаправлять на удалённый сокет
* слушать на локальном сокете — перенаправлять на TCP-порт
* слушать на локальном сокете — перенаправлять на удалённый сокет

### Процедура

Следуйте процедуре эксперимента 1 для локального проброса портов и эксперимента 2 для удалённого проброса портов. Подключитесь к server через bastion следующим образом:

```bash
ssh -J $USER1@bastion $USER2@server
```

Если вы хотите попробовать это сами, сейчас хорошее время, чтобы остановить чтение и сделать собственные наблюдения.

### Результаты

**Случай 1**: Локальный проброс портов со слушателем и сервисом на TCP-портах.

```text
ssh -J bastion -L 8080:localhost:80 -f server sleep 10
```

### Выводы

* Проброс портов через jump-хосты работает.

* Во всех случаях трафик перенаправляется с конечного сервера, а не с bastion.

* Сам SSH-трафик перенаправляется с bastion на сервер в сети bastion. Это можно наблюдать по выводу netstat на bastion.

* Более эффективно пробрасывать локальные порты, подключаясь к bastion, а не к другим серверам в сети bastion, чтобы избежать дополнительных ssh-соединений.

* Для проброса удалённых портов сервера необходимо подключение к серверу напрямую через jump-хосты, поскольку слушатели создаются на сервере. Альтернативой может быть настройка удалённого проброса портов на ethernet-интерфейсе bastion.
