# 1) Docker и DNS

В [части III](http://zwischenzugs.com/2018/07/06/anatomy-of-a-linux-dns-lookup-part-iii/) мы рассмотрели DNSMasq и узнали, что он работает, направляя DNS-запросы на адрес localhost `127.0.0.1`, где процесс, слушающий порт 53, принимает запрос.

Так что, когда вы запускаете Docker-контейнер на хосте с такой настройкой, что вы ожидаете увидеть в его `/etc/resolv.conf`?

Подумайте и попробуйте угадать.

Вот вывод по умолчанию при стандартной установке Docker:

```bash
$  docker run  ubuntu cat /etc/resolv.conf
# Dynamic resolv.conf(5) file for glibc resolver(3) generated by resolvconf(8)
#     DO NOT EDIT THIS FILE BY HAND -- YOUR CHANGES WILL BE OVERWRITTEN
# 127.0.0.53 is the systemd-resolved stub resolver.
# run "systemd-resolve --status" to see details about the actual nameservers.

search home
nameserver 8.8.8.8
nameserver 8.8.4.4
```

Хм-м.

#### Откуда взялись адреса `8.8.8.8` и `8.8.4.4`?

Когда я размышлял над этим вопросом, моей первой мыслью было, что контейнер унаследует настройки `/etc/resolv.conf` от хоста. Но небольшое размышление показывает, что это сработает не всегда.

Если на хосте настроен DNSmasq, файл `/etc/resolv.conf` указывает на loopback-адрес `127.0.0.1`. Если бы он передавался в контейнер, контейнер выполнял бы DNS-запросы из собственного сетевого контекста, а внутри контекста контейнера DNS-сервер недоступен — DNS-запросы завершались бы ошибкой.

«Ага!» — можете подумать вы: мы всегда можем использовать DNS-сервер хоста, указав IP-адрес _хоста_, доступный из контейнера как маршрут по умолчанию:

```text
root@79a95170e679:/# ip route
default via 172.17.0.1 dev eth0
172.17.0.0/16 dev eth0 proto kernel scope link src 172.17.0.2
```

#### Использовать хост?

Отсюда мы можем вычислить, что «хост» находится по IP-адресу `172.17.0.1`, так что можно попробовать вручную направить DNS туда с помощью dig (можно было бы также обновить `/etc/resolv.conf` и запустить `ping`; просто кажется удачным моментом представить `dig` и его флаг `@`, который направляет запрос на указанный вами IP-адрес):

```text
root@79a95170e679:/# dig @172.17.0.1 google.com | grep -A1 ANSWER.SECTION
;; ANSWER SECTION:
google.com.             112     IN      A       172.217.23.14
```

Однако: это сработало бы, если вы используете DNSMasq, но без него — нет, поскольку на хосте нет DNS-сервера для запросов.

Так что решение Docker в этой дилемме — обойти всю эту сложность и направить ваши DNS-запросы на DNS-серверы Google `8.8.8.8` и `8.8.4.4`, игнорируя контекст хоста.

_Анекдот: это стало источником моей первой проблемы с Docker ещё в 2013 году. Наша корпоративная сеть блокировала доступ к этим IP-адресам, поэтому мои контейнеры не могли разрешать URL._

Итак, это Docker-контейнеры, но _оркестраторы_ контейнеров вроде Kubernetes могут делать совсем другие вещи…

# 2) Kubernetes и DNS

Единицей развёртывания контейнеров в Kubernetes является Pod. Pod — это набор совместно размещённых контейнеров, которые (помимо прочего) делят один IP-адрес.

Дополнительная сложность с Kubernetes в том, что нужно пересылать запросы к сервисам Kubernetes (например, `myservice.kubernetes.io`) правильному резолверу в частной сети, выделенной под адреса этих сервисов. Говорят, что эти адреса находятся в «кластерном домене» (cluster domain). Этот кластерный домен настраивается администратором, так что это может быть `cluster.local` или `myorg.badger` в зависимости от вашей конфигурации.

В Kubernetes у вас есть четыре опции настройки работы DNS-запросов внутри вашего pod.

  * **Default**

Эта (вводящая в заблуждение по названию) опция использует тот же путь DNS-разрешения, что и хост, на котором запущен pod, как в «наивном» DNS-запросе, описанном ранее. Название вводит в заблуждение, потому что это не значение по умолчанию! По умолчанию — ClusterFirst.

Если вы хотите переопределить записи `/etc/resolv.conf`, вы можете сделать это в конфигурации kubelet.

  * **ClusterFirst**

ClusterFirst выполняет избирательную пересылку DNS-запросов. Это достигается одним из двух способов в зависимости от конфигурации.

В первом, более старом и простом варианте, соблюдалось правило: если кластерный домен не найден в запросе, запрос пересылается хосту.

Во втором, более новом подходе, вы можете настроить избирательную пересылку на внутреннем DNS.

Вот как выглядит конфигурация, а также диаграмма из [документации Kubernetes](https://kubernetes.io/docs/tasks/administer-cluster/dns-custom-nameservers/#impacts-on-pods), показывающая поток:

```text
apiVersion: v1
kind: ConfigMap
metadata:
  name: kube-dns
  namespace: kube-system
data:
  stubDomains: |
    {"acme.local": ["1.2.3.4"]}
  upstreamNameservers: |
    ["8.8.8.8", "8.8.4.4"]
```

Запись `stubDomains` определяет конкретные DNS-серверы для конкретных доменов. Upstream-серверы — это серверы, к которым мы обращаемся, когда ничто другое не перехватило DNS-запрос.

Это реализуется с помощью нашего старого друга DNSMasq, запущенного в pod.

Остальные две опции более нишевые:

  * **ClusterFirstWithHostNet**

Это применяется, если вы используете хостовую сеть для ваших pod, то есть обходите сетевую настройку Docker, чтобы использовать ту же сеть, что и напрямую на хосте, где запущен pod.

  * **None**

None ничего не делает с DNS, но заставляет вас указать настройки DNS в поле `dnsConfig` в спецификации pod.

### Грядёт CoreDNS

И если этого было недостаточно, всё снова изменится с приходом в Kubernetes CoreDNS, заменяющего kube-dns. CoreDNS предложит ряд преимуществ перед kube-dns: он более конфигурируем и более эффективен.

Узнать больше можно [здесь](https://coredns.io/).

Если вам интересна работа сети OpenShift, я писал об этом пост [здесь](http://zwischenzugs.com/2017/10/21/openshift-3-6-dns-in-pictures/). Но он был для версии 3.6, так что теперь, скорее всего, устарел.
