# rsync, статья 1: сценарии использования (2022)

Источник: [rsync, article 1: Scenarios (2022)](https://michael.stapelberg.ch/posts/2022-06-18-rsync-article-1-scenarios/)

Опубликовано 18 июня 2022, последний раз изменено 2 июля 2022

Это первая статья в серии публикаций о rsync, [см. обзор серии](../2022-06-18-rsync-overview/).

Чтобы показать, зачем имеет смысл изучать rsync, я приведу три сценария, в которых я по достоинству оценил rsync: перенос DokuWiki, развёртывание ПО и резервное копирование.

## Сценарий: перенос DokuWiki с помощью rsync

Недавно я настроил пару инструментов для веб-сайта, построенного на DokuWiki, например, проверку битых ссылок и программу статистики. Чтобы не перегружать рабочий сайт (и, возможно, не создавать ложных запросов, мешающих статистике), я решил, что лучше всего запустить отдельную копию установки DokuWiki локально. Это требует синхронизации:

1. Файлов исходного кода PHP самого DokuWiki (включая плагины и конфигурацию)
2. По одному текстовому файлу на каждую вики-страницу и все загруженные медиафайлы

Установка DokuWiki — это именно тот вид файлового дерева, который [`scp(1)`](https://manpages.debian.org/scp.1) не может эффективно передать (слишком много мелких файлов), а [`rsync(1)`](https://manpages.debian.org/rsync.1) — может! Передача с помощью `rsync` занимает всего несколько секунд, неважно, идёт ли речь о полном скачивании (может быть проще для пакетных задач) или инкрементальной синхронизации (эффективнее для регулярных синхронизаций, таких как резервное копирование).

## Сценарий: развёртывание ПО с помощью rsync

Для небольших проектов, где я не публикую новые версии через Docker, я вместо этого использую shell-скрипт для передачи и запуска моего ПО на сервере.

`rsync` здесь отлично подходит: он эффективно передаёт множество мелких файлов (статические ресурсы и шаблоны), передаёт только те бинарники, которые действительно изменились, и не возражает, если загружаемый бинарный файл сейчас запущен (в отличие, например, от [`scp(1)`](https://manpages.debian.org/scp.1)).

Чтобы показать, как может выглядеть такой скрипт, вот мой push-скрипт для [Debian Code Search](https://codesearch.debian.net/):

```bash
#!/bin/zsh
set -ex

# Asynchronously transfer assets while compiling:
(
    ssh root@dcs 'for i in $(seq 0 5); do mkdir -p /srv/dcs/shard${i}/{src,idx}; done'
    ssh root@dcs "adduser --disabled-password --gecos 'Debian Code Search' dcs || true"
    rsync -r systemd/ root@dcs:/etc/systemd/system/ &
    rsync -r cmd/dcs-web/templates/ root@dcs:/srv/dcs/templates/ &
    rsync -r static/ root@dcs:/srv/dcs/static/ &
    wait
) &

# Compile a new Debian Code Search version:
tmp=$(mktemp -d)
mkdir $tmp/bin
GOBIN=$tmp/bin \
GOAMD64=v3 \
  go install \
  -ldflags '-X github.com/Debian/dcs/cmd/dcs-web/common.Version=$version' \
  github.com/Debian/dcs/cmd/...

# Transfer the Debian Code Search binaries:
rsync \
  $tmp/bin/dcs-{web,source-backend,package-importer,compute-ranking,feeder} \
  $tmp/bin/dcs \
  root@dcs:/srv/dcs/bin/

# Wait for the asynchronous asset transfer to complete:
wait

# Restart Debian Code Search on the server:
UNITS=(dcs-package-importer.service dcs-source-backend.service dcs-compute-ranking.timer dcs-web.service)
ssh root@dcs systemctl daemon-reload \&\& \
  systemctl enable ${UNITS} \; \
  systemctl reset-failed ${UNITS} \; \
  systemctl restart ${UNITS} \; \
  systemctl reload nginx

rm -rf "${tmp?}"
```

## Сценарий: резервное копирование с помощью rsync

Первой системой резервного копирования, которой я пользовался, была [bacula](https://en.wikipedia.org/wiki/Bacula), которую Википедия описывает как систему резервного копирования корпоративного уровня. Это определённо соответствует моему впечатлению — как в положительном, так и в отрицательном смысле: bacula очень мощная, но некоторые, казалось бы, обычные операции в bacula оказываются весьма сложными. Восстановление одного файла или дерева каталогов из резервной копии всегда требовало больше усилий, чем я считал разумным. По какой-то причине мне часто приходилось восстанавливать каталоги резервных копий, прежде чем я мог получить доступ к содержимому резервной копии (точных деталей не помню).

Переезжая в прошлый раз в новую квартиру, я воспользовался возможностью изменить свою стратегию резервного копирования. Вместо использования сложного специализированного ПО со своим собственным форматом томов файлов (как bacula) я хотел, чтобы файлы из резервных копий были доступны на уровне файловой системы со стандартными инструментами вроде `rm`, `ls`, `cp` и т.д.

Работа с файлами в обычной файловой системе облегчает повседневное использование, а также гарантирует, что когда мой сетевой накопитель умрёт, я смогу просто подключить жёсткий диск к любому ПК, загрузить Linux live-систему и восстановить свои данные.

Чтобы создавать резервные копии машин в файловую систему моего [сетевого накопителя](/posts/2019-10-23-nas/), я в итоге пришёл к [самописному скрипту-обёртке вокруг rsync](https://github.com/stapelberg/zkj-nas-tools/blob/85e445a284c89590d595a52e16cb6dd652b1388e/dornroeschen/backup-remote.pl), который копирует полную файловую систему каждой машины в деревья каталогов с датами:

```text
storage2# ls -l backup/midna/2022-05-27
bin   boot  etc  home  lib  lib64  media  opt
proc  root  run  sbin  sys  tmp    usr    var

storage2# ls -l backup/midna/2022-05-27/home/michael/configfiles/zshrc
-rw-r--r--. 7 1000 1000 14554 May  9 19:37 backup/midna/2022-05-27/home/michael/configfiles/zshrc
```

Чтобы вернуть мой `~/.zshrc` к старой версии, я могу скачать файл с помощью [`scp(1)`](https://manpages.debian.org/scp.1):

```text
midna% scp storage2:/srv/backup/midna/2022-05-27/home/michael/configfiles/zshrc ~/configfiles/zshrc
```

Чтобы сравнить целое старое дерево исходников, я могу смонтировать его с помощью [`sshfs(1)`](https://manpages.debian.org/sshfs.1):

```text
midna% mkdir /tmp/2022-05-27-i3
midna% sshfs storage2:/srv/backup/midna/2022-05-27/$HOME/i3 /tmp/2022-05-27-i3
midna% diff -ur /tmp/2022-05-27-i3 ~/i3/
```

### Инкрементальные резервные копии

Конечно, идея не в том, чтобы передавать полное содержимое машины каждый день — это быстро заполнило бы 16-терабайтный диск моего сетевого накопителя! Вместо этого можно использовать опцию rsync `--link-dest` для элегантной дедупликации файлов с помощью жёстких ссылок файловой системы:

```text
backup/midna/2022-05-26
backup/midna/2022-05-27 # rsync --link-dest=2022-05-26
```

Чтобы проверить уровень дедупликации, можно использовать [`du(1)`](https://manpages.debian.org/du.1), сначала на одном каталоге:

```text
storage2# du -hs 2022-05-27
113G	2022-05-27
```

…а затем на двух соседних каталогах:

```text
storage2# du -hs 2022-05-25 2022-05-27
112G	2022-05-25
7.3G	2022-05-27
```

Как видите, резервная копия от 2022-05-27 заняла 7.3 ГБ дискового пространства, а 104.7 ГБ были повторно использованы из предыдущих резервных копий.

Чтобы вывести все файлы, изменившиеся с момента последней резервной копии, можно использовать:

```text
storage2# find 2022-05-27 -type f -links 1 -print
```

### Ограничение: совместимость файловых систем

Существенное ограничение резервного копирования на уровне файлов состоит в том, что целевая файловая система (сетевой накопитель) должна поддерживать все возможности файловых систем, используемые на машинах, копии которых вы делаете.

Например, если вы используете [POSIX ACL](https://help.ubuntu.com/community/FilePermissionsACLs) или [расширенные атрибуты](https://wiki.archlinux.org/title/File_permissions_and_attributes#Extended_attributes) (возможно, для [Capabilities](https://wiki.archlinux.org/title/Capabilities) или [SELinux](https://wiki.archlinux.org/title/SELinux)), вам нужно убедиться, что эти возможности включены в файловой системе для резервных копий и что вы используете опцию `--xattrs` (сокращённо `-X`) у [`rsync(1)`](https://manpages.debian.org/rsync.1).

Это может превратиться из подводного камня в полный блокер, как только в дело вовлекаются несколько операционных систем. Например, версия `rsync` в macOS содержит [специфичный для Apple код](https://github.com/apple-oss-distributions/rsync/blob/aa4e500aa53b9417014c718a5ff0e29215f08e48/rsync/generator.c#L1447) для работы с Apple [resource forks](https://en.wikipedia.org/wiki/Resource_fork) и другими расширенными атрибутами. Мне неясно, может ли macOS `rsync` отправить файлы в Linux `rsync`, восстановить их и получить то же состояние системы.

К счастью, меня интересует резервное копирование только Linux-систем или лишь домашних каталогов не-Linux систем, где расширенные атрибуты не используются.

### Недостаток: медленные массовые операции (подсчёт занятого места, удаление)

Самый большой недостаток этой архитектуры в том, что работа с деревьями каталогов в массовом порядке может быть очень медленной, особенно при использовании жёсткого диска вместо SSD. Например, удаление старых резервных копий легко может занять много часов или даже несколько дней (!). Конечно, можно просто оставить команду `rm` работать в фоне, но всё равно это раздражает.

Даже простой подсчёт занятого дискового пространства каждого дерева каталогов — мучительно медленная операция. Я пробовал использовать инструменты подсчёта с сохранением состояния, вроде [duc](http://duc.zevv.nl/), но он [работал ненадёжно](https://github.com/zevv/duc/issues/240) на моих резервных копиях.

На практике я обнаружил, что для поиска больших файлов использование [`ncdu(1)`](https://manpages.debian.org/ncdu.1) на любой недавней резервной копии обычно быстро показывает этот большой файл. В одном случае я обнаружил, что `var/lib/postgresql` потребляет много гигабайт. Я исключил его в пользу использования [`pg_dump(1)`](https://manpages.debian.org/pg_dump.1), что привело к гораздо меньшим резервным копиям!

К сожалению, даже при использовании SSD определение того, какие файлы занимают больше всего места в полной резервной копии, занимает несколько минут:

```text
storage2# time du -hs backup/midna/2022-06-09
742G	backup/midna/2022-06-09

real	8m0.202s
user	0m11.651s
sys	2m0.731s
```

### Транспорт резервных копий (SSH) и планирование

Для передачи данных с помощью `rsync` с копируемой машины на мой сетевой накопитель я использую SSH.

SSH-доступ каждой машины ограничен в конфигурационном файле SSH [`authorized_keys(5)`](https://manpages.debian.org/authorized_keys.5) моего сетевого накопителя: вместо разрешения произвольных команд разрешено выполнение только одной конкретной операции. Единственной разрешённой операцией в моём случае является запуск `rrsync` («restricted rsync», ограниченный rsync) в контейнере, файловая система которого содержит только подкаталог копируемой машины, например `websrv.zekjur.net`:

```text
command="/bin/docker run --log-driver none -i -e SSH_ORIGINAL_COMMAND -v /srv/backup/websrv.zekjur.net:/srv/backup/websrv.zekjur.net stapelberg/docker-rsync /srv/backup/websrv.zekjur.net",no-port-forwarding,no-X11-forwarding ssh-ed25519 AAAAC3…
```

([Соответствующий `Dockerfile` можно найти в моей статье о Gigabit NAS](/posts/2016-11-21-gigabit-nas-coreos/#dockerfiles-rrsync-and-samba).)

Чтобы удалённо запускать такую защищённую по SSH передачу `rsync`, я использую небольшую самодельную программу планирования под названием [dornröschen](https://github.com/stapelberg/zkj-nas-tools/tree/master/dornroeschen). Программа обеспечивает включение всех задействованных машин (с помощью [Wake-on-LAN](https://en.wikipedia.org/wiki/Wake-on-LAN)) и затем запускает `rsync` через _ещё одно SSH-соединение с ограничением операции_.

Вы легко можете заменить это cron-задачей, если WOL вам не важен.

Архитектура выглядит так:

![Архитектура резервного копирования](/images/64e6c660092ab4a17c9ae54d5494bf8faa74a137be193c8450dea16269debcd7.png)

SSH-соединение с ограничением операции на каждой копируемой машине настраивается в конфигурационном файле SSH [`authorized_keys(5)`](https://manpages.debian.org/authorized_keys.5):

```text
command="/root/backup-remote.pl",no-port-forwarding,no-X11-forwarding ssh-ed25519 AAAAC3…
```
