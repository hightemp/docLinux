# Выбор адреса по умолчанию. Часть 1

Источник: [Default Address Selection Part 1 — вводная статья про выбор IPv6-адресов в Linux: RFC 3484, выбор адреса источника и назначения, таблицы `ip addrlabel`, `label`/`precedence` и настройка `/etc/gai.conf`.](https://linux-hacks.blogspot.com/2008/04/default-address-selection-part-1.html)

varun · 21 апреля 2008

Если вы знакомы с IPv6, то вам должно быть известно, что выбор адреса по умолчанию (default address selection) — очень важное понятие. Он был определён в [RFC 3484](http://www.ietf.org/rfc/rfc3484.txt). Из-за нехватки места я решил разбить эту тему на 2 части. Первая часть будет посвящена просто введению и тому, как пользоваться этой возможностью. Вторая часть объяснит внутренности ядра/glibc, задействованные в этой реализации. Надеюсь, я скоро напишу вторую часть. Перед продолжением рекомендуется прочитать сам RFC.</think> Чтобы дать краткое представление о том, что такое выбор адреса по умолчанию, я хотел бы привести пример хоста, имеющего несколько IPv6-адресов и нуждающегося в выборе того, какой адрес использовать для связи. Чтобы связь состоялась, должен быть адрес источника и адрес назначения, но проблема возникает, когда есть несколько адресов источника и назначения на выбор. IPv6 по умолчанию позволяет хостам настраивать несколько адресов, поэтому нужен алгоритм для сортировки этого списка. Выбор адреса по умолчанию можно в целом разделить на 2 типа:

1) Выбор адреса источника по умолчанию
2) Выбор адреса назначения по умолчанию

Допустим, хост A хочет связаться с другим хостом B (это может быть внешняя или внутренняя система) — ему нужно знать IP-адрес назначения хоста B. Чтобы получить адрес назначения, DNS-запрос отправляется настроенному DNS-серверу, и ответ берётся в качестве IP-адреса назначения. А что если DNS-ответ содержит несколько IP для одного доменного имени? Вот тут в игру вступает выбор адреса назначения. Теперь, когда мы «как-то» выбрали IP-адрес назначения, нам нужно выбрать подходящий IP источника. Может возникнуть вопрос: зачем нам это делать? Разве нельзя просто взять первый IP из списка IP-адресов источника и начать общение? Ответ — нет. Дело в том, что IPv6-адреса могут быть link-local, site-local или глобальными. Если адрес назначения — глобальный IP, а первый выбранный из списка IP источника — link-local, то, очевидно, связь не сможет состояться из-за несоответствия областей (scope). Поэтому нам нужен некий интеллектуальный алгоритм для выбора правильного IP источника.

Ещё один интересный аспект выбора адреса назначения — решить, какой IP использовать, если DNS-запрос возвращает как IPv4-, так и IPv6-адрес. Должен быть какой-то фактор, определяющий этот выбор. Подробнее обо всём этом — во второй части :-). Итак, у нас есть ситуация, когда адреса выбираются по определённым критериям. По умолчанию критерии соответствуют RFC. Для большинства пользователей этого достаточно, но что если их нужно изменить? Скажем, по умолчанию IPv6-адресу даётся больший приоритет, чем IPv4, а администратор хочет, чтобы больший приоритет был у IPv4. В таких случаях должен быть способ настроить выбор адреса источника и выбор адреса назначения. По этой причине RFC определяет пользовательские таблицы конфигурации (User Configuration Tables) для выбора источника/назначения.

Прежде чем перейти к таблицам конфигурации, посмотрим на один базовый факт. Выбор адреса источника реализован в ядре, а выбор адреса назначения — в glibc. Интересно, почему? Причина очень проста. Glibc реализует API DNS-запросов вроде gethostbyname и семейства, которые инициируют DNS-запрос. Так что очевидно, что этот API получает и все ответы. Имеет смысл реализовать алгоритм в API glibc.

Давайте посмотрим на пользовательские таблицы конфигурации как для выбора адреса источника, так и для выбора адреса назначения. Есть интересная статья от мейнтейнера glibc Ульриха Дреппера (Ulrich Drepper). Вы можете найти её [здесь](http://people.redhat.com/drepper/linux-rfc3484.html).

Базовые требования:

- Ядро Linux 2.6.24 или выше
- Утилиты iproute2, собранные для 2.6.24 (проверьте, поддерживает ли «#ip help» подкоманду 'addrlabel')

Когда у нас есть всё необходимое, можно приступать.

Пользовательская таблица конфигурации для выбора адреса источника:

```text
[root@t6018ab-009124035140 ip]# ./ip addrlabel show
prefix ::1/128 label 0
prefix ::/96 label 3
prefix ::ffff:0.0.0.0/96 label 4
prefix 2001::/32 label 6
prefix 2002::/16 label 2
prefix fc00::/7 label 5
prefix ::/0 label 1
```

Это пользовательская таблица конфигурации адресов источника по умолчанию. Поле «label» — очень важный аспект таблицы. Префикс с меньшим значением label получает более высокий приоритет, чем с большим. Например, префикс ::1 получает наивысший приоритет при сопоставлении меток префикса.

Допустим, у нас есть два префикса одного типа

```text
prefix 2003:470:1f00:ffff::4/64 label 8
prefix 2003:470:1f00:ffff::5/64 label 8
```

Список адресов источника:

```text
2003:470:1f00:ffff::4
2003:470:1f00:ffff::5
2003:470:1f00:ffff::6
```

Адрес назначения

```text
2003:470:1f00:ffff::7
```

Независимо от порядка списка адресов источника, IP 2003:470:1f00:ffff::6 будет выбран как правильный кандидат, поскольку у двух других адресов значение label равно 8, тогда как 2003:470:1f00:ffff::6 подпадает под правило «prefix ::/0 label 1». Таким образом, наименьшему значению label даётся более высокий приоритет. Мы можем поэкспериментировать, назначая разным префиксам разные значения label. Поскольку выбор адреса источника работает в связке с выбором адреса назначения, мы рассмотрим тестирование этого аспекта несколько позже.

Пользовательская таблица конфигурации для выбора адреса назначения:

Пользовательская таблица конфигурации адреса назначения основана на conf-файле под названием gai.conf. Он располагается в /etc/. Дистрибутивы не размещают этот файл там по определённой причине. Подробнее читайте статью Ульриха Дреппера, упомянутую выше. В моей системе файл gai.conf находится в /usr/share/doc/glibc-common-2.6/gai.conf. Этот файл нужно скопировать в /etc/, если вы намерены изменить поведение по умолчанию.

Типичный файл gai.conf:

```text
# label
# Add another rule to the RFC 3484 label table. See section 2.1 in
# RFC 3484. The default is:
#
#label ::1/128 0
#label ::/0 1
#label 2002::/16 2
#label ::/96 3
#label ::ffff:0:0/96 4
#label fec0::/10 5
#label fc00::/7 6

#

# precedence
# Add another rule the to RFC 3484 precedence table. See section 2.1
# and 10.3 in RFC 3484. The default is:
#
#precedence ::1/128 50
#precedence ::/0 40
#precedence 2002::/16 30
#precedence ::/96 20
#precedence ::ffff:0:0/96 10
#
# For sites which prefer IPv4 connections change the last line to
#
#precedence ::ffff:0:0/96 100
```

Для выбора адреса назначения два основных критерия — label и precedence (приоритет). Всегда нужно помнить: precedence связан только с выбором адреса назначения, тогда как label общий и для выбора адреса источника, и для выбора адреса назначения. Именно по этой причине обе таблицы должны оставаться синхронизированными для корректного результата.

Тестирование выбора адреса назначения

Чтобы протестировать алгоритм выбора адреса назначения, нужно написать небольшую программу. Лучший способ протестировать алгоритм выбора адреса назначения — использовать примеры из RFC 3484. Смотрите раздел 10.2.

Несколько требований:

- Добавить запись «multi on» в /etc/host.conf
- Остановить демон кеширования имён (service nscd stop)
- Скомпилировать программу, приведённую ниже (она протестирует результат выбора адреса по умолчанию)

```c
#include <errno.h>
#include <error.h>
#include <netdb.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <netinet/in.h>
#include <sys/socket.h>

char buf[INET6_ADDRSTRLEN];

int
main(int argc, char *argv[])
{
int err;
struct addrinfo *ai;
struct addrinfo hints;
struct addrinfo *runp;
int sock;

memset(&hints, '\0', sizeof(hints));
hints.ai_protocol = IPPROTO_TCP;

// dummy gethostbyname call so that /etc/host.conf is read
gethostbyname(argv[1]);

err = getaddrinfo(argv[1], "", &hints, &ai);
if (err != 0)
error(EXIT_FAILURE, 0, "getaddrinfo(%d): %s", err,
gai_strerror(err));
runp = ai;
while (runp != NULL) {
getnameinfo(runp->ai_addr, runp->ai_addrlen, buf,
INET6_ADDRSTRLEN, NULL, 0, NI_NUMERICHOST);

printf("family:%2d socktype:%2d protocol:%3d addr:%s(%d)\n",
runp->ai_family, runp->ai_socktype, runp->ai_protocol,
buf, runp->ai_addrlen);
runp = runp->ai_next;
}

freeaddrinfo(ai);
}
```

Пример из раздела 10.2 RFC:

```text
Candidate Source Addresses: 2001::2 or fec0::2 or fe80::2
Destination Address List: 2001::1 or fec0::1 or fe80::1
Result: fe80::1 (src fe80::2) then fec0::1 (src fec0::2) then 2001::1 (src 2001::2) (prefer smaller scope)
```

Выбор адреса назначения будет продемонстрирован на примере из RFC.
Первый шаг — добавить несколько DNS-записей на DNS-сервере. Это большой процесс, поэтому для простоты я буду использовать файл /etc/hosts (это работает так же, как ответы DNS-сервера).

Итак, добавьте следующее в /etc/hosts

```text
fec0::1 rockon
2001::1 rockon
fe80::1 rockon
```

Добавьте адреса источника на интерфейс

```bash
#ip -6 addr add 2001::2 dev eth0
```

Аналогично для fec0::2 и fe80::2

Следующий шаг — убедиться, что для каждого адреса назначения, добавленного в /etc/hosts, есть допустимая запись маршрута. Иначе вышеописанное не заработает.
Например: fec0::1 — это IP-адрес назначения. Алгоритм выберет его только при наличии допустимого маршрута к этому IP.

```bash
#ip -6 route add fec0::1 dev eth0
```

Аналогично добавьте маршруты для остальных кандидатов в адреса назначения.

Для запуска программы

```text
#./a.out rockon
family:10 socktype: 1 protocol: 6 addr:fe80::1(28)
family:10 socktype: 1 protocol: 6 addr:fec0::1(28)
family:10 socktype: 1 protocol: 6 addr:2001::1(28)
```

Результат показывает порядок, в котором отсортированы адреса назначения. Остальные примеры можно попробовать самостоятельно. Пользовательскую таблицу конфигурации адресов назначения (gai.conf) можно изменять, чтобы увидеть разные результаты.

Тестирование выбора адреса источника:

Давайте посмотрим, как протестировать функциональность выбора адреса источника. Лучший способ — следовать тестовым примерам, описанным в RFC 3484. Смотрите раздел 10.1.
Для тестирования выбора адреса источника используйте ping6.

Пример из раздела 10.1 RFC:

```text
Destination: 2001::1
Candidate Source Addresses: 3ffe::1 or fe80::1
Result: 3ffe::1 (prefer appropriate scope)
```

Настройте IPv6-адрес для интерфейса eth0

```bash
#ip -6 addr add 3ffe::1 dev eth0
```

fe80::1 можно игнорировать, так как link-local адрес у вас будет по умолчанию.
Добавьте допустимый маршрут к IP-адресу назначения.

```bash
#ip -6 route add 2001::1 dev eth0
#ping6 2001::1
```

Результатом будет «destination unreachable», если 2001::1 не существует. Но это не наша проблема. Сообщение о недоступности покажет, какой адрес источника был выбран. Вот так можно протестировать алгоритм выбора адреса источника. Попробуйте все разные примеры из RFC. Теперь, подправив пользовательскую таблицу конфигурации, как описано в разделе «Пользовательская таблица конфигурации для выбора адреса источника», мы можем изменить поведение.
