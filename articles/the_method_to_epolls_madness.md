# Метод безумия epoll

Источник: [the_method_to_epolls_madness](https://medium.com/@copyconstruct/the-method-to-epolls-madness-d9d2d6378642)

Синди Шридхаран · 30 октября 2017 · 16 мин чтения

Мой предыдущий пост охватывал основы файловых дескрипторов, а также некоторые из наиболее часто используемых форм неблокирующих операций ввода-вывода в Linux и BSD. Некоторые люди поинтересовались, почему он вообще не освещал epoll, но я упоминал в заключении того поста, что epoll — безусловно, самая интересная из всех тем, и поэтому она заслуживает отдельного поста.

epoll расшифровывается как event poll (опрос событий) и является специфичной для Linux конструкцией. Она позволяет процессу отслеживать несколько файловых дескрипторов и получать уведомления, когда на них возможен ввод-вывод. Она поддерживает как уведомления, срабатывающие по фронту (edge-triggered), так и по уровню (level-triggered). Прежде чем заглянуть во внутренности epoll, давайте сначала изучим синтаксис.

## Синтаксис epoll

В отличие от poll, сам по себе epoll — это не системный вызов. Это структура данных ядра, которая позволяет процессу мультиплексировать ввод-вывод на нескольких файловых дескрипторах.

![](/images/60b531c8cc245bf3b3c7ce8e83321c6f.png)

Эта структура данных может быть создана, изменена и удалена тремя системными вызовами.

### 1) epoll_create

Экземпляр epoll создаётся с помощью системного вызова epoll_create, который возвращает файловый дескриптор экземпляра epoll. Сигнатура epoll_create выглядит следующим образом:

```c
#include <sys/epoll.h>
int epoll_create(int size);
```

Аргумент size — это подсказка ядру о количестве файловых дескрипторов, которые процесс хочет отслеживать, что помогает ядру определить размер экземпляра epoll. Начиная с Linux 2.6.8, этот аргумент игнорируется, поскольку структура данных epoll динамически изменяет размер по мере добавления или удаления файловых дескрипторов.

Системный вызов epoll_create возвращает файловый дескриптор на новосозданную структуру данных ядра epoll. Вызывающий процесс может затем использовать этот файловый дескриптор, чтобы добавлять, удалять или изменять другие файловые дескрипторы, которые он хочет отслеживать для ввода-вывода, в экземпляре epoll.

![](/images/de41a256ff916904629abc9234b8eca4.png)

Есть ещё один системный вызов epoll_create1, который определён следующим образом:

```c
int epoll_create1(int flags);
```

Аргумент flags может быть равен 0 или EPOLL_CLOEXEC.

Если установлен 0, epoll_create1 ведёт себя так же, как epoll_create.

Когда установлен флаг EPOLL_CLOEXEC, любой дочерний процесс, порождённый текущим процессом через fork, закроет дескриптор epoll перед exec, так что дочерний процесс больше не будет иметь доступа к экземпляру epoll.

Важно отметить, что файловый дескриптор, связанный с экземпляром epoll, должен быть освобождён системным вызовом close(). Несколько процессов могут удерживать дескриптор одного и того же экземпляра epoll — например, fork без флага EPOLL_CLOEXEC продублирует дескриптор экземпляра epoll в дочерний процесс). Когда все эти процессы relinquish (освобождают) свои дескрипторы экземпляра epoll (либо вызовом close(), либо завершаясь), ядро уничтожает экземпляр epoll.

### 2) epoll_ctl

Процесс может добавлять файловые дескрипторы, которые он хочет отслеживать, в экземпляр epoll, вызывая epoll_ctl. Все файловые дескрипторы, зарегистрированные с экземпляром epoll, вместе называются epoll-набором (epoll set) или списком интереса (interest list).

![](/images/a9ccca4f22506b53680df2ea2c960583.png)

На диаграмме выше процесс 483 зарегистрировал файловые дескрипторы fd1, fd2, fd3, fd4 и fd5 с экземпляром epoll. Это список интереса или epoll-набор этого конкретного экземпляра epoll. Впоследствии, когда любой из зарегистрированных файловых дескрипторов становится готовым для ввода-вывода, считается, что они находятся в готовом списке (ready list).

Готовый список — это подмножество списка интереса.

![](/images/fce856747bee297377d498404f5e9e59.png)

Сигнатура системного вызова epoll_ctl выглядит следующим образом:

```c
#include <sys/epoll.h>
int epoll_ctl(int epfd, int op, int fd, struct epoll_event *event);
```

* epfd — это файловый дескриптор, возвращённый epoll_create, который идентифицирует экземпляр epoll в ядре.
* fd — это файловый дескриптор, который мы хотим добавить в epoll-список/список интереса.
* op — операция, которую нужно выполнить над файловым дескриптором fd. В общем случае поддерживаются три операции:

— Зарегистрировать fd в экземпляре epoll (EPOLL_CTL_ADD) и получать уведомления о событиях, происходящих на fd.

— Удалить/отменить регистрацию fd из экземпляра epoll. Это будет означать, что процесс больше не будет получать никаких уведомлений о событиях на этом файловом дескрипторе (EPOLL_CTL_DEL). Если файловый дескриптор был добавлен в несколько экземпляров epoll, его закрытие удалит его из всех списков интереса epoll, в которые он был добавлен.

— Изменить события, которые отслеживает fd (EPOLL_CTL_MOD).

* event — это указатель на структуру под названием epoll_event, которая хранит событие, которое мы действительно хотим отслеживать для fd.

Первое поле events структуры epoll_event — это битовая маска, указывающая, какие события отслеживаются для fd.

Так, если fd — это socket, мы можем захотеть отслеживать прибытие новых данных в буфер сокета (EPOLLIN). Мы можем также захотеть отслеживать fd для уведомлений, срабатывающих по фронту, что делается через OR-комбинацию EPOLLET с EPOLLIN. Мы можем также захотеть отслеживать fd для наступления зарегистрированного события, но только один раз, и прекратить отслеживание fd для последующих наступлений этого события. Это можно accomplish через OR-комбинацию других флагов (EPOLLET, EPOLLIN), которые мы хотим установить для дескриптора fd, с флагом доставки уведомления только один раз EPOLLONESHOT. Все возможные флаги можно найти в man-странице.

Второе поле структуры epoll_event — это поле типа union.

### 3) epoll_wait

Поток может получать уведомления о событиях, произошедших на epoll-наборе/списке интереса экземпляра epoll, вызывая системный вызов epoll_wait, который блокируется, пока любой из отслеживаемых дескрипторов не станет готовым для ввода-вывода.

Сигнатура epoll_wait выглядит следующим образом:

```c
#include <sys/epoll.h>
int epoll_wait(int epfd, struct epoll_event *evlist, int maxevents, int timeout);
```

* epfd — это файловый дескриптор, возвращённый epoll_create, который идентифицирует экземпляр epoll в ядре.
* evlist — это массив структур epoll_event. evlist выделяется вызывающим процессом, и когда epoll_wait возвращается, этот массив изменяется, чтобы указать информацию о подмножестве файловых дескрипторов из списка интереса, которые находятся в готовом состоянии (это называется готовым списком).
* maxevents — это длина массива evlist.
* timeout — этот аргумент ведёт себя так же, как для poll или select. Это значение указывает, как долго системный вызов epoll_wait будет блокироваться:

— когда timeout установлен в 0, epoll_wait не блокируется, а немедленно возвращается после проверки, какие файловые дескрипторы в списке интереса для epfd готовы;

— когда timeout установлен в -1, epoll_wait будет блокироваться «вечно». Когда epoll_wait блокируется, ядро может усыпить процесс, пока epoll_wait не вернётся. epoll_wait будет блокироваться, пока 1) один или более дескрипторов, указанных в списке интереса для epfd, не станут готовыми, или 2) вызов не будет прерван обработчиком сигнала;

— когда timeout установлен в неотрицательное и ненулевое значение, epoll_wait будет блокироваться, пока 1) один или более дескрипторов, указанных в списке интереса для epfd, не станут готовыми, или 2) вызов не будет прерван обработчиком сигнала, или 3) не истечёт количество времени, указанное в timeout миллисекунд.

Возвращаемые значения epoll_wait таковы:

— если произошла ошибка (EBADF, EINTR, EFAULT или EINVAL), код возврата равен -1;

— если вызов завершился по таймауту до того, как какой-либо файловый дескриптор из списка интереса стал готовым, код возврата равен 0;

— если один или более файловых дескрипторов из списка интереса стали готовыми, код возврата — положительное целое число, которое указывает общее количество готовых файловых дескрипторов в массиве evlist. Затем evlist исследуется, чтобы определить, какие события произошли на каких файловых дескрипторах.

## Подводные камни epoll

Чтобы полностью понять нюансы epoll, важно понимать, как файловые дескрипторы действительно работают. Это исследовалось в моём предыдущем посте, но стоит повторить ещё раз.

Процесс ссылается на потоки ввода-вывода с помощью дескрипторов. Каждый процесс поддерживает таблицу файловых дескрипторов, к которым он имеет доступ. Каждая запись в этой таблице имеет два поля:

— флаги, управляющие работой файлового дескриптора (единственный такой флаг — close-on-exec);

— указатель на нижележащую структуру данных ядра, которую мы вскоре исследуем.

Дескрипторы создаются либо явно системными вызовами вроде open, pipe, socket и так далее, либо наследуются от родительского процесса при fork. Дескрипторы также «дублируются» системным вызовом dup/dup2.

![](/images/fa97c5c38f6e647bafe082b29dd4956f.png)

Дескрипторы освобождаются, когда:

— процесс завершается;

— вызывается системный вызов close;

— когда процесс делает fork, все дескрипторы «дублируются» в дочернем процессе. Если какие-либо из дескрипторов помечены как close-on-exec, то после того как родитель сделал fork, но до того как дочерний процесс сделает exec, дескрипторы в дочернем процессе, помеченные как close-on-exec, закрываются и больше не будут доступны дочернему процессу. Родитель всё ещё может продолжать использовать дескриптор, но дочерний процесс не сможет использовать его после exec.

Предположим, в примере выше процесс A имеет дескриптор 3, помеченный флагом close-on-exec. Если процесс A порождает (fork) процесс B, то сразу после fork процессы A и B идентичны, и, как таковой, процесс B будет иметь «доступ» к файловым дескрипторам 0, 1, 2 и 3.

![](/images/6506e10e8e3d8e8f91a1657cf6f77dfc.png)

Но поскольку дескриптор 3 помечен как close-on-exec, перед тем как процесс B сделает exec, этот дескриптор будет помечен как «неактивный», и процесс B больше не сможет к нему обращаться.

![](/images/ea9a90bca3652892115e362b5c37ab10.png)

Чтобы по-настоящему понять, что это значит, важно понимать, что дескриптор на самом деле — это просто указатель процесса на нижележащую структуру данных ядра, называемую (что сбивает с толку) file description (описанием файла).

Ядро поддерживает таблицу всех открытых описаний файлов, называемую таблицей открытых файлов (open file table).

![](/images/116af5b8b2c87fb25811d371eaddc9d5.png)

Допустим, fd3 процесса A был создан в результате системного вызова dup или fcntl на дескрипторе fd0. И исходный дескриптор fd0, и «дублированный» дескриптор fd3 указывают на одно и то же описание файла в ядре.

Если процесс A затем порождает процесс B, а fd3 помечен флагом close-on-exec, то дочерний процесс B унаследует все дескрипторы родительского процесса A, но не сможет использовать fd3.

Важно отметить, что fd0 в дочернем процессе B также будет указывать на то же самое открытое описание файла в таблице открытых файлов ядра.

![](/images/0012aac86f9b52d7227ad381b9f669c9.png)

У нас есть три дескриптора — fd0 и fd3 в процессе A и fd0 в процессе B — которые все указывают на одно и то же нижележащее открытое описание файла ядра. Запомните это, потому что это имеет некоторые важные последствия для epoll. Все прочие файловые дескрипторы в обоих процессах A и B также указывают на записи в таблице открытых файлов, но опущены на диаграмме.

Примечание — описания файлов разделяются не только двумя процессами, когда один порождает другого. Если один процесс передаёт файловый дескриптор другому процессу через сокет домена Unix (Unix Domain Socket), то дескрипторы обоих процессов снова указывают на одно и то же нижележащее открытое описание файла ядра.

![](/images/32dca8f1dc80ac3d302ecefc6420cc7f.png)

Наконец, становится важным понять, что такое поле указателя на inode у описания файла. Но перед этим важно понять, что такое inode.

Inode — это структура данных файловой системы, которая содержит информацию об объекте файловой системы, таком как файл или директория. Эта информация включает:

— расположение блоков на диске, где хранятся данные файла или директории;

— атрибуты файла или директории;

— дополнительные метаданные о файле или директории, такие как время доступа, владелец, права доступа и так далее.

Каждый файл (и директория) в файловой системе имеет запись inode, которая является числом, ссылающимся на файл. Это число также называется номером inode. На многих файловых системах максимальное количество inode ограничено определённым значением, что означает, что общее количество файлов, которое может быть сохранено в системе, также ограничено.

На диске существует запись таблицы inode, которая поддерживает отображение номера inode в фактическую структуру данных inode на диске. Большинство файловых систем доступны через драйвер файловой системы ядра. Этот драйвер использует номер inode для доступа к информации, хранящейся в inode. Таким образом, чтобы узнать расположение файла или любые метаданные, относящиеся к файлу, драйверу файловой системы ядра необходимо обратиться к таблице inode.

![](/images/8be45f8d5bfc306dc8bac9730b228bf0.png)

Допустим, после того как процесс A породил процесс B, процесс A создал ещё два файловых дескриптора fd4 и fd5. Они не дублируются в процессе B.

Допустим, fd5 создан в результате вызова open процессом A файла abc.txt для чтения. Допустим, процесс B также вызывает open на abc.txt, но для записи, и файловый дескриптор, который вызов open возвращает процессу B, — это fd10.

Тогда fd5 процесса A и fd10 процесса B указывают на разные открытые описания файлов в таблице открытых файлов, но они указывают на одну и ту же запись таблицы inode (или, другими словами, на один и тот же файл).

![](/images/e5c643ad09a63b65086c2b7c68789cd5.png)

Это имеет два очень важных следствия:

— поскольку fd0 в процессах A и B ссылается на одно и то же открытое описание файла, они разделяют файловое смещение (file offset). Это значит, что если процесс A продвигает файловое смещение (вызывая read(), write() или lseek()), то смещение меняется и для процесса B. Это также применимо к fd3, принадлежащему процессу A, поскольку fd3 ссылается на то же открытое описание файла, что и fd0;

— это также применимо к изменениям, внесённым файловым дескриптором одного процесса в флаг состояния открытого файла (O_ASYNC, O_NONBLOCK, O_APPEND). Так, если процесс B переводит fd0 в неблокирующий режим, устанавливая флаг O_NONBLOCK через системный вызов fcntl, то дескрипторы fd0 и fd3, принадлежащие процессу A, также начнут демонстрировать неблокирующее поведение.

## Внутренности epoll

Допустим, процесс A имеет два открытых файловых дескриптора fd0 и fd1, у которых есть два открытых описания файлов в таблице открытых файлов. Допустим, оба эти описания файлов указывают на разные inode.

![](/images/21ff7c240d8ad8b25a47b65f8aef5940.png)

epoll_create создаёт новую запись inode (экземпляр epoll), а также открытое описание файла для него в ядре и возвращает вызывающему процессу файловый дескриптор (fd9) на это открытое описание файла.

![](/images/23127ea5d7ee7c215508abf406f00a94.png)

Когда мы используем epoll_ctl, чтобы добавить файловый дескриптор (скажем, fd0) в список интереса экземпляра epoll, мы на самом деле добавляем нижележащее описание файла fd0 в список интереса экземпляра epoll.

![](/images/b5293b7d9bec2e242500191e08c821b7.png)

Таким образом, экземпляр epoll на самом деле отслеживает нижележащее описание файла, а не файловый дескриптор уровня процесса. Это имеет некоторые интересные следствия:

— если процесс A порождает дочерний процесс B, то B наследует все дескрипторы A, включая fd9, дескриптор epoll. Однако дескрипторы fd0, fd1 и fd9 процесса B по-прежнему ссылаются на те же нижележащие структуры данных ядра. Дескриптор epoll (fd9) процесса B разделяет тот же список интереса с процессом A.

![](/images/50c51762ae7839ae50a771095c49b403.png)

Если после fork процесс A создаёт новый дескриптор fd8 (не дублированный в процессе B) и добавляет его в свой список интереса epoll через epoll_ctl, то не только процесс A получает уведомления о событиях на fd8 при вызове epoll_wait().

Если процесс B вызовет epoll_wait(), то процесс B также получит уведомление о fd8 (который принадлежит процессу A и не был дублирован при fork). Это также применимо, когда файловый дескриптор epoll дублируется с помощью вызова dup/dup2 или когда файловый дескриптор epoll передаётся другому процессу через сокет домена Unix.

![](/images/33a835252ac13789acb6556831b7fa0f.png)

Допустим, процесс B открывает файл, на который указывает fd8, новым вызовом open и получает новый файловый дескриптор (fd15) в результате. Теперь допустим, что процесс A закрывает fd8. Можно было бы предположить, что поскольку процесс A закрыл fd8, он больше не будет получать уведомления о событиях на fd8 при вызове epoll_wait. Однако это не так, поскольку список интереса отслеживает открытое описание файла. Поскольку fd15 указывает на то же описание, что и fd8 (так как это один и тот же нижележащий файл), процесс A получает уведомления о событиях на fd15. Можно с уверенностью сказать, что как только файловый дескриптор зарегистрирован процессом в экземпляре epoll, процесс будет продолжать получать уведомления о событиях на дескрипторе, даже если он закроет дескриптор, до тех пор, пока на нижележащее открытое описание файла всё ещё ссылается хотя бы один другой дескриптор (принадлежащий тому же или другому процессу).

## Почему epoll производительнее, чем select и poll

Как указывалось в предыдущем посте, стоимость select/poll — O(N), что означает, когда N очень велико (представьте веб-сервер, обслуживающий десятки тысяч в основном «спящих» клиентов), при каждом вызове select/poll, даже если произошло лишь небольшое количество событий, ядру всё равно нужно сканировать каждый дескриптор в списке.

Поскольку epoll отслеживает нижележащее описание файла, всякий раз, когда открытое описание файла становится готовым для ввода-вывода, ядро добавляет его в готовый список, не дожидаясь, пока процесс вызовет epoll_wait. Когда процесс действительно вызывает epoll_wait, ядру в этот момент не нужно выполнять какую-либо дополнительную работу для ответа на вызов — вместо этого оно возвращает всю информацию о готовом списке, который оно поддерживало всё это время.

Более того, каждый вызов select/poll требует передачи ядру информации о дескрипторах, которые мы хотим отслеживать. Это очевидно из сигнатур обоих вызовов. Ядро возвращает информацию обо всех переданных файловых дескрипторах, которую процессу снова нужно исследовать (сканируя все дескрипторы), чтобы выяснить, какие из них готовы для ввода-вывода.

```c
int poll(struct pollfd *fds, nfds_t nfds, int timeout);

int select(int nfds, fd_set *readfds, fd_set *writefds, fd_set *exceptfds,
           struct timeval *timeout);
```

С epoll, как только мы добавили файловые дескрипторы в список интереса экземпляра epoll с помощью вызова epoll_ctl, при последующих вызовах epoll_wait нам не нужно снова передавать файловые дескрипторы, информацию о готовности которых мы хотим узнать. Ядро опять же возвращает информацию только о тех дескрипторах, которые готовы для ввода-вывода, в отличие от модели select/poll, где ядро возвращает информацию о каждом переданном дескрипторе.

В результате стоимость epoll — O(количество произошедших событий), а не O(количество отслеживаемых дескрипторов), как было в случае с select/poll.

## Epoll с уведомлениями по фронту

По умолчанию epoll предоставляет уведомления по уровню (level-triggered). Каждый вызов epoll_wait возвращает только подмножество файловых дескрипторов, принадлежащих списку интереса, которые готовы.

Так, если у нас зарегистрированы четыре файловых дескриптора (fd1, fd2, fd3 и fd4), и только два (fd2 и fd3) готовы в момент вызова epoll_wait, то будет возвращена информация только об этих двух дескрипторах.

![](/images/73e85c38714d5e36395b9f41afc28887.png)

Также интересно отметить, что в случае по умолчанию с уведомлениями по уровню характер дескрипторов (блокирующие против неблокирующих) в списке интереса epoll не повлияет на результат вызова epoll_wait, поскольку epoll обновляет свой готовый список только когда нижележащее открытое описание файла становится готовым.

Иногда мы можем захотеть узнать статус любого дескриптора (скажем, fd1) в списке интереса, независимо от того, готов он или нет. epoll позволяет узнать, возможен ли ввод-вывод на любом конкретном файловом дескрипторе (даже если он не готов в момент вызова epoll_wait) с помощью поддержки уведомлений, срабатывающих по фронту (edge-triggered). Если мы хотим узнать, была ли какая-либо активность ввода-вывода на файловом дескрипторе с момента предыдущего вызова epoll_wait (или с момента открытия дескриптора, если процесс не делал предыдущего вызова epoll_wait), мы можем получать edge-triggered-уведомления, комбинируя через OR флаг EPOLLET при вызове epoll_ctl во время регистрации файлового дескриптора в экземпляре epoll.

Пожалуй, полезнее увидеть это в действии в коде из реального проекта, где файловый дескриптор регистрируется в экземпляре epoll с помощью epoll_ctl, где флаг EPOLLET комбинируется через OR с некоторыми другими флагами.

```lua
function Poller:register(fd, r, w)
	local ev = self.ev[0]
	ev.events = bit.bor(C.EPOLLET, C.EPOLLERR, C.EPOLLHUP)
	if r then
		ev.events = bit.bor(ev.events, C.EPOLLIN)
	end
	if w then
		ev.events = bit.bor(ev.events, C.EPOLLOUT)
	end
	ev.data.u64 = fd
	local rc = C.epoll_ctl(self.fd, C.EPOLL_CTL_ADD, fd, ev)
	if rc < 0 then errors.get(rc):abort() end
end
```

Возможно, иллюстративный пример поможет лучше понять, как работают edge-triggered-уведомления с epoll. Используем пример из предыдущего раздела, где процесс зарегистрировал четыре дескриптора в экземпляре epoll. Допустим, что fd3 — это сокет.

Допустим, что в момент t1 на сокет, на который ссылается fd3, прибывает входной поток байтов.

![](/images/ba253a89eb4452db929f96faa761b968.png)

В момент t0 на сокет прибывает ввод. Теперь допустим, что в момент t4 процесс вызывает epoll_wait().

Если в момент t4 файловые дескрипторы fd2 и fd3 готовы, то вызов epoll_wait сообщает о fd2 и fd3 как о готовых.

![](/images/cb8602ebc41ebf0e5479cd03587d29eb.png)

В момент t4 процесс вызывает epoll_wait. Допустим, что процесс снова вызывает epoll_wait в момент t6. Допустим, fd1 готов. Также допустим, что никакой ввод не прибыл на сокет, на который ссылается fd3, между моментами t4 и t6.

В случае level-triggered вызов epoll_wait вернёт процессу fd1, поскольку fd1 — единственный готовый дескриптор. Однако в случае edge-triggered этот вызов заблокируется, поскольку никаких новых данных не прибыло на сокет, на который ссылается fd3, между моментами t4 и t6.

![](/images/73e85c38714d5e36395b9f41afc28887.png)

В момент t6 процесс снова вызывает epoll_wait.
