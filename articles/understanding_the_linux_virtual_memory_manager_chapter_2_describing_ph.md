## 2.1 Узлы

Как мы упоминали, каждый узел памяти описывается `pg_data_t` — typedef для `struct pglist_data`. При выделении страницы Linux использует _политику локального выделения в узле (node-local allocation policy)_, выделяя память из узла, ближайшего к работающему CPU. Поскольку процессы склонны работать на одном и том же CPU, вероятно, будет использоваться память текущего узла. Структура объявлена в <`linux/mmzone.h`> следующим образом:

```c
129 typedef struct pglist_data {
130     zone_t node_zones[MAX_NR_ZONES];
131     zonelist_t node_zonelists[GFP_ZONEMASK+1];
132     int nr_zones;
133     struct page *node_mem_map;
134     unsigned long *valid_addr_bitmap;
135     struct bootmem_data *bdata;
136     unsigned long node_start_paddr;
137     unsigned long node_start_mapnr;
138     unsigned long node_size;
139     int node_id;
140     struct pglist_data *node_next;
141 } pg_data_t;
```

Кратко опишем каждое из этих полей:

* **node_zones** — зоны этого узла: `ZONE_HIGHMEM`, `ZONE_NORMAL`, `ZONE_DMA`;
* **node_zonelists** — порядок зон, из которых предпочитаются выделения. `build_zonelists()` в `mm/page_alloc.c` устанавливает этот порядок при вызове из `free_area_init_core()`. Неудавшееся выделение в `ZONE_HIGHMEM` может откатиться к `ZONE_NORMAL` или далее к `ZONE_DMA`;
* **nr_zones** — число зон в этом узле, от 1 до 3. Не во всех узлах будет три. Например, у CPU-банка может не быть `ZONE_DMA`;
* **node_mem_map** — первая страница массива `struct page`, представляющего каждый физический фрейм в узле. Она будет размещена где-то внутри глобального массива `mem_map`;
* **valid_addr_bitmap** — битовая карта, описывающая «дыры» в узле памяти, для которых памяти не существует. В действительности используется только архитектурами Sparc и Sparc64 и игнорируется всеми остальными;
* **bdata** — интересен только для загрузочного распределителя памяти (boot memory allocator), обсуждаемого в главе [5](understand008.html#chap: Boot Memory Allocator);
* **node_start_paddr** — начальный физический адрес узла. unsigned long работает неоптимально, так как ломается на ia32 с _Physical Address Extension (PAE)_, например. PAE подробнее рассматривается в разделе 2.5. Более подходящее решение — хранить это как _номер страничного фрейма (Page Frame Number, PFN)_. PFN — это просто индекс в физической памяти, отсчитываемый в единицах размером со страницу. PFN для физического адреса тривиально определяется как (`page_phys_addr` >> `PAGE_SHIFT`);
* **node_start_mapnr** — смещение страницы внутри глобального `mem_map`. Вычисляется в `free_area_init_core()` подсчётом числа страниц между `mem_map` и локальным `mem_map` для этого узла, называемым `lmem_map`;
* **node_size** — общее число страниц в этой зоне;
* **node_id** — _Node ID (NID)_ узла, начинается с 0;
* **node_next** — указатель на следующий узел в списке, завершённом NULL.

Все узлы в системе поддерживаются в списке под названием `pgdat_list`. Узлы помещаются в этот список по мере инициализации функцией `init_bootmem_core()`, описанной далее в разделе [5.2.1](understand008.html#sec: Initialising bootmem_data). Вплоть до поздних ядер 2.4 (> `2.4.18`) блоки кода, обходившие список, выглядели примерно так:

```c
    pg_data_t * pgdat;
    pgdat = pgdat_list;
    do {
          /* do something with pgdata_t */
          ...
    } while ((pgdat = pgdat->node_next));
```

В более новых ядрах предоставлен макрос `for_each_pgdat()`, тривиально определяемый как for-цикл, для улучшения читабельности кода.

## 2.2 Зоны

Зоны описываются `struct zone_struct` и обычно называются по своему typedef `zone_t`. Она хранит информацию вроде статистики использования страниц, сведений о свободных областях и блокировок. Объявлена в <`linux/mmzone.h`> следующим образом:

```c
37 typedef struct zone_struct {
41     spinlock_t        lock;
42     unsigned long     free_pages;
43     unsigned long     pages_min, pages_low, pages_high;
44     int               need_balance;
45
49     free_area_t       free_area[MAX_ORDER];
50
76     wait_queue_head_t * wait_table;
77     unsigned long     wait_table_size;
78     unsigned long     wait_table_shift;
79
83     struct pglist_data *zone_pgdat;
84     struct page        *zone_mem_map;
85     unsigned long      zone_start_paddr;
86     unsigned long      zone_start_mapnr;
87
91     char               *name;
92     unsigned long      size;
93 } zone_t;
```

Кратко поясним каждое поле структуры.

* **lock** — spinlock, защищающий зону от конкурентного доступа;
* **free_pages** — общее число свободных страниц в зоне;
* **pages_min, pages_low, pages_high** — уровни зоны (zone watermarks), описываемые в следующем разделе;
* **need_balance** — флаг, говорящий демону выгрузки **kswapd** сбалансировать зону. Говорят, что зоне нужен баланс, когда число доступных страниц достигает одного из _уровней зоны (zone watermarks)_. Уровни обсуждаются в следующем разделе;
* **free_area** — битовые карты свободных областей, используемые распределителем buddy;
* **wait_table** — хеш-таблица очередей ожидания процессов, ждущих освобождения страницы. Важна для `wait_on_page()` и `unlock_page()`. Хотя процессы могли бы ждать все в одной очереди, это привело бы к тому, что все ждущие процессы бросились бы соревноваться за всё ещё заблокированные страницы при пробуждении. Большая группа процессов, конкурирующих за общий ресурс, иногда называется «стадо слонов» (thundering herd). Таблицы ожидания подробнее обсуждаются в разделе 2.2.3;
* **wait_table_size** — число очередей в хеш-таблице, являющееся степенью 2;
* **wait_table_shift** — определяется как число бит в long минус двоичный логарифм размера таблицы выше;
* **zone_pgdat** — указывает на родительский `pg_data_t`;
* **zone_mem_map** — первая страница в глобальном `mem_map`, на которую ссылается эта зона;
* **zone_start_paddr** — тот же принцип, что у `node_start_paddr`;
* **zone_start_mapnr** — тот же принцип, что у `node_start_mapnr`;
* **name** — строковое имя зоны: "DMA", "Normal" или "HighMem";
* **size** — размер зоны в страницах.

### 2.2.1 Уровни зоны (Zone Watermarks)

Когда доступной памяти в системе мало, демон выгрузки **kswapd** пробуждается, чтобы начать освобождать страницы (см. главу [10](understand013.html#chap: Page Frame Reclamation)). Если давление высоко, процесс будет освобождать память синхронно — это иногда называют путём _direct-reclaim_. Параметры, влияющие на поведение выгрузки, схожи с параметрами FreeBSD [[McK96](understand031.html#mckusick96)] и Solaris [[MM01](understand031.html#mauro01)].

У каждой зоны три уровня: `pages_low`, `pages_min` и `pages_high`, помогающие отслеживать, под каким давлением находится зона. Их соотношение показано на рисунке 2.2. Число страниц для `pages_min` вычисляется в функции `free_area_init_core()` при инициализации памяти и основано на отношении к размеру зоны в страницах. Изначально оно вычисляется как _ZoneSizeInPages_ / 128. Минимальное значение — 20 страниц (80K на x86), максимально возможное — 255 страниц (1 МиБ на x86).

> Рисунок 2.2: Уровни зоны (Zone Watermarks)

* **pages_low** — когда достигается число свободных страниц `pages_low`, распределитель buddy пробуждает **kswapd**, чтобы начать освобождать страницы. Это эквивалентно достижению `lotsfree` в Solaris и `freemin` в FreeBSD. Значение по умолчанию — удвоенное `pages_min`;
* **pages_min** — когда достигается `pages_min`, распределитель выполняет работу **kswapd** синхронно; это иногда называют путём _direct-reclaim_. В Solaris реального эквивалента нет, но ближе всего `desfree` или `minfree`, определяющие, как часто пробуждается сканер выгрузки;
* **pages_high** — после пробуждения **kswapd** для освобождения страниц он не сочтёт зону «сбалансированной», пока не свободно `pages_high` страниц. Когда уровень достигнут, **kswapd** снова засыпает. В Solaris это называется `lotsfree`, в BSD — `free_target`. По умолчанию `pages_high` втрое больше `pages_min`.

Как бы ни назывались параметры выгрузки в каждой ОС, смысл один: они помогают определить, насколько усердно демон выгрузки или процессы работают над освобождением страниц.

### 2.2.2 Вычисление размера зон

> Рисунок 2.3: Граф вызовов: `setup_memory()`

PFN — это смещение, отсчитываемое в страницах, внутри карты физической памяти. Первый PFN, пригодный для использования системой, `min_low_pfn`, расположен в начале первой страницы после `_end` — конца загруженного образа ядра. Значение хранится как переменная файловой области в `mm/bootmem.c` для использования загрузочным распределителем памяти.

То, как вычисляется последний страничный фрейм в системе, `max_pfn`, сильно зависит от архитектуры. В случае x86 функция `find_max_pfn()` просматривает всю карту _e820_ в поисках наивысшего фрейма. Значение также хранится как переменная файловой области в `mm/bootmem.c`. e820 — таблица, предоставляемая BIOS и описывающая, какая физическая память доступна, зарезервирована или не существует.

Значение `max_low_pfn` на x86 вычисляется функцией `find_max_low_pfn()` и отмечает конец `ZONE_NORMAL`. Это физическая память, напрямую доступная ядру; она связана с разделением ядра/пользовательского пространства в линейном адресном пространстве, отмеченном `PAGE_OFFSET`. Значение, как и остальные, хранится в `mm/bootmem.c`. Обратите внимание: на машинах с малой памятью `max_pfn` будет тем же, что и `max_low_pfn`.

Имея три переменные `min_low_pfn`, `max_low_pfn` и `max_pfn`, несложно вычислить начало и конец верхней памяти (high memory) и поместить их как переменные файловой области в `arch/i386/mm/init.c` под именами `highstart_pfn` и `highend_pfn`. Эти значения позже используются для инициализации страниц верхней памяти для физического распределителя страниц, как мы увидим значительно позже, в разделе [5.5](understand008.html#sec: Retiring the Boot Memory Allocator).

### 2.2.3 Таблица очередей ожидания зоны

Когда над страницей выполняется ввод-вывод — например, при подкачке страниц в память или из памяти — она блокируется, чтобы предотвратить доступ к ней с неконсистентными данными. Процессы, желающие её использовать, должны встать в очередь ожидания, вызвав `wait_on_page()`. По завершении ввода-вывода страница разблокируется через `UnlockPage()`, и все процессы, ждущие в очереди, пробуждаются. У каждой страницы могла бы быть своя очередь ожидания, но иметь столько отдельных очередей было бы очень дорого по памяти, поэтому очередь ожидания хранится в `zone_t`.

Можно было бы иметь в зоне всего одну очередь ожидания, но это означало бы, что все процессы, ждущие любую страницу в зоне, пробуждаются, когда разблокируется одна из них. Это вызвало бы серьёзную проблему _thundering herd_. Вместо этого в `zone_t`->`wait_table` хранится хеш-таблица очередей ожидания. При коллизии в хеше процессы всё же могут пробуждаться без нужды, но ожидается, что коллизии не будут частыми.

> Рисунок 2.4: Ожидание на заблокированной странице

Таблица выделяется во время `free_area_init_core()`. Её размер вычисляется функцией `wait_table_size()` и хранится в `zone_t`->`wait_table_size`. Максимальный размер — 4096 очередей ожидания. Для меньших таблиц размером является минимальная степень 2, необходимая для хранения `NoPages / PAGES_PER_WAITQUEUE` очередей, где `NoPages` — число страниц в зоне, а `PAGE_PER_WAITQUEUE` определён как 256. Иначе говоря, размер таблицы вычисляется как целая часть следующего уравнения:

```text
wait_table_size = log2((NoPages * 2) / PAGES_PER_WAITQUEUE - 1)
```

Поле `zone_t`->`wait_table_shift` вычисляется как число бит, на которое нужно сдвинуть адрес страницы вправо, чтобы получить индекс в таблице. Функция `page_waitqueue()` отвечает за возврат очереди ожидания, используемой для страницы в зоне. Она использует простой мультипликативный алгоритм хеширования на основе виртуального адреса хешируемого `struct page`.

Работает это так: адрес просто умножается на `GOLDEN_RATIO_PRIME`, а результат сдвигается на `zone_t`->`wait_table_shift` бит вправо для индексации в хеш-таблице. `GOLDEN_RATIO_PRIME` [[Lev00](understand031.html#lever00)] — наибольшее простое число, ближайшее к _золотому сечению_ [[Knu68](understand031.html#knuth68)] наибольшего целого, представимого архитектурой.

## 2.3 Инициализация зон

Зоны инициализируются после того, как таблицы страниц ядра полностью настроены функцией `paging_init()`. Инициализация таблиц страниц рассматривается в разделе [3.6](understand006.html#sec: Kernel Page Tables). Предсказуемо, каждая архитектура выполняет эту задачу по-своему, но цель всегда одна: определить, какие параметры передать либо в `free_area_init()` для архитектур UMA, либо в `free_area_init_node()` для NUMA. Единственный параметр, необходимый для UMA, — `zones_size`. Полный список параметров:

* **nid** — Node ID, логический идентификатор узла, зоны которого инициализируются;
* **pgdat** — `pg_data_t` узла, который инициализируется. В UMA это будет просто `contig_page_data`;
* **pmap** — устанавливается позже функцией `free_area_init_core()` и указывает на начало локального массива `lmem_map`, выделенного для узла. В NUMA игнорируется, так как NUMA рассматривает `mem_map` как виртуальный массив, начинающийся с `PAGE_OFFSET`. В UMA этот указатель — глобальная переменная `mem_map`, и именно так `mem_map` инициализируется в UMA.
* **zones_sizes** — массив, содержащий размер каждой зоны в страницах;
* **zone_start_paddr** — начальный физический адрес первой зоны;
* **zone_holes** — массив, содержащий общий размер дыр памяти в зонах.

Основная функция `free_area_init_core()` отвечает за заполнение каждого `zone_t` релевантной информацией и выделение массива `mem_map` для узла. Заметьте: информация о том, какие страницы зон свободны, на этом этапе не определяется. Она не известна до момента вывода из эксплуатации загрузочного распределителя памяти, что обсуждается значительно позже, в главе [5](understand008.html#chap: Boot Memory Allocator).

### 2.3.1 Инициализация `mem_map`

Область `mem_map` создаётся при старте системы одним из двух способов. На системах NUMA глобальный `mem_map` рассматривается как виртуальный массив, начинающийся с `PAGE_OFFSET`. `free_area_init_node()` вызывается для каждого активного узла в системе и выделяет часть этого массива для инициализируемого узла. На системах UMA `free_area_init()` использует `contig_page_data` как узел, а глобальный `mem_map` — как «локальный» `mem_map` для этого узла. Граф вызовов обеих функций показан на рисунке 2.5.

> Рисунок 2.5: Граф вызовов: `free_area_init()`

Основная функция `free_area_init_core()` выделяет локальный `lmem_map` для инициализируемого узла. Память под массив выделяется из загрузочного распределителя памяти функцией `alloc_bootmem_node()` (см. главу [5](understand008.html#chap: Boot Memory Allocator)). В архитектурах UMA эта вновь выделенная память становится глобальным `mem_map`, но для NUMA всё немного иначе.

Архитектуры NUMA выделяют память для `lmem_map` внутри собственного узла памяти. Глобальный `mem_map` никогда явно не выделяется — вместо этого он устанавливается в `PAGE_OFFSET` и рассматривается как виртуальный массив. Адрес локальной карты хранится в `pg_data_t`->`node_mem_map`, существующем где-то внутри виртуального `mem_map`. Для каждой зоны, существующей в узле, адрес внутри виртуального `mem_map` для зоны хранится в `zone_t`->`zone_mem_map`. Весь остальной код затем обращается с `mem_map` как с реальным массивом, поскольку узлы будут использовать только валидные области внутри него.

## 2.4 Страницы

С каждым физическим страничным фреймом в системе связан `struct page`, используемый для отслеживания его состояния. В ядре 2.2 [[BC00](understand031.html#bovet00)] эта структура напоминала свой эквивалент в System V [[GC94](understand031.html#goodheart94)], но, как и в других вариантах UNIX, структура значительно изменилась. Она объявлена в <`linux/mm.h`> следующим образом:

```c
152 typedef struct page {
153     struct list_head list;
154     struct address_space *mapping;
155     unsigned long index;
156     struct page *next_hash;
158     atomic_t count;
159     unsigned long flags;
161     struct list_head lru;
163     struct page **pprev_hash;
164     struct buffer_head * buffers;
175
176 #if defined(CONFIG_HIGHMEM) || defined(WANT_PAGE_VIRTUAL)
177     void *virtual;
179 #endif /* CONFIG_HIGMEM || WANT_PAGE_VIRTUAL */
180 } mem_map_t;
```

Краткое описание каждого поля:

* **list** — страницы могут принадлежать многим спискам, и это поле используется как голова списка. Например, страницы в отображении (mapping) находятся в одном из трёх кольцевых связных списков, поддерживаемых `address_space`: `clean_pages`, `dirty_pages` и `locked_pages`. В распределителе slab это поле используется для хранения указателей на slab и кэш, к которым относится страница. Оно также используется для связывания блоков свободных страниц;
* **mapping** — когда файлы или устройства отображаются в память, их inode имеет связанный `address_space`. Это поле указывает на это адресное пространство, если страница относится к файлу. Если страница анонимная и `mapping` установлен, `address_space` — это `swapper_space`, управляющий адресным пространством подкачки;
* **index** — у поля два применения, и смысл зависит от состояния страницы. Если страница — часть отображения файла, это смещение внутри файла. Если страница — часть кэша подкачки, это смещение внутри `address_space` для адресного пространства подкачки (`swapper_space`). Во-вторых, когда блок страниц освобождается для конкретного процесса, порядок (степень двойки числа освобождаемых страниц) освобождаемого блока сохраняется в `index`. Это устанавливается в функции `__free_pages_ok()`;
* **next_hash** — страницы, являющиеся частью отображения файла, хешируются по inode и смещению. Это поле связывает вместе страницы из одного хеш-бакета;
* **count** — счётчик ссылок на страницу. Если падает до 0, страница может быть освобождена. Больше — она используется одним или несколькими процессами или используется ядром, например при ожидании ввода-вывода;
* **flags** — флаги, описывающие состояние страницы. Все они объявлены в <`linux/mm.h`> и перечислены в таблице 2.1. Есть ряд макросов для тестирования, очистки и установки бит — все перечислены в таблице 2.2. Единственный по-настоящему интересный — `SetPageUptodate()`, который вызывает зависящую от архитектуры функцию `arch_set_page_uptodate()`, если она определена, перед установкой бита;
* **lru** — для политики замещения страниц, которые могут быть выгружены, существуют либо в `active_list`, либо в `inactive_list`, объявленных в `page_alloc.c`. Это голова этих LRU-списков. Эти два списка подробно обсуждаются в главе [10](understand013.html#chap: Page Frame Reclamation);
* **pprev_hash** — дополнение к `next_hash`, чтобы хеш мог работать как двусвязный список;
* **buffers** — если со страницей связаны буферы блочного устройства, это поле используется для отслеживания `buffer_head`. Анонимная страница, отображённая процессом, тоже может иметь связанный `buffer_head`, если она подкреплена файлом подкачки. Это необходимо, так как страницу нужно синхронизировать с хранилищем блоками размера, определяемого нижележащей файловой системой;
* **virtual** — обычно ядро напрямую отображает только страницы из `ZONE_NORMAL`. Для обращения к страницам в `ZONE_HIGHMEM` используется `kmap()`, отображающая страницу для ядра; это подробнее описано в главе [9](understand012.html#chap: High Memory Management). Отобразить можно только фиксированное число страниц. Когда страница отображена, это её виртуальный адрес.

Тип `mem_map_t` — typedef для `struct page`, чтобы на него было легко ссылаться внутри массива `mem_map`.

### 2.4.1 Сопоставление страниц с зонами

Вплоть до совсем недавнего ядра `2.4.18` `struct page` хранил ссылку на свою зону в `page`->`zone`, что позже посчитали расточительным: даже такой маленький указатель потребляет много памяти, когда существуют тысячи `struct page`. В более новых ядрах поле `zone` удалено, и вместо него верхние `ZONE_SHIFT` (на x86 — 8) бит `page`->`flags` используются для определения зоны, к которой относится страница. Сначала настраивается `zone_table` зон. Она объявлена в `mm/page_alloc.c` так:

```c
33 zone_t *zone_table[MAX_NR_ZONES*MAX_NR_NODES];
34 EXPORT_SYMBOL(zone_table);
```

`MAX_NR_ZONES` — максимальное число зон, которое может быть в узле, т.е. 3. `MAX_NR_NODES` — максимальное число узлов, которое может существовать. Функция `EXPORT_SYMBOL()` делает `zone_table` доступной загружаемым модулям. С этой таблицей обращаются как с многомерным массивом. Во время `free_area_init_core()` все страницы узла инициализируются. Сначала устанавливается значение таблицы:

```c
733           zone_table[nid * MAX_NR_ZONES + j] = zone;
```

где nid — ID узла, j — индекс зоны, а `zone` — структура `zone_t`. Для каждой страницы вызывается функция `set_page_zone()`:

```c
788           set_page_zone(page, nid * MAX_NR_ZONES + j);
```

Параметр `page` — страница, для которой устанавливается зона. Так что, очевидно, индекс в `zone_table` хранится в странице.

## 2.5 Верхняя память (High Memory)

Поскольку адресное пространство, пригодное для использования ядром (`ZONE_NORMAL`), ограничено по размеру, ядро поддерживает концепцию верхней памяти (High Memory). На 32-битных системах x86 существуют два порога верхней памяти: один на 4 ГиБ и второй на 64 ГиБ. Порог 4 ГиБ связан с объёмом памяти, адресуемым 32-битным физическим адресом. Для доступа к памяти в диапазоне от 1 ГиБ до 4 ГиБ ядро временно отображает страницы из верхней памяти в `ZONE_NORMAL` с помощью `kmap()`. Это подробнее обсуждается в главе [9](understand012.html#chap: High Memory Management).

Второй порог, 64 ГиБ, связан с _Physical Address Extension (PAE)_ — изобретением Intel, позволяющим использовать больше ОЗУ на 32-битных системах. Он делает доступными 4 дополнительных бита для адресации памяти, позволяя адресовать до 2^36 байт (64 ГиБ) памяти.

PAE позволяет процессору в теории адресовать до 64 ГиБ, но на практике процессы в Linux всё равно не могут получить доступ к такому объёму ОЗУ, так как виртуальное адресное пространство всё ещё лишь 4 ГиБ. Это привело к разочарованию пользователей, пытавшихся выделить (`malloc()`) всю свою память одним процессом.

Во-вторых, PAE не позволяет самому ядру располагать таким объёмом памяти. `struct page`, используемый для описания каждого фрейма страницы, по-прежнему требует 44 байта и расходует виртуальное адресное пространство ядра в `ZONE_NORMAL`. Это значит, что для описания 1 ГиБ памяти требуется примерно 11 МиБ памяти ядра. Таким образом, при 16 ГиБ потребляется 176 МиБ памяти, что создаёт значительное давление на `ZONE_NORMAL`. Не так страшно, пока не учесть другие структуры, использующие `ZONE_NORMAL`. Даже очень маленькие структуры, такие как _записи таблицы страниц (Page Table Entries, PTEs)_, в худшем случае требуют около 16 МиБ. Это делает 16 ГиБ примерно практическим пределом доступной физической памяти для Linux на x86. Если нужно больше памяти, совет прост и прямолинеен: купите 64-битную машину.

## 2.6 Что нового в 2.6

##### Узлы

На первый взгляд, изменений в описании памяти немного, но кажущиеся мелкими изменения имеют широкий охват. У дескриптора узла `pg_data_t` есть несколько новых полей:

* **node_start_pfn** — заменяет поле `node_start_paddr`. Единственное отличие: новое поле — PFN вместо физического адреса. Изменено потому, что архитектуры PAE адресуют больше памяти, чем влезает в 32 бита, и узлы, начинающиеся за 4 ГиБ, были бы недостижимы со старым полем;
* **kswapd_wait** — новая очередь ожидания для **kswapd**. В 2.4 была глобальная очередь ожидания для демона подкачки. В 2.6 есть один **kswapdN** на каждый узел, где `N` — идентификатор узла, и каждый **kswapd** имеет собственную очередь ожидания в этом поле.

Поле `node_size` удалено и заменено двумя полями. Изменение внесено, чтобы отразить тот факт, что в узлах могут быть «дыры», где за адресом не стоит физическая память.

* **node_present_pages** — общее число физических страниц, реально присутствующих в узле.
* **node_spanned_pages** — общая область, адресуемая узлом, включая любые существующие дыры.

##### Зоны

Даже на первый взгляд зоны выглядят совсем иначе. Они больше не называются `zone_t` — теперь это просто `struct zone`. Второе крупное отличие — LRU-списки. Как мы увидим в главе [10](understand013.html#chap: Page Frame Reclamation), ядро 2.4 имеет глобальный список страниц, определяющий порядок освобождения или выгрузки страниц. Теперь эти списки хранятся в `struct zone`. Релевантные поля:

* **lru_lock** — spinlock для LRU-списков этой зоны. В 2.4 это глобальная блокировка `pagemap_lru_lock`;
* **active_list** — активный список для этой зоны. Тот же список, что описан в главе [10](understand013.html#chap: Page Frame Reclamation), только теперь он на зону, а не глобальный;
* **inactive_list** — неактивный список для этой зоны. В 2.4 он глобальный;
* **refill_counter** — число страниц, удаляемых из `active_list` за один проход. Интересен только при замещении страниц;
* **nr_active** — число страниц в `active_list`;
* **nr_inactive** — число страниц в `inactive_list`;
* **all_unreclaimable** — устанавливается в 1, если демон выгрузки дважды просканировал все страницы зоны и всё равно не смог освободить достаточно;
* **pages_scanned** — число просканированных страниц с момента последнего массового освобождения. В 2.6 списки страниц освобождаются разом, а не по одной, как в 2.4;
* **pressure** — измеряет интенсивность сканирования этой зоны. Это затухающее среднее, влияющее на то, насколько усердно сканер страниц будет работать над освобождением страниц.

Ещё три поля новые, но связаны они с размерами зоны:

* **zone_start_pfn** — начальный PFN зоны. Заменяет поля `zone_start_paddr` и `zone_start_mapnr` из 2.4;
* **spanned_pages** — число страниц, которые охватывает зона, включая дыры памяти, существующие на некоторых архитектурах;
* **present_pages** — число реальных страниц, существующих в зоне. Для многих архитектур это то же значение, что и `spanned_pages`.

Следующее добавление — `struct per_cpu_pageset`, используемый для поддержания списков страниц на каждый CPU для снижения конкуренции за spinlock. Поле `zone`->`pageset` — массив `struct per_cpu_pageset` размера `NR_CPU`, где `NR_CPU` — скомпилированный верхний предел числа CPU в системе. Per-cpu структура обсуждается подробнее в конце раздела.

Последнее добавление в `struct zone` — заполнение нулями (padding) в структуре. Разработка VM 2.6 признала, что некоторые spinlock'и очень сильно конкурируемы и часто захватываются. Поскольку известно, что некоторые блокировки почти всегда захватываются парами, следует позаботиться, чтобы они использовали разные строки кэша — распространённый приём кэш-программирования [[Sea00](understand031.html#sears00)]. Эти заполнения в `struct zone` помечены макросом `ZONE_PADDING()` и используются, чтобы поля `zone`->`lock`, `zone`->`lru_lock` и `zone`->`pageset` использовали разные строки кэша.

##### Страницы

Первое заметное изменение — порядок полей изменён так, чтобы связанные элементы с большой вероятностью попадали в одну строку кэша. Поля по сути те же, кроме двух добавлений. Первое — новый union для создания цепочки PTE. Цепочки PTE связаны с управлением таблицами страниц и будут обсуждены в конце главы [3](understand006.html#chap: Page Table Management). Второе добавление — поле `page`->`private`, содержащее приватную информацию, специфичную для отображения. Например, поле используется для хранения указателя на `buffer_head`, если страница — буферная. Это значит, что поле `page`->`buffers` тоже удалено. Последнее важное изменение: `page`->`virtual` больше не нужен для поддержки верхней памяти и будет существовать, только если архитектура явно его запросит. О том, как поддерживаются страницы верхней памяти, подробнее в главе [9](understand012.html#chap: High Memory Management).

##### Списки страниц на CPU

В 2.4 только одна подсистема активно пытается поддерживать per-cpu списки для любых объектов — распределитель slab, обсуждаемый в главе [8](understand011.html#chap: Slab Allocator). В 2.6 концепция распространилась гораздо шире, и появилась формализованная концепция горячих и холодных страниц.

`struct per_cpu_pageset`, объявленный в <`linux/mmzone.h`>, имеет одно поле — массив из двух элементов типа `per_cpu_pages`. Нулевой элемент массива — для горячих страниц, первый — для холодных, где «горячесть/холодность» определяет, насколько «активна» страница в кэше в данный момент. Когда достоверно известно, что страницы скоро не понадобятся — как при опережающем чтении (readahead) I/O — они будут выделяться как холодные.

`struct per_cpu_pages` поддерживает счётчик числа страниц, находящихся в списке в данный момент, верхний и нижний уровни, определяющие, когда набор следует пополнить или страницы освободить пачкой, переменную, определяющую, сколько страниц выделять одним блоком, и, наконец, саму голову списка страниц.

В дополнение к per-cpu спискам страниц есть и per-cpu механизм учёта страниц. Есть `struct page_state`, хранящий ряд учётных переменных — например, поле `pgalloc`, отслеживающее число страниц, выделенных этому CPU, и `pswpin`, отслеживающее число чтений из swap. Структура обстоятельно прокомментирована в <`linux/page-flags.h`>. Для обновления полей `page_state` работающего CPU предоставлена единственная функция `mod_page_state()` и три вспомогательных макроса: `inc_page_state()`, `dec_page_state()` и `sub_page_state()`.
