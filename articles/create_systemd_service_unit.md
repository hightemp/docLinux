# Как создать сервисный модуль systemd в Linux

Источник: [How to create systemd service unit in Linux](https://linuxconfig.org/how-to-create-systemd-service-unit-in-linux)

Несмотря на многочисленные споры вокруг systemd, доходившие даже до создания ответвлений дистрибутивов с целью отказаться от этой системы (например, Devuan — ответвление Debian, в котором systemd по умолчанию заменена на sysvinit), в итоге она стала фактическим стандартом системы инициализации в мире Linux.

В этой статье мы разберём структуру службы systemd и научимся создавать собственные сервисные модули.

**Из статьи вы узнаете:**

- что такое сервисный модуль;
- из каких разделов он состоит;
- какие параметры чаще всего используются в каждом разделе;
- какие типы служб можно определить.

## Требования к программному обеспечению и используемые обозначения

| Категория | Требования, обозначения или версия ПО |
| --- | --- |
| Система | Дистрибутив GNU/Linux, использующий systemd как систему инициализации |

| `$` | Указанные [команды Linux](https://linuxconfig.org/linux-commands) необходимо выполнять от имени обычного непривилегированного пользователя |

## Система инициализации systemd

Все основные дистрибутивы, включая RHEL, CentOS, Fedora, Ubuntu, Debian и Arch Linux, приняли systemd в качестве системы инициализации. На самом деле systemd — нечто большее, чем просто система инициализации. Это одна из причин, по которой некоторые пользователи категорически не согласны с её архитектурой: она противоречит устоявшемуся принципу Unix «делай что-то одно и делай это хорошо».

В то время как другие системы инициализации управляют службами с помощью простых сценариев командной оболочки, systemd использует собственные файлы `.service` — модули с таким расширением. Далее мы рассмотрим их структуру, создание и установку.

## Структура сервисного модуля

Что такое сервисный модуль? Файл с расширением `.service` содержит сведения о процессе, которым управляет systemd. Он состоит из трёх основных разделов:

- `[Unit]` — общие сведения, не привязанные к конкретному типу модуля, например описание службы;
- `[Service]` — сведения о модуле конкретного типа, в данном случае о службе;
- `[Install]` — сведения об установке модуля.

Рассмотрим каждый из них подробнее.

## Раздел `[Unit]`

Раздел `[Unit]` файла `.service` содержит описание самого модуля, сведения о его поведении и зависимостях. Например, для правильной работы одной службе может потребоваться другая. Ниже перечислены наиболее важные параметры этого раздела.

### Параметр `Description`

Параметр `Description` позволяет задать описание модуля. Оно отображается, например, в обзоре состояния systemd, который возвращает команда `systemctl`. Вот как служба `httpd` описана в Fedora:

```ini
[Unit]
Description=The Apache HTTP Server
```

### Параметр `After`

Параметр `After` указывает, что наш модуль следует запускать после модулей, перечисленных через пробел. Например, в файле службы веб-сервера Apache есть такая строка:

```ini
After=network.target remote-fs.target nss-lookup.target httpd-init.service
```

Она предписывает systemd запускать сервисный модуль `httpd.service` только после модулей `network.target`, `remote-fs.target`, `nss-lookup.target` и `httpd-init.service`.

### Строгие зависимости с помощью `Requires`

Как уже упоминалось, для правильной работы один модуль — в нашем случае служба — может зависеть от других модулей, не обязательно сервисных. Такие зависимости объявляются с помощью параметра `Requires`.

Если какой-либо модуль, от которого зависит служба, не запустится, активация самой службы будет остановлена. Поэтому такие зависимости называют строгими. В следующей строке из файла службы `avahi-daemon` объявлена её зависимость от модуля `avahi-daemon.socket`:

```ini
Requires=avahi-daemon.socket
```

### Слабые зависимости с помощью `Wants`

Для объявления слабых зависимостей службы используется параметр `Wants`.

В чём разница? Если не удаётся запустить строгую зависимость, зависимая служба также не запускается. Ошибка слабой зависимости, напротив, не влияет на зависимый модуль. В следующем примере модуль `docker.service` имеет слабую зависимость от `docker-storage-setup.service`:

```ini
[Unit]
Wants=docker-storage-setup.service
```

## Раздел `[Service]`

В разделе `[Service]` сервисного модуля можно указать команду, выполняемую при запуске службы, тип самой службы и другие параметры. Рассмотрим некоторые из них.

### Запуск, остановка и перезагрузка службы

Службу можно запустить, остановить, перезапустить или перезагрузить её конфигурацию. Команды для каждого из этих действий задаются соответствующими параметрами раздела `[Service]`.

Команда, выполняемая при запуске службы, задаётся параметром `ExecStart`. В качестве его аргумента также можно передать путь к сценарию. При необходимости с помощью параметров `ExecStartPre` и `ExecStartPost` можно объявить команды, которые должны выполняться соответственно до и после запуска службы. Например, для запуска NetworkManager используется следующая команда:

```ini
[Service]
ExecStart=/usr/sbin/NetworkManager --no-daemon
```

Аналогичным образом параметры `ExecStop` и `ExecReload` задают команды для остановки службы и перезагрузки её конфигурации. С помощью `ExecStopPost` можно указать одну или несколько команд, которые должны выполняться после остановки процесса, подобно тому как `ExecStartPost` задаёт действия после запуска.

### Тип службы

В зависимости от ожидаемого поведения systemd определяет несколько типов служб. Тип службы задаётся параметром `Type`, которому можно присвоить одно из следующих значений:

- `simple`;
- `forking`;
- `oneshot`;
- `dbus`;
- `notify`.

Если параметры `Type` и `BusName` не заданы, но через `ExecStart` указана команда, по умолчанию используется тип `simple`. Для такой службы команда из `ExecStart` считается основным процессом службы.

Тип `forking` работает иначе: ожидается, что команда из `ExecStart` создаст дочерний процесс, который станет основным процессом службы. После завершения запуска родительский процесс должен завершиться.

Тип `oneshot` используется по умолчанию, если параметры `Type` и `ExecStart` не заданы. Он работает почти так же, как `simple`, но процесс должен завершить свою работу до запуска последующих модулей. Если параметру `RemainAfterExit` присвоено значение `yes`, модуль продолжает считаться активным даже после завершения команды. По умолчанию используется значение `no`.

Следующий тип службы — `dbus`. При его использовании демон должен получить в D-Bus имя, указанное в обязательном для этого типа параметре `BusName`. В остальном он работает подобно типу `simple`, однако последующие модули запускаются только после получения имени D-Bus.

Тип `notify` также похож на `simple`, но демон должен отправить уведомление с помощью функции `sd_notify`. Последующие модули запускаются только после отправки этого уведомления.

### Настройка тайм-аутов процесса

Специальные параметры позволяют задать тайм-ауты службы. Параметр `RestartSec` определяет, сколько времени systemd должна ждать перед перезапуском службы; по умолчанию значение задаётся в секундах. Можно также указать интервал в другом формате, например `5min 20s`. Значение по умолчанию — `100ms`.

Параметры `TimeoutStartSec` и `TimeoutStopSec` задают соответственно тайм-аут запуска и остановки службы. Если запуск демона не завершится за время, указанное в `TimeoutStartSec`, он будет признан неудачным.

Если служба не завершится за время, указанное в `TimeoutStopSec`, ей сначала будет отправлен сигнал `SIGTERM`, а по истечении такого же интервала — `SIGKILL`. Оба параметра принимают в качестве значения интервал времени. Их также можно настроить одновременно с помощью сокращённого параметра `TimeoutSec`. Значение `infinity` отключает тайм-ауты.

Наконец, параметр `RuntimeMaxSec` позволяет ограничить время работы службы. Если служба превысит этот лимит, она будет завершена и признана отказавшей.

## Раздел `[Install]`

Раздел `[Install]` содержит параметры, связанные с установкой службы. Например, параметр `Alias` позволяет задать разделённый пробелами список псевдонимов службы, которые можно использовать в командах `systemctl`, кроме `enable`.

Подобно параметрам `Requires` и `Wants` из раздела `[Unit]`, в разделе `[Install]` для определения зависимостей используются `RequiredBy` и `WantedBy`. Оба параметра объявляют список модулей, которые зависят от настраиваемого модуля: `RequiredBy` задаёт строгие зависимости, а `WantedBy` — слабые. Например:

```ini
[Install]
WantedBy=multi-user.target
```

Этой строкой мы объявили, что целевой модуль `multi-user.target` имеет слабую зависимость от нашего модуля. В терминологии systemd модули с суффиксом `.target` можно сопоставить с уровнями выполнения (`runlevel`) в других системах инициализации, например SysVinit. Следовательно, при достижении цели `multi-user.target` должна быть подключена и наша служба.

## Создание и установка сервисного модуля

Сервисные модули systemd устанавливаются главным образом в два каталога: `/usr/lib/systemd/system` и `/etc/systemd/system`. Первый предназначен для служб, поставляемых установленными пакетами. Второй системный администратор может использовать для собственных служб и переопределений стандартных модулей.

Создадим собственную службу. Предположим, при её запуске нужно отключать функцию Wake-on-LAN для определённого интерфейса Ethernet — в нашем случае `ens5f5`, — а при остановке снова включать её. Основную задачу можно выполнить командой `ethtool`. Файл службы будет выглядеть так:

```ini
[Unit]
Description=Force ens5f5 ethernet interface to 100Mbps
Requires=network.target
After=network.target

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/sbin/ethtool -s ens5f5 wol d
ExecStop=/usr/sbin/ethtool -s ens5f5 wol g

[Install]
WantedBy=multi-user.target
```

Мы задали простое описание модуля, объявили зависимость службы от `network.target` и указали, что она должна запускаться после достижения этой цели. В разделе `[Service]` службе назначен тип `oneshot`. Параметр `RemainAfterExit` предписывает systemd считать её активной после выполнения команды. Здесь же определены команды для запуска и остановки службы. Наконец, в разделе `[Install]` указано, что служба должна быть подключена к цели `multi-user.target`.

Чтобы установить службу, скопируем файл в каталог `/etc/systemd/system` под именем `wol.service`, а затем запустим её:

```console
$ sudo cp wol.service /etc/systemd/system && sudo systemctl start wol.service
```

Проверим, активна ли служба:

```console
$ systemctl is-active wol.service
active
```

Как и ожидалось, команда вывела `active`. Теперь убедимся, что параметр Wake-on-LAN получил значение `d`, то есть функция отключена:

```console
$ sudo ethtool ens5f5|grep Wake-on
Supports Wake-on: pg
Wake-on: d
```

После остановки службы результат должен измениться на противоположный: Wake-on-LAN снова будет включён.

```console
$ sudo systemctl stop wol.service && sudo ethtool ens5f5|grep Wake-on
Supports Wake-on: pg
Wake-on: g
```

## Заключение

Мы рассмотрели структуру файла службы systemd, его разделы и некоторые доступные в них параметры. Мы научились задавать описание службы, определять её зависимости и объявлять команды, которые должны выполняться при запуске, остановке и перезагрузке конфигурации.

Нравится нам это или нет, systemd стала стандартной системой инициализации в мире Linux, поэтому важно познакомиться с её принципами работы.
