# select фундаментально сломан

Источник: [Select is fundamentally broken](https://idea.popcount.org/2017-01-06-select-is-fundamentally-broken/)

Marek · 6 января 2017

В предыдущей записи блога мы обсудили [краткую историю системного вызова `select(2)`](https://idea.popcount.org/2016-11-01-a-brief-history-of-select2/). Статья завершается выводом, что некое мультиплексирование ввода-вывода было необходимо для эмуляции консоли, игр и нетривиальных приложений TCP/IP.

Разработчики BSD выбрали модель мультиплексирования `select`, а остальные Unix последовали их примеру. Но является ли `select` единственной моделью мультиплексирования?

Хорошее объяснение можно найти в старом издании книги ["The Design and Implementation of the FreeBSD Operating System"](https://www.freebsd.org/doc/en_US.ISO8859-1/books/design-44bsd/). Она есть в [Google books](https://books.google.pl/books?id=KfCuBAAAQBAJ&pg=PA325&lpg=PA325&redir_esc=y), вот фрагмент:

> Есть четыре возможных альтернативы, позволяющие избежать проблемы блокировки:
>
>   1. Установить все дескрипторы в неблокирующий режим. [...]
>   2. Разрешить всем интересующим дескрипторам [посылать] сигнал, когда можно выполнить I/O. [...]
>   3. Предоставить со стороны системы метод, позволяющий узнать, какие дескрипторы способны выполнить I/O [...]
>   4. Заставить процесс зарегистрировать в [операционной] системе все интересующие его события, включая I/O на дескрипторах, которые он хочет отслеживать.

Вариант 1) наивен. Идея состоит в активном опросе (busy-polling) неблокирующих дескрипторов. Это требует 100% загрузки CPU. Не очень практично.

Вариант 2) — это старая добрая [SIGIO](http://davmac.org/davpage/linux/async-io.html) модель асинхронного I/O. Linux реализует её с помощью [`fcntl(F_SETSIG)`](https://linux.die.net/man/2/fcntl). Когда `fcntl` настроен, сигнал будет уведомлять ваш процесс об изменении доступности дескриптора для чтения / записи. Увы, модель `F_SETSIG` в текущей реализации почти совершенно бесполезна1.

Вариант 3) — это модель, которую предоставляет `select()`. Она проста, хорошо определена и легка для понимания. Эту же модель разделяют системные вызовы `poll` и `epoll`.

Вариант 4) — самый интересный. Идея в том, чтобы перенести часть состояния в ядро и сообщить ему, что именно мы хотим делать с файловым дескриптором. Это модель, предоставляемая `kqueue` и Windows IOCP.

Каждая из этих четырёх моделей мультиплексирования имеет свои слабые места, но я хотел бы сфокусироваться именно на третьем варианте: `select`.

## Тяжеловесность

`select()` была [впервые реализована 33 года назад](https://idea.popcount.org/2016-11-01-a-brief-history-of-select2/) и для своего возраста держится замечательно. К сожалению, она сломана концептуально (by design).

Сломан не только системный вызов `select()`. Все технологии, унаследовавшие его семантику, тоже сломаны! Это касается `select`, `poll` и в меньшей степени `epoll`.

Обычный аргумент против `select` состоит в том, что API требует линейного обхода файловых дескрипторов. Это правда, но, на мой взгляд, это не самая большая проблема. Семантика `select` не даёт ядру делать какие-либо оптимизации. Создать быструю реализацию `select` на стороне ядра невозможно.

Каждый раз, когда ваш процесс входит в `select()`, ядро должно обойти переданные файловые дескрипторы, проверить их состояние и зарегистрировать обратные вызовы. Затем, когда событие происходит на _любом_ из fd, ядро должно снова выполнить обход, чтобы разрегистрировать обратные вызовы. По сути, на стороне ядра вход в `select()` и выход из него — тяжеловесная операция, требующая касания множества указателей и «прогревания» кэша процессора, и обойти это никак нельзя.

`epoll()` — решение Linux. С его помощью разработчик может избежать постоянной регистрации и разрегистрации файловых дескрипторов. Это делается явным управлением регистрациями с помощью системного вызова `epoll_ctl`.

Но `epoll` решает не все проблемы.

## Проблема «громового стада» (thundering herd)

Представьте файловый дескриптор сокета, общий для нескольких процессов операционной системы. Когда происходит событие, _все_ процессы должны быть разбужены. Это может показаться надуманной претензией — зачем делить дескриптор сокета между процессами? — но на практике такое случается.

Допустим, вы запускаете HTTP-сервер, обслуживающий большое количество короткоживущих соединений. Вы хотите принимать (`accept()`) как можно больше соединений в секунду. Вызов `accept()` только в одном процессе наверняка упрётся в CPU. Как это исправить?

Наивный ответ: давайте сделаем дескриптор общим и позволим нескольким процессам одновременно вызывать `accept()`! К сожалению, на практике это _ухудшит_ производительность.

Чтобы проиллюстрировать проблему, я написал два куска кода.

Первый — программа [`server.c`](https://github.com/majek/dump/blob/master/select-sucks/server.c). Она привязывается к TCP-порту 1025 и перед блокировкой на `select` делает несколько форков. Псевдокод:

```python
sd = socket.socket()
sd.bind('127.0.0.1:1025')
sd.listen()
for i in range(N):
    if os.fork() == 0:
        break
select([sd])
```

Чтобы запустить 1024 форка, все висят в `select` на одном привязанном сокете:

```bash
$ ./server 1024
forks = 1024, dupes per fork = 1, total = 1024
[+] started
```

Вторая программа [`client.c`](https://github.com/majek/dump/blob/master/select-sucks/client.c) тривиальна. Она подключается к TCP-порту и измеряет время. Для лучшей иллюстрации проблемы она выполняет неблокирующий вызов `connect(2)`. Теоретически это всегда должно быть молниеносно быстро.

Есть, однако, нюанс. Поскольку соединение идёт через loopback на localhost, пакеты будут обработаны синхронно, в ходе обработки системного вызова `connect` ядром.

Измерение длительности неблокирующего `connect` на практике показывает время диспетчеризации ядра. Мы измерим, сколько времени ядру требуется, чтобы:

  * создать новое соединение через loopback,
  * найти соответствующий дескриптор слушающего сокета на принимающей стороне,
  * поместить новое соединение в очередь accept
  * и разбудить процессы, ожидающие на этом слушающем сокете.

Стоимость последнего шага пропорциональна числу процессов, ожидающих на этом сокете. Вот график, показывающий, что длительность системного вызова `connect` линейно растёт с числом процессов, висящих в `select` на слушающем сокете:

Вызов неблокирующего `connect()` к слушающему сокету, общему для 16 тысяч процессов, занимает на моей машине 35 миллисекунд.

Эти результаты ожидаемы. Ядру нужно делать линейно больше работы для каждого процесса, который нужно разбудить, и для каждого файлового дескриптора, на котором процесс блокируется в `select()`. Это справедливо и для `epoll()`.

## Экстремальный эксперимент

Доведём эксперимент до крайности. Посмотрим, что будет, если в цикле `select` ждёт не один слушающий сокет, а тысяча. Чтобы усложнить ядру задачу, мы скопируем привязанный к TCP-порту 1025 сокет тысячу раз с помощью `dup()`. Псевдокод:

```python
sd = socket.socket()
sd.bind('127.0.0.1:1025')
sd.listen()

list_of_duplicated_sd = [dup(sd) for i in xrange(1019)]
```

```python
for i in range(N):
    if os.fork() == 0:
        break
select([sd] + list_of_duplicated_sd)
```

Это тоже реализовано в `server.c`:

```text
marek:~$ ./server 1024 1019
forks = 1024, dupes per fork = 1019, total = 1043456
[+] started
```

График покажет линейную стоимость, но с куда большим постоянным множителем:

График подтверждает очень большую стоимость такой конфигурации. При 16 тысячах работающих процессов, каждый из которых продублировал слушающий сокет 1019 раз (в сумме 16 млн файловых дескрипторов), ядру требуется целых 1,5 секунды, чтобы выполнить неблокирующий `connect()` на localhost.

Вот как это выглядит в консоли:

```text
marek:~$ time nc localhost 1025 -q0
real    0m1.523s

marek:~$ strace -T nc localhost 1025 -q0
...
connect(3, {sa_family=AF_INET, sin_port=htons(1025), sin_addr=inet_addr("127.0.0.1")}, 16) = -1 EINPROGRESS (Operation now in progress) <1.390385>
...
```

Такая конфигурация перегружает машину. Наше единственное событие стремительно переводит тысячи процессов Linux из состояния «sleep» в «runnable», что даёт интересные значения load average:

```text
marek:~$ uptime
 load average: 1388.77, 1028.89, 523.62
```

## Epoll exclusive спешит на помощь

Это классическая проблема «громового стада» (thundering herd). Она смягчается новым флагом `EPOLLEXCLUSIVE` для `epoll_ctl`. Он был добавлен совсем недавно, в ядро 4.5. [Man-страница](man7.org/linux/man-pages/man2/epoll_ctl.2.html) гласит:

> EPOLLEXCLUSIVE (since Linux 4.5) Sets an exclusive wakeup mode for the epoll file descriptor that is being attached to the target file descriptor, fd. When a wakeup event occurs and multiple epoll file descriptors are attached to the same target file using EPOLLEXCLUSIVE, one or more of the epoll file descriptors will receive an event with epoll_wait(2).

Вот соответствующий патч ядра:

  * <https://lwn.net/Articles/667087/>

Если я правильно понимаю код, он предназначен для улучшения среднего случая. Патч не решает фундаментально проблему того, что время диспетчеризации ядра составляет затратные `O(N)` по числу процессов / дескрипторов.

## Резюме

Я объяснил две проблемы модели мультиплексирования `select()`.

Она тяжеловесна. Она требует постоянно регистрировать и разрегистрировать процессы на файловых дескрипторах — потенциально тысячи дескрипторов, тысячи раз в секунду.

Другая проблема — масштабируемость совместного использования сокета между процессами. В традиционной модели ядро должно будить все процессы, висящие на сокете, даже если доставить нужно лишь одно событие. Это приводит к проблеме «громового стада» и массе бесполезных пробуждений процессов.

Linux решает первую проблему системным вызовом `epoll`, а вторую — «заплаткой» `EPOLLEXCLUSIVE`.

Думаю, настоящее решение — фундаментально переосмыслить мультиплексирование сокетов. Вместо того чтобы клеить заплатки на «вариант 3)» из книги Кирка МакКьюсика, нам стоит сфокусироваться на «варианте 4)» — интерфейсах `kqueue` и `IOCP`.

Но это тема для другой статьи.
