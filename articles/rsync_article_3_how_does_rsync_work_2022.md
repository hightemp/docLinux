## Как работает rsync?

Говоря о протоколе rsync, нам нужно различать:

  * роли на уровне протокола: «отправитель» (sender) и «получатель» (receiver)
  * роли TCP: «клиент» и «сервер»

Все роли могут свободно сочетаться: оба rsync-клиента (или сервера!) могут как отправлять, так и принимать.

Теперь, когда вы знаете терминологию, давайте посмотрим на протокол rsync с высокого уровня. Мы рассмотрим версию протокола 27 — она старше, но проще, и это самая широко поддерживаемая версия протокола, реализованная в `openrsync` и других сторонних реализациях:

Протокол rsync можно разделить на две фазы:

  1. В первой фазе отправитель обходит локальное дерево файлов, чтобы сгенерировать и отправить _список файлов_ (file list) получателю. Список файлов должен быть передан полностью, потому что обе стороны сортируют его по имени файла (более поздние версии протокола rsync устраняют этот шаг синхронной сортировки).

  2. Во второй фазе, одновременно:

```text
 * The receiver compares and requests each file in the file list. The receiver requests the full file when it didn’t exist on disk yet, or it will send checksums for the rsync _hash search_ algorithm when the file already existed.
 * The receiver receives file data from the sender. The sender answers the requests with just enough data to reconstruct the current file contents based on what’s already on the receiver.
```

Архитектура позволяет легко реализовать вторую фазу в 3 отдельных процесса, каждый из которых отправляет в сеть настолько быстро, насколько возможно, используя агрессивный пайплайнинг. В результате доступные аппаратные ресурсы (I/O, CPU, сеть) на отправителе и получателе используются на полную.

### Наблюдение за фазами передачи rsync

При запуске передачи rsync просмотр использования ресурсов обеих машин позволяет нам подтвердить наше понимание архитектуры rsync и локализовать любые узкие места:

[![](/images/82bcb8135266b7d5aac99f31af1be2bf.png)](https://michael.stapelberg.ch/posts/2022-07-02-rsync-how-does-it-work/2022-05-29-rsync-exo1-backup.jpg)

  1. фаза: Отправителю rsync требуется 17 секунд, чтобы обойти файловую систему и отправить список файлов. Получатель rsync в это время читает из сети и пишет в RAM.

```text
 * This phase is random I/O (querying file system metadata) for the sender.
```

  2. фаза: Затем отправитель rsync читает с диска и отправляет в сеть. Получатель rsync принимает из сети и пишет на диск.

```text
 * The receiver does roughly the same amount of random I/O as the sender did in phase 1, as it needs to create directories and request missing files.
 * The sender does sequential disk reads and possibly checksum calculation, if the file(s) existed on the receiver side.
```

(Опять же, вышеописанное было зафиксировано на версии протокола rsync 27; более поздние версии протокола rsync не синхронизируются после завершения фазы 1, а перемежают фазы сильнее.)

### Поиск по хэшам rsync (hash search)

До сих пор мы описывали протокол rsync на высоком уровне. Давайте приблизимся к шагу поиска по хэшам — именно его многие люди, возможно, ассоциируют с термином «алгоритм rsync».

Когда файл существует на обеих сторонах — отправителе и получателе rsync — получатель сначала делит файл на блоки. Размер блока — это округлённый квадратный корень из длины файла. Затем получатель отправляет контрольные суммы всех блоков отправителю. В ответ отправитель находит совпадающие блоки в файле и отправляет только те данные, которые нужны для реконструкции файла на стороне получателя.

Конкретно, отправитель проходит по **каждому байту** файла и пытается сопоставить его с существующим содержимым получателя. Чтобы снизить вычислительную стоимость, rsync комбинирует две контрольные суммы.

rsync сначала вычисляет то, что называет [«sum1»](https://github.com/WayneD/rsync/blob/0ac7ebceef70417355f25daf9e2fd94e84c49749/checksum.c#L182-L203), или «быструю сигнатуру». Это маленькая контрольная сумма (два `uint16`), которую можно вычислить с минимальными усилиями для скользящего окна по данным файла. rsync tridge поставляется с [SIMD-реализациями](https://github.com/WayneD/rsync/blob/v3.2.4/simd-checksum-x86_64.cpp), чтобы ещё ускорить это там, где возможно.

Только если sum1 совпала, вычисляется [«sum2»](https://github.com/WayneD/rsync/blob/0ac7ebceef70417355f25daf9e2fd94e84c49749/checksum.c#L205-L300) (или «сильная сигнатура») — 16-байтовый хэш MD4. Более новые версии протокола позволяют согласовывать алгоритм хэширования и поддерживают куда более быстрые алгоритмы xxhash.

Если sum2 совпала, блок считается одинаковым на обеих сторонах.

Следовательно, лучший случай для rsync — когда файл либо вовсе не изменился, либо делится максимально большим числом целых блоков содержимого со старой версией.

## Изменяющиеся наборы данных

Теперь, когда мы знаем, как rsync работает на уровне файлов, давайте отступим на уровень наборов данных.

Простейшая ситуация — когда вы передаёте набор данных, который в данный момент не меняется. Но что происходит, когда набор данных меняется прямо во время передачи rsync? Вот два примера.

[debiman](https://github.com/Debian/debiman) — генератор man-страниц, на котором работает [manpages.debian.org](https://manpages.debian.org/) — запущен на виртуальной машине Debian, с которой rsync-задание периодически передаёт статический архив man-страниц на различные статические веб-серверы по всему миру. Rsync-задание и debiman никак не согласованы по последовательности выполнения. Вместо этого debiman аккуратно [атомарно заменяет файлы](https://github.com/Debian/debiman/blob/79b8abe8573daaaf15e4cf40e85daf309e00d454/internal/write/atomically.go#L23) в своём выходном каталоге или добавляет новые файлы перед тем, как заменить обновлённый индекс.

Второй пример — система управления базами данных [PostgreSQL](https://en.wikipedia.org/wiki/PostgreSQL) — противоположная ситуация: вместо полного контроля над тем, как раскладываются файлы, здесь я не контролирую то, как файлы записываются (это обобщается на любую ситуацию, когда модель «только заменять файлы» нереализуема). Файлы данных, которые моя установка Postgres держит на диске, не подходят для синхронизации rsync: они большие и часто меняются. Вместо этого я теперь исключаю их из rsync-передачи и использую [`pg_dump(1)`](https://manpages.debian.org/pg_dump.1), чтобы создавать слепок моих баз данных.

Чтобы детально подтвердить поведение rsync в отношении изменяющихся наборов данных, я модифицировал rsync, чтобы он запрашивал подтверждение между генерацией списка файлов и передачей файлов. Вот что я обнаружил:

  * Если файлы добавлены после того, как rsync передал список файлов, новые файлы просто не попадут в передачу.
  * Если файл исчезает между генерацией списка файлов и передачей файла, rsync завершается с кодом состояния 24, который [его man-страница документирует как «Partial transfer due to vanished source files»](https://manpages.debian.org/bullseye/rsync/rsync.1.en.html#EXIT_VALUES). Мой обёрточный мониторинговый скрипт `rsyncprom` [предлагает флаг, чтобы трактовать код выхода 24 как код выхода 0](https://github.com/stapelberg/rsyncprom/commit/bbf82934093b938d054d460a7f9764234d30bc17), потому что в зависимости от набора данных исчезновение файлов — ожидаемое явление.
  * Если содержимое файла меняется (неважно, растёт файл, уменьшается или модифицируется на месте) между генерацией списка файлов и фактической передачей файла, это не проблема — rsync передаст содержимое файла так, как прочитает его, когда передача начнётся. Заметьте, что это может быть несогласованным представлением данных, в зависимости от приложения.

```text
* Ideally, don’t ever modify files within a data set that is rsynced. Instead, atomically move complete files into the data set.
```

Иначе говоря, согласованность данных — это не то, что rsync может каким-либо образом гарантировать. Вам решать: либо смириться с несогласованностью (часто достаточно хорошая стратегия!), либо добавить дополнительный шаг, который гарантирует, что набор данных, передаваемый rsync, согласован.
