В [«Анатомии DNS-запроса в Linux. Часть I»](http://zwischenzugs.com/2018/06/08/anatomy-of-a-linux-dns-lookup-part-i/) я рассмотрел:

Всё это было более общим поведением Linux **(\*)**, но здесь мы твёрдо переходим на территорию, специфичную для дистрибутивов. Я использую ubuntu, но многое из этого будет пересекаться с Debian и даже дистрибутивами на базе CentOS, а также отличаться от более ранних или поздних версий Ubuntu.

###### (\) на самом деле это предмет стандарта POSIX, так что не ограничивается Linux (я узнал об этом из фантастического [комментария](https://zwischenzugs.com/2018/06/08/anatomy-of-a-linux-dns-lookup-part-i/#comment-2312) к предыдущему посту)

Иначе говоря: с этого места поведение вашего хоста скорее будет отличаться в деталях.

В Части II я разберу, как может обновляться `resolv.conf`, что происходит при запуске `systemctl restart networking` и как здесь замешан `dhclient`.

# 1) Обновление /etc/resolv.conf вручную

Мы знаем, что на `/etc/resolv.conf` (скорее всего) ссылаются, так что, конечно же, можно просто добавить nameserver в этот файл, и ваш хост будет использовать этот nameserver в дополнение к остальным, верно?

Если попробовать так:

```bash
$ echo nameserver 10.10.10.10 >> /etc/resolv.conf
```

всё выглядит хорошо:

```text
# Dynamic resolv.conf(5) file for glibc resolver(3) generated by resolvconf(8)
#     DO NOT EDIT THIS FILE BY HAND -- YOUR CHANGES WILL BE OVERWRITTEN
nameserver 10.0.2.3
search home
nameserver 10.10.10.10
```

пока не перезапустится сеть:

```bash
$ systemctl restart networking
$ cat /etc/resolv.conf
# Dynamic resolv.conf(5) file for glibc resolver(3) generated by resolvconf(8)
#     DO NOT EDIT THIS FILE BY HAND -- YOUR CHANGES WILL BE OVERWRITTEN
nameserver 10.0.2.3
search home
```

наш nameserver `10.10.10.10` исчез!

Вот здесь и всплывают те комментарии, которые мы игнорировали в Части I…

# 2) resolvconf

Видите фразу `generated by resolvconf` в файле `/etc/resolv.conf` выше? Это наша зацепка.

Если копнуть, что делает `systemctl restart networking`, то среди многого другого он в итоге вызывает скрипт: `/etc/network/if-up.d/000resolvconf`. Внутри этого скрипта есть вызов `resolvconf`:

```text
/sbin/resolvconf -a "${IFACE}.${ADDRFAM}"
```

Небольшое копание в man-страницах показывает, что флаг `-a` позволяет нам:

```text
Add or overwrite the record IFACE.PROG then run the update scripts
if updating is enabled.
```

Может, мы можем вызвать это напрямую, чтобы добавить nameserver:

```text
echo 'nameserver 10.10.10.10' | /sbin/resolvconf -a enp0s8.inet
```

Оказывается, можем!

```bash
$ cat /etc/resolv.conf  | grep nameserver
nameserver 10.0.2.3
nameserver 10.10.10.10
```

Значит, на этом всё, верно? Вот так обновляется `/etc/resolv.conf`? Вызов `resolvconf` добавляет запись в какую-то базу, а затем обновляет (если настроено, что бы это ни значило) файл `resolv.conf`?

Нет.

```bash
$ systemctl restart networking
root@linuxdns1:/etc# cat /etc/resolv.conf
# Dynamic resolv.conf(5) file for glibc resolver(3) generated by resolvconf(8)
#     DO NOT EDIT THIS FILE BY HAND -- YOUR CHANGES WILL BE OVERWRITTEN
nameserver 10.0.2.3
search home
```

Аррр! Он снова исчез.

Значит, `systemctl restart networking` делает больше, чем просто запуск `resolvconf`. Информация о nameserver должна браться откуда-то ещё. Откуда?

* * *

# 3) ifup/ifdown

Дальнейшее копание в том, что делает `systemctl restart networking`, говорит нам пару вещей:

```text
cat /lib/systemd/system/networking.service
[...]
[Service]
Type=oneshot
EnvironmentFile=-/etc/default/networking
ExecStartPre=-/bin/sh -c '[ "$CONFIGURE_INTERFACES" != "no" ] && [ -n "$(ifquery --read-environment --list --exclude=lo)" ] && udevadm settle'
ExecStart=/sbin/ifup -a --read-environment
ExecStop=/sbin/ifdown -a --read-environment --exclude=lo
[...]
```

Во-первых, «сервис» networking на самом деле является скриптом типа ‘oneshot’, который выполняет эти команды:

```text
/sbin/ifdown -a --read-environment --exclude=lo
/bin/sh -c '[ "$CONFIGURE_INTERFACES" != "no" ] && [ -n "$(ifquery --read-environment --list --exclude=lo)" ] && udevadm settle'
/sbin/ifup -a --read-environment
```

Первая строка с `ifdown` опускает все сетевые интерфейсы (кроме локального). **(\*)**

###### (\*) Мне неясно, почему это не выкидывает меня из vagrant-сессии в моём примере кода (кто-нибудь знает?).

Вторая строка гарантирует, что система завершила всё, что нужно, касающееся опускания сетевых интерфейсов, прежде чем поднять их все обратно с помощью `ifup` в третьей строке. Так что второе, что мы узнаём: `ifup` и `ifdown` — это то, что networking-сервис «на самом деле» запускает.

Флаг `--read-environment` не документирован и существует, чтобы `systemctl` мог с этим дружить. Многие ненавидят `systemctl` за такие вещи.

Отлично. Так что же делает `ifup` (и его близнец `ifdown`)? Чтобы не тянуть долго: он запускает все скрипты в `etc/network/if-pre-up.d/` и `/etc/network/if-up.d/`. Те в свою очередь могут запускать другие скрипты и так далее.

Одно из действий (и я всё ещё не совсем понимаю, как — может, замешан `udev`?) — запускается `dhclient`.

# 4) dhclient

`dhclient` — программа, которая взаимодействует с DHCP-серверами, согласовывая детали того, какой IP-адрес должен использовать указанный сетевой интерфейс. Она также может получить DNS-nameserver, который затем помещается в `/etc/resolv.conf`.

Сразу к делу: сымитируем, что он делает, но только на интерфейсе `enp0s3` моей примерной VM, предварительно удалив nameserver из файла `/etc/resolv.conf`:

```bash
$ sed -i '/nameserver.*/d' /run/resolvconf/resolv.conf
$ cat /etc/resolv.conf | grep nameserver
$ dhclient -r enp0s3 && dhclient -v enp0s3
Killed old client process
Internet Systems Consortium DHCP Client 4.3.3
Copyright 2004-2015 Internet Systems Consortium.
All rights reserved.
For info, please visit https://www.isc.org/software/dhcp/
Listening on LPF/enp0s8/08:00:27:1c:85:19
Sending on   LPF/enp0s8/08:00:27:1c:85:19
Sending on   Socket/fallback
DHCPDISCOVER on enp0s8 to 255.255.255.255 port 67 interval 3 (xid=0xf2f2513e)
DHCPREQUEST of 172.28.128.3 on enp0s8 to 255.255.255.255 port 67 (xid=0x3e51f2f2)
DHCPOFFER of 172.28.128.3 from 172.28.128.2
DHCPACK of 172.28.128.3 from 172.28.128.2
bound to 172.28.128.3 -- renewal in 519 seconds.
```

```text
$ cat /etc/resolv.conf | grep nameserver
nameserver 10.0.2.3
```

Так вот откуда берётся nameserver…

Но подождите — что делает тут этот `/run/resolvconf/resolv.conf`, когда должен быть `/etc/resolv.conf`?

Оказывается, `/etc/resolv.conf` не всегда «просто» файл.

На моей VM это символическая ссылка на «настоящий» файл, хранящийся в `/run/resolvconf`. Это намёк, что файл конструируется во время выполнения, и одна из причин, почему нам говорят не редактировать файл напрямую.

Если бы команда `sed` выше была выполнена над файлом `/etc/resolv.conf` напрямую, поведение было бы другим, и было бы выдано предупреждение о том, что `/etc/resolv.conf` не является символической ссылкой (`sed -i` не работает с симлинками умно — он просто создаёт новый файл).

`dhclient` даёт возможность переопределить DNS-сервер, выданный вам по DHCP, если копнуть поглубже в настройку `supersede` в `/etc/dhcp/dhclient.conf`…
