# Пейсинг пакетов в Linux: fq против tbf

Источник: [Packet Pacing on Linux: fq vs tbf](https://osg-htc.org/networking/perfsonar/packet-pacing/)

OSG Networking Area · обновлено в декабре 2025

Этот документ объясняет, как работает пейсинг пакетов (packet pacing) в Linux с дисциплиной очередей `fq` (Fair Queue) и чем он отличается от явного ограничения скорости через `tbf` (Token Bucket Filter). Также здесь разъясняется, как всё это взаимодействует с профилями tuned и сценариями использования perfSONAR/DTN-хостов.

## Резюме

* fq: включает TCP-пейсинг для каждого потока. Сглаживает всплески и учитывает скорости пейсинга на поток, задаваемые ядром или приложениями. Нет жёсткого ограничения на уровне интерфейса.
* tbf: накладывает ограничение на уровне интерфейса. Полезно при требованиях политики или ограничениях железа. Не поблочно-поточное; применяется ко всему трафику через qdisc.
* tuned: профиль `network-throughput` обычно устанавливает `net.core.default_qdisc=fq`, что активирует TCP-пейсинг, когда интерфейс использует `fq`.

## fq (Fair Queue) и TCP-пейсинг

* Очереди на каждый поток: `fq` поддерживает отдельные очереди для каждого потока (например, TCP-соединения).
* SO_MAX_PACING_RATE: приложения могут вызывать `setsockopt()` с `SO_MAX_PACING_RATE`, чтобы задать желаемую максимальную скорость пейсинга для socket'а. Примеры: `iperf3` и некоторые инструменты передачи данных устанавливают её.
* Управляемый ядром пейсинг: даже когда приложения не задают `SO_MAX_PACING_RATE`, современный TCP в Linux вычисляет пейсинг на основе окна перегрузки и RTT, а `sch_fq` использует `sk->sk_pacing_rate` для планирования пакетов, сглаживая всплески.
* Поведение по умолчанию: если скорость пейсинга не задана, трафик жёстко не ограничивается `fq`; потоки всё равно выигрывают от изоляции и сглаживания всплесков.
* Зачем использовать fq: соответствует рекомендациям Fasterdata для высокопроизводительных хостов; улучшает справедливость и задержку под нагрузкой; хорошо работает с BBR/CUBIC.

### Полезные ручки `fq` (продвинутое)

* `tc qdisc add dev <if> root fq [quantum <bytes>] [flow_limit <packets>] [low_rate_threshold <bps>]`
* Большинству сайтов не нужно это настраивать; значения по умолчанию хорошо работают на современных ядрах.

## tbf (Token Bucket Filter)

* Ограничение скорости на уровне интерфейса: `tbf` принуждает к максимальной скорости передачи с помощью корзины токенов с параметрами `rate`, `burst` и `latency`.
* Не поблочно-поточно: весь трафик делит общий лимит; может снизить общую пропускную способность, если задать её ниже ёмкости канала.
* Когда использовать: требования политики сайта; ограничения железа или вышестоящего сегмента; лабораторные/тестовые сценарии.

### Пример команды `tbf`

```bash
# Ограничение до 2 Гбит/с, всплеск ~1 мс, бюджет задержки 100 мс
sudo tc qdisc replace dev eth0 root tbf rate 2000mbps burst 250000 latency 100ms
```

Рекомендация по burst: примерно `(rate * 1ms) / 8` байт; зажимать между ~1500 байт и ~10 МБ. Удалить tbf: `sudo tc qdisc del dev eth0 root` или заменить на `fq`.

## Взаимодействие с tuned

* `tuned-adm profile network-throughput` обычно устанавливает `net.core.default_qdisc=fq` (через sysctl), поэтому новые интерфейсы используют `fq`.
* Аудиты должны принимать `fq` (TCP-пейсинг) или `tbf` (явное ограничение) как «пейсинг применён» — в зависимости от намерений сайта.
* Если tuned или другие инструменты неожиданно настроили `tbf`, уточните требования сайта, прежде чем менять его на `fq`.

## Соображения для perfSONAR/DTN

Измерительные хосты: предпочитайте `fq` для сглаживания всплесков без искусственных ограничений. DTN-хосты: по умолчанию `fq`; добавляйте `tbf` только когда требуется конкретное ограничение. Скрипт настройки поддерживает оба пути:

* `--apply-packet-pacing` → устанавливает `fq` (TCP-пейсинг)
* `--apply-packet-pacing --use-tbf-cap` → применяет `tbf` с автоматическим лимитом (по умолчанию ≈ 90% скорости канала)
* `--apply-packet-pacing --tbf-cap-rate 2000mbps` → применяет `tbf` с явным лимитом (устаревший псевдоним: `--packet-pacing-rate`)

### Подсказки интерфейса в аудитах

* `fq` отображается зелёным (предпочтительно)
* `tbf` отображается голубым (приемлемо, когда ограничение интерфейса сделано намеренно)

## Проверка

* Показать qdisc: `tc qdisc show dev <if>` должен показывать `fq ...` или `tbf ...` в корне.
* Проверить sysctl: `sysctl -n net.core.default_qdisc` должно быть `fq` при tuned-профиле `network-throughput`.
* На уровне приложения: такие инструменты, как `iperf3`, могут задавать `SO_MAX_PACING_RATE`; иначе применяется TCP-пейсинг ядра при `fq`.

## Пейсинг пакетов для узлов передачи данных

## Обзор

**Пейсинг пакетов (packet pacing)** — критически важная техника настройки для высокопроизводительных узлов передачи данных (Data Transfer Nodes, DTN) и других хостов, которым нужно надёжно передавать большие объёмы данных через глобальные сети. Управляя скоростью, с которой пакеты отправляются с хоста, пейсинг пакетов может кардинально снизить потери пакетов, предотвратить переполнение буферов приёмника и повысить общую пропускную способность — иногда **в 2-4 раза на длинных путях**.

Этот документ объясняет, почему пейсинг пакетов важен, как он работает и как внедрить его на DTN-узлах с помощью управления трафиком Linux (`tc`).

## Проблема: узкие места скорости данных и потери пакетов

При передаче данных по сети эффективная пропускная способность ограничена **минимумом из трёх факторов**:

1. **Скорость чтения хоста-источника** — как быстро отправляющий хост может читать данные из хранилища/памяти

2. **Доступная сетевая пропускная способность** — ёмкость сетевого пути

3. **Скорость записи приёмника** — как быстро принимающий хост может писать данные в хранилище/память

### Типичные сценарии узких мест

#### Сценарий 1: быстрый источник, более медленный сетевой путь

* 10G DTN отправляет данные 1G-приёмнику или через 1G-сеть

* Без пейсинга DTN заливает сеть пакетами

* Приёмник не успевает, что приводит к переполнению буфера и потерям пакетов

* TCP снижает скорость, вызывая резкое падение пропускной способности

#### Сценарий 2: несколько параллельных потоков

* 10G DTN с 4-8 параллельными потоками GridFTP к 10G-приёмнику

* Общая доступная полоса — 10G, но каждый поток пытается выжать максимум из своего соединения

* Потоки конкурируют за буферы на приёмнике

* Потери пакетов и снижение скорости TCP уменьшают общую пропускную способность

#### Сценарий 3: несбалансированная производительность CPU/сети

* Быстрый хост 40G/100G с медленным CPU

* Сеть может отправлять пакеты быстрее, чем CPU успевает их обрабатывать

* Узкое место на стороне приёма у более медленного хоста

* Потери пакетов и накладные расходы на ретрансмиссии

#### Сценарий 4: дальние пути (RTT 50-80 мс)

* Сетевые пути с высокой задержкой через континенты

* Даже при достаточной полосе несогласованные скорости отправки/приёма вызывают проблемы

* Пакеты приходят быстрее, чем приёмник успевает их вычитывать

* Исследования показывают улучшение пропускной способности в 2-4 раза при пейсинге на таких путях

## Как работает пейсинг пакетов

Пейсинг пакетов решает эту проблему, **управляя скоростью, с которой пакеты покидают хост-источник**, гарантируя, что приёмник никогда не будет перегружен и сможет обрабатывать пакеты в устойчивом темпе.

### Механизм: дисциплина очередей Fair Queuing (FQ)

Современный Linux (ядро 3.11+) включает планировщик **Fair Queuing (FQ)**, реализующий продвинутый пейсинг пакетов. Qdisc FQ:

* **Поддерживает отдельные очереди** для разных потоков (различая разные потоки данных)

* **Обеспечивает справедливое деление полосы** — каждый поток получает равную долю доступной полосы

* **Интеллектуально распределяет пакеты по времени** — вместо отправки всплесками

* **Снижает давление на буферы** — не даёт принимающей стороне перегружаться

#### FQ против FQ_CODEL

* **FQ** (Fair Queuing): отлично подходит для высокопроизводительного TCP и передачи данных

* **FQ_CODEL**: значение по умолчанию в современных ядрах (4.12+), но менее оптимально для длительных высокопроизводительных передач

Для DTN и скоростной передачи данных **рекомендуется FQ вместо FQ_CODEL**.

### Ограничение скорости с помощью Token Bucket Filter (TBF)

Qdisc **Token Bucket Filter (TBF)** принуждает к максимальному лимиту скорости следующим образом:

* **Накапливает токены** с заданной скоростью (например, 2 Гбит/с)

* **Требует токены для отправки пакетов** — каждый пакет потребляет токены, равные его размеру

* **Ставит пакеты в очередь**, когда токенов нет

* **Сглаживает трафик** до предсказуемой, контролируемой скорости

Размер burst определяет, сколько пакетов подряд можно отправить до включения ограничения скорости. Обычно мы рассчитываем burst как объём пакетов за 1-2 мс при целевой скорости.

## Почему пейсинг пакетов работает: результаты исследований ESnet

Тесты производительности ESnet совместно с Berkeley Lab и другими продемонстрировали значительные улучшения от пейсинга пакетов:

### Ключевые выводы

1. **Снижение потерь пакетов**: за счёт предотвращения переполнения буфера приёмника

2. **Более высокая устойчивая пропускная способность**: улучшения в 2-4 раза на длинных путях (RTT 50-80 мс)

3. **Лучшее использование ресурсов**: предотвращает напрасные ретрансмиссии и снижение скорости TCP

4. **Предсказуемая производительность**: более стабильные результаты при разных сетевых условиях

5. **Преимущества для мультипотоков**: особенно эффективно с 4-8 параллельными потоками (типично для GridFTP)

### Реальный сценарий на DTN

**Конфигурация**: 10G DTN с 4 параллельными потоками GridFTP к 10G-приёмнику

**Без пейсинга**:

* Всплески пакетов перегружают приёмник

* Потери пакетов вызывают TCP-ретрансмиссии

* Управление перегрузкой TCP агрессивно снижает скорость

* Пропускная способность: ~3-5 Гбит/с (при доступных 10G используется не полностью)

**С пейсингом 2 Гбит/с на поток** (всего 8 Гбит/с из 4 потоков):

* Плавный трафик снижает потери пакетов

* TCP может поддерживать большее окно перегрузки

* Лучшее использование ресурсов на приёмнике

* Пропускная способность: ~8-9 Гбит/с (почти скорость линии)

**Результат**: улучшение пропускной способности в 2-3 раза

## Рекомендуемые скорости пейсинга для типичных сценариев

### Правило большого пальца: 80-90% скорости NIC

Для DTN с **N параллельными потоками** делите доступную полосу соответственно:

| Скорость NIC хоста | Параллельные потоки | Рекомендуемая скорость на поток | Пример команды |
| --- | --- | --- | --- |
| 10G | 4 | 2 Гбит/с | `tc qdisc add dev eth0 root fq maxrate 2gbit` |
| 10G | 8 | 1 Гбит/с | `tc qdisc add dev eth0 root fq maxrate 1gbit` |
| 40G | 4 | 8 Гбит/с | `tc qdisc add dev eth0 root fq maxrate 8gbit` |
| 40G | 8 | 5 Гбит/с | `tc qdisc add dev eth0 root fq maxrate 5gbit` |
| 100G | 8 | 10-12 Гбит/с | `tc qdisc add dev eth0 root fq maxrate 10gbit` |
| 100G (на пути 10G) | Любое | 2 Гбит/с | `tc qdisc add dev eth0 root fq maxrate 2gbit` |

### Обоснование

* **Консервативное значение по умолчанию: 2 Гбит/с** — подходит для большинства передач 10G-на-10G, не даёт перегрузить типовые приёмники

* **Корректируйте по RTT**: более длинные пути выигрывают от чуть меньших скоростей

* **Делите полосу**: при 4 параллельных потоках на 10G NIC 2 Гбит/с на поток = 8 Гбит/с суммарно (утилизация 80%)

* **Мониторьте и настраивайте**: используйте `iperf3 --fq-rate` или perfSONAR pscheduler для тестирования вашего конкретного пути

## Внедрение: использование fasterdata-tuning.sh

Скрипт `fasterdata-tuning.sh` включает автоматическую настройку пейсинга пакетов для DTN-узлов.

### Аудит текущего состояния

Проверьте, какие скорости пейсинга рекомендуются для вашего DTN:

```bash
fasterdata-tuning.sh --mode audit --target dtn
```

Вывод показывает:

* Применён ли пейсинг пакетов сейчас

* Рекомендуемая скорость по умолчанию: 2 Гбит/с (2000mbps)

### Применить пейсинг пакетов

Применить пейсинг со скоростью по умолчанию 2 Гбит/с:

```bash
sudo fasterdata-tuning.sh --mode apply --target dtn --apply-packet-pacing
```

Применить с произвольной скоростью (например, для 100G-хоста с 8 потоками):

```bash
sudo fasterdata-tuning.sh --mode apply --target dtn --apply-packet-pacing --packet-pacing-rate 10gbps
```

Поддерживаемые единицы скорости: `kbps`, `mbps`, `gbps`, `tbps`

Примеры:

* `2gbps` — 2 гигабита в секунду

* `10000mbps` — 10 гигабит в секунду (эквивалент 10gbps)

* `2000mbps` — 2 гигабита в секунду (по умолчанию)

### Пробный запуск (dry-run)

Посмотрите, что будет применено, без внесения изменений:

```bash
sudo fasterdata-tuning.sh --mode apply --target dtn --apply-packet-pacing --dry-run
```

Вывод показывает точные команды `tc`, которые будут выполнены на каждом интерфейсе.

### Расчёт размера burst

Скрипт автоматически рассчитывает размер burst как объём пакетов за 1 миллисекунду:

* **2 Гбит/с** → burst 250 КБ

* **5 Гбит/с** → burst 625 КБ

* **10 Гбит/с** → burst 1.25 МБ

Burst зажимается в безопасные границы:

* **Минимум**: 1500 байт (типичный размер MTU)

* **Максимум**: 10 МБ (предотвращает чрезмерную буферизацию)

## Ручная настройка командой `tc`

Если вы предпочитаете настраивать пейсинг пакетов вручную, используйте команду `tc` напрямую:

### Проверить текущий qdisc

```bash
tc qdisc show dev eth0
```

### Установить Fair Queuing с пейсингом

Замените `eth0` на имя вашего интерфейса:

```bash
sudo tc qdisc replace dev eth0 root fq maxrate 2gbit
```

### Проверить конфигурацию

```bash
tc qdisc show dev eth0
tc qdisc stat dev eth0
```

### Удалить пейсинг (вернуть по умолчанию)

```bash
sudo tc qdisc del dev eth0 root
```

### Использование Token Bucket Filter (TBF) вместо

Для более гранулярного контроля используйте TBF вместо FQ:

```bash
sudo tc qdisc replace dev eth0 root tbf rate 2gbit burst 250000 latency 100ms
```

Где:

* `rate` = скорость пейсинга пакетов (например, 2gbit, 5gbit)

* `burst` = максимальный размер burst в байтах

* `latency` = максимальная задержка в очереди до отбрасывания пакетов

## Тестирование и валидация

### Убедиться, что пейсинг активен

```bash
sysctl net.core.default_qdisc
# Должно показать: net.core.default_qdisc = fq

tc qdisc show dev eth0
# Должно показать: qdisc fq 8001: root refcnt 2 limit 10000p flows 1024 ...
```

### Тест с iperf3

iperf3 поддерживает пейсинг на основе FQ через опцию `--fq-rate`:

```bash
# Тест С пейсингом (рекомендуется)
iperf3 -c <receiver> -P 4 --time 60 --fq-rate 2gbps

# Для сравнения БЕЗ пейсинга
iperf3 -c <receiver> -P 4 --time 60
```

Ожидаемое улучшение: на 10-50% выше пропускная способность с пейсингом на длинных путях.

### Тест с perfSONAR pscheduler

pscheduler из perfSONAR также поддерживает пейсинг. Проверьте конфигурацию perfSONAR на наличие тестов с поддержкой пейсинга.

## Распространённые проблемы и устранение неполадок

### Проблема: пейсинг не применён

**Симптом**: `tc qdisc show` показывает `qdisc mq` вместо `qdisc fq`

**Решение**: убедитесь, что `/etc/sysctl.conf` содержит:

```bash
net.core.default_qdisc = fq
sysctl -p
```

Затем снова примените пейсинг с помощью `fasterdata-tuning.sh` или команды `tc`.

### Проблема: пропускная способность всё ещё низкая после пейсинга

**Причины**:

* Скорость пейсинга слишком консервативна — попробуйте увеличить на 10-20%

* Приёмник всё ещё в узком месте — проверьте, что приёмник способен держать более высокие скорости

* Проблема сетевого пути — проверьте потери пакетов с помощью `mtr` или `iperf3`

**Шаги отладки**:

1. Проверьте между теми же хостами в обратном направлении (чтобы исключить проблему только отправителя)

2. Постепенно увеличивайте скорость пейсинга шагами по 1-2 Гбит/с

3. Следите за `tc -s qdisc show dev eth0` на предмет отброшенных/задержанных пакетов

### Проблема: конфигурация пейсинга теряется после перезагрузки

**Решение**: режим apply в `fasterdata-tuning.sh` создаёт systemd-сервис для персистентности. Включите его:

```bash
sudo systemctl enable ethtool-persist.service
sudo systemctl start ethtool-persist.service
```

Проверьте:

```bash
sudo systemctl status ethtool-persist.service
tc qdisc show dev eth0
```

## Когда НЕ следует использовать пейсинг пакетов

* **Приложения с низкой задержкой и малой пропускной способностью** — пейсинг добавляет задержку

* **Чувствительные к задержке протоколы** (HFT, игры, VoIP) — избегайте пейсинга

* **Измерительные хосты** — пейсинг не следует применять к измерительным/мониторинговым хостам

* **Передачи с малой полосой** — пейсинг даёт мало выгоды ниже 1G

## Продвинутое: пейсинг для отдельных приложений

Если вам нужен более тонкий контроль, чем пейсинг на уровне хоста, приложения могут задавать скорость пейсинга через опцию socket `SO_MAX_PACING_RATE`:

```c
#include <sys/socket.h>

// В коде вашего приложения:
int pacing_rate = 2000000000;  // 2 Гбит/с в байтах в секунду
setsockopt(sockfd, SOL_SOCKET, SO_MAX_PACING_RATE,
           &pacing_rate, sizeof(pacing_rate));
```

**Требования**:

* Ядро 4.13+

* Хост настроен с `net.core.default_qdisc = fq` или `fq_codel`

* Требуются изменения в коде приложения

## Резюме

**Пейсинг пакетов необходим для DTN-узлов и высокопроизводительной передачи данных**, потому что он:

1. **Предотвращает переполнение буфера приёмника** — плавный трафик вместо всплесков

2. **Снижает потери пакетов** — устраняет снижение скорости TCP и накладные расходы на ретрансмиссии

3. **Повышает пропускную способность в 2-4 раза** — особенно на длинных путях с высокой задержкой

4. **Справедливое деление полосы** — каждый поток получает равное обращение

5. **Прост в реализации** — одна команда или вызов скрипта

**Рекомендуемая конфигурация для 10G DTN с 4 параллельными потоками**:

```bash
sudo fasterdata-tuning.sh --mode apply --target dtn --apply-packet-pacing --packet-pacing-rate 2gbps
```

**Ожидаемый результат**: пропускная способность, близкая к скорости линии, с минимальными потерями пакетов.
