# Как настроить централизованное логирование в Linux с помощью Rsyslog

Источник: [How to Set Up Centralized Logging on Linux with Rsyslog](https://betterstack.com/community/guides/logging/how-to-configure-centralised-rsyslog-server/)

Айоолува Исайя · обновлено 19 января 2026

Этот туториал описывает, как настроить централизованную службу логирования в Linux с помощью [Rsyslog](https://www.rsyslog.com/). Такая централизованная конфигурация полезна при администрировании логов с нескольких серверов, поскольку вам не придётся входить на каждый сервер для просмотра его логов — особенно если серверов огромное количество.

При централизованном решении для логирования хост-сервер будет получать записи логов от всех клиентских серверов, чтобы их можно было мониторить, анализировать и архивировать в одном месте. Обычно [облачные решения для управления логами](https://betterstack.com/log-management) предпочитают за простоту настройки, богатый набор функций и прозрачные цены, но самостоятельные (self-hosted) решения в некоторых случаях могут быть более подходящим вариантом.

Rsyslog — хороший и популярный выбор для организации централизованного логирования, поскольку он предлагает впечатляющую производительность (до миллиона записей логов в секунду), доставку сообщений по TCP, SSL и TLS, многопоточность и высоко настраиваемую фильтрацию и форматы вывода. Он также может пересылать входящие записи логов в другие пункты назначения после применения к ним определённых преобразований.

**Прочитав эту статью, вы узнаете, как:**

- Настроить центральный сервер логирования, получающий все сообщения логов от различных клиентов.
- Настроить Rsyslog на каждом клиентском сервере так, чтобы он пересылал все свои логи на сервер логирования.

## Предварительные требования

Для прохождения этого туториала вам необходим доступ к двум Linux-системам. Одна из них будет выступать централизованным сервером логирования, а другая — в роли продакшн-сервиса, генерирующего логи. Пользователь без прав root с доступом `sudo` требуется на обеих системах.

Команды, показанные в этом руководстве, относятся к основанным на Debian дистрибутивам (таким как Ubuntu), но концепции остаются теми же независимо от выбранного вами дистрибутива Linux. Также учтите, что клиент и сервер не обязаны быть одним и тем же дистрибутивом, хотя в этом руководстве они изображены одинаковыми.

Для упрощения туториала трафик между обеими системами не будет шифроваться, и любой, у кого есть доступ к сети, сможет читать ваши логи. Поэтому обязательно шифруйте трафик между серверами, чтобы предотвратить это в ваших продакшн-системах.

## Шаг 1 — Поиск приватного IP-адреса централизованного сервера (опционально)

Прежде всего, вам нужно выяснить приватные IPv4-адреса хост-сервера, если вы не собираетесь передавать свои логы через интернет. В противном случае вы можете использовать публичный IP-адрес сервера.

Подключитесь к серверу через `ssh`. Замените плейсхолдеры в команде ниже соответствующим образом.

```text
ssh <username>@<your_server_public_ip_address>
```

После подключения к хост-серверу вы можете определить его приватный IP-адрес, выполнив команду `hostname`, как показано ниже:

```text
hostname -I
```

Вы должны получить вывод, который выглядит так:

```text
0.0.0.0 2a01:4f8:c010:5f07::1
```

Первое значение вывода (`0.0.0.0`) — это приватный IPv4-адрес сервера. На некоторых системах он может совпадать с публичным IP-адресом.

Теперь вы можете перейти к следующему шагу, где мы проверим, что Rsyslog установлен и включён как на клиенте, так и на сервере.

## Шаг 2 — Установка и включение службы Rsyslog

В этом разделе мы проверим статус службы Rsyslog и на клиенте, и на хост-сервере. Проверить, установлен ли Rsyslog в системе, можно командой ниже:

```text
rsyslogd -v
```

Если всё хорошо, вы должны получить следующий вывод:

```text

        PLATFORM (lsb_release -d):
```

Поскольку Ubuntu уже предустанавливает `rsyslog`, вы можете сразу подтвердить его активный статус командой ниже:

```text
systemctl status rsyslog
```

Вы должны увидеть следующий вывод:

```text

```

Если он не активен, запустите службу командой ниже:

```text
sudo systemctl start rsyslog
```

## Шаг 3 — Настройка хост-сервера на приём логов

Теперь, когда мы подтвердили, что Rsyslog установлен и работает на хост-сервере, откройте его конфигурационный файл для редактирования в текстовом редакторе, например `nano`:

```text
sudo nano /etc/rsyslog.conf
```

Файл имеет следующее содержимое (сокращено для краткости):

```text
#################
#### MODULES ####
#################

module(load="imuxsock") # provides support for local system logging
#module(load="immark")  # provides --MARK-- message capability

# provides UDP syslog reception
#module(load="imudp")
#input(type="imudp" port="514")

# provides TCP syslog reception
#module(load="imtcp")
#input(type="imtcp" port="514")

# provides kernel logging support and enable non-kernel klog messages
module(load="imklog" permitnonkernelfacility="on")

###########################
#### GLOBAL DIRECTIVES ####
###########################

. . .
```

Найдите следующие закомментированные строки:

```text
# provides UDP syslog reception
#module(load="imudp")
#input(type="imudp" port="514")

# provides TCP syslog reception
#module(load="imtcp")
#input(type="imtcp" port="514")
```

Эти строки загружают модули `imudp` и `imtcp` для прослушивания указанных портов UDP или TCP (оба — порт `514`). Вы можете прослушивать оба порта, если хотите, или поменять номер порта по своему усмотрению.

Для этого туториала мы будем использовать только TCP-соединение. Включите его, раскомментировав следующие две строки кода (удалите префикс `#`):

```text
module(load="imtcp")
input(type="imtcp" port="514")
```

Сохраните изменения в файле `/etc/rsyslog.conf` и закройте редактор.

Если в вашей системе есть конфигурация межсетевого экрана, вы также должны разрешить новую TCP-службу на указанном порту с помощью `ufw`. Требуется `sudo`, так как это меняет правила межсетевого экрана.

```text
sudo ufw allow 514/tcp
```

После выполнения команды выше межсетевой экран не будет мешать трафику Rsyslog. Перезапустите службу `rsyslog`, чтобы применить новую конфигурацию:

```text
sudo systemctl restart rsyslog.service
```

Наконец, вы можете проверить, что TCP-порт 514 открыт, с помощью утилиты `ss`. `sudo` требуется, так как эта утилита читает сокеты:

```text
sudo ss -tulnp | grep "rsyslog"
```

Вот краткое пояснение параметров `ss`, использованных выше:

- `-u`: показать UDP-сокеты.
- `-t`: показать TCP-сокеты.
- `-l`: показать только слушающие сокеты.
- `-n`: не преобразовывать номер порта в человекочитаемое имя службы.
- `-p`: показать процесс, использующий сокет.

Вывод `ss` фильтруется через `grep`, который печатает только строки, содержащие `rsyslog`:

```text
tcp    LISTEN  0       25                  0.0.0.0:514            0.0.0.0:*      users:(("rsyslogd",pid=440497,fd=5))
tcp    LISTEN  0       25                     [::]:514               [::]:*      users:(("rsyslogd",pid=440497,fd=6))
```

Вывод выше показывает, что служба Rsyslog уже слушает порт 514.

## Шаг 4 — Настройка места хранения удалённых логов

По умолчанию все логи, полученные с TCP-порта 514, будут смешиваться в каталоге `/var/log` с системным файлом логов. Обычно это нежелательное поведение, поскольку оно смешивает все удалённые логи с локальными логами хост-сервера, что затрудняет их последующий поиск и фильтрацию. Чтобы предотвратить такое поведение, нужно отредактировать конфигурацию Rsyslog.

Снова откройте файл `/etc/rsyslog.conf` в вашем текстовом редакторе и добавьте следующие строки в начало файла:

```bash
$template RemoteLogs,"/var/log/%HOSTNAME%/%PROGRAMNAME%.log"
*.* ?RemoteLogs
& ~
```

Директива `$template RemoteLogs` указывает Rsyslog хранить все входящие записи логов в месте, определённом третьим параметром. В нашем случае удалённые логи продолжат храниться в каталоге `/var/log`, но у каждого клиента будет свой подкаталог с именем, соответствующим hostname клиента. Этот подкаталог будет хранить каждую запись лога в файле, соответствующем клиентской программе, которая её сгенерировала.

В следующей строке директива `*.* ?RemoteLogs` применяет правило конфигурации `RemoteLogs` ко всем средствам (facilities) со всеми уровнями приоритета (другими словами, ко всем логам). Наконец, директива `& ~` определяет, что Rsyslog прекращает обработку ввода лога после его сохранения в файл, определённый в предыдущих строках. Без этой строки конфигурация по умолчанию перезапишет предыдущее правило.

Сохраните файл, затем перезапустите службу `rsyslog` с помощью `systemctl`:

```text
sudo systemctl restart rsyslog.service
```

На этом этапе ваш сервер Rsyslog полностью настроен на приём логов от любого количества удалённых клиентов. Вам стоит рассмотреть монтирование каталога `/var/log` в отдельный раздел от того, на котором расположена хост-система, чтобы входящие логи не заполняли хранилище хост-сервера.

## Шаг 5 — Пересылка логов с Rsyslog-клиента

В этом разделе мы настроим наш Rsyslog-клиент на пересылку всех его логов на центральный сервер Rsyslog. Прежде всего, вы должны подключиться к вашему клиентскому серверу через `ssh`:

```text
ssh <username>@<your_server_ip_address>
```

После успешного входа отредактируйте конфигурацию Rsyslog по умолчанию в `/etc/rsyslog.d/50-default.conf` в текстовом редакторе (`sudo` требуется для права записи):

```text
sudo nano /etc/rsyslog.d/50-default.conf
```

Добавьте директиву `*.* @@<your_rsyslog_server_ip_address>:514` новой строкой в начало файла. Обязательно замените плейсхолдер на фактический IPv4-адрес сервера, который вы получили на шаге 1.

```text
#  Default rules for rsyslog.
#
#                       For more information see rsyslog.conf(5) and /etc/rsyslog.conf

*.* @@0.0.0.0:514

#
# First some standard log files.  Log by facility.
#
auth,authpriv.*                 /var/log/auth.log
*.*;auth,authpriv.none          -/var/log/syslog
#cron.*                         /var/log/cron.log
#daemon.*                       -/var/log/daemon.log
kern.*                          -/var/log/kern.log
#lpr.*                          -/var/log/lpr.log
mail.*                          -/var/log/mail.log
#user.*                         -/var/log/user.log
```

Добавленная вами выше директива определяет, что служба Rsyslog должна отправлять все facilities со всеми уровнями приоритета (другими словами, все логи) на IP-адрес (`0.0.0.0` в примере выше) централизованного сервера на TCP-порт 514. Если вы настроите эту директиву с одним `@` вместо `@@`, то она будет пересылать логи на UDP-порт.

Обратите внимание, что синтаксис `*.*` определяет, что все записи логов на сервере должны пересылаться. Если вы хотите пересылать только определённые логи, вы можете указать имя службы вместо `*`, например `cron.* @@0.0.0.0:514` или `apache2.* @@0.0.0.0:514`. Вы также можете пересылать логи более чем на один сервер:

```text
*.* @@0.0.0.0:514

*.* @@192.168.122.235

cron.* @@192.168.122.237:514
```

После сохранения изменений в файле перезапустите службу `rsyslog`, чтобы применить новую конфигурацию:

```text
sudo systemctl restart rsyslog.service
```

На этом этапе ваш Rsyslog-клиент полностью настроен на отправку своих логов на централизованный сервер Rsyslog.

## Шаг 6 — Тестирование вашей конфигурации

Теперь, когда вы настроили и Rsyslog-клиент, и централизованный сервер, давайте проверим, что наши изменения возымели желаемый эффект. Создайте запись лога на клиенте вручную с помощью команды `logger`:

```text
logger 'test from client'
```

После этого подтвердите, что запись присутствует в файле `/var/log/syslog`, с помощью команды `tail`:

```text
sudo tail /var/log/syslog
```

Вы должны увидеть следующее сообщение ближе к концу вывода:

```text
Feb  9 22:17:42 ubuntu-20-04 root: test from client
```

Теперь переключитесь на централизованный сервер Rsyslog и посмотрите содержимое каталога `/var/log`:

```text
ls /var/log
```

Вы должны увидеть каталог, соответствующий hostname клиентской системы. В этом примере hostname клиентского сервера — `ubuntu-20-04`, и вы можете наблюдать каталог `ubuntu-20-04` в выводе ниже.

```text
alternatives.log  btmp                   dpkg.log    lastlog        ubuntu-2gb-nbg1-1/          wtmp
apache2/          cloud-init.log         faillog     private/       ubuntu-advantage.log
apt/              cloud-init-output.log  journal/    syslog         ubuntu-advantage-timer.log
auth.log          dist-upgrade/          kern.log    syslog.1       ufw.log
bootstrap.log     dmesg                  landscape/  ubuntu-20-04/  unattended-upgrades/
```

Просмотрите последние 10 строк файла `root.log` в этом подкаталоге:

```text
sudo tail /var/log/<your_client_hostname>/root.log
```

Вы должны увидеть ту же запись лога, что наблюдалась на клиентском сервере:

```text
2022-02-09T22:17:42+00:00 ubuntu-20-04 root: test from client
```

На этом этапе ясно, что ваша конфигурация Rsyslog клиент-сервер работает, как ожидалось.

## Заключение и следующие шаги

В этом туториале вы создали централизованную службу логирования с помощью Rsyslog. Мы начали с обсуждения ценности, которую даёт централизованная служба логирования, затем настроили хост-сервер Rsyslog, который будет хранить все записи логов отдельных клиентов. После этого мы настроили клиентский сервер на пересылку его логов на центральный сервер и протестировали нашу конфигурацию, подтвердив, что она работает корректно.

Теперь вы готовы **пересылать логи на централизованный сервер с любого количества клиентов**. Чтобы гарантировать, что записи логов каждого клиента хранятся в собственном каталоге, убедитесь, что hostname каждого клиента уникален. Также не забудьте применять [ротацию логов](/community/guides/logging/how-to-manage-log-files-with-logrotate-on-ubuntu-20-04/) на хост-сервере, чтобы предотвратить разрастание файлов логов и автоматически удалять логи старше определённого количества дней или недель.

Для получения дополнительных материалов о Rsyslog узнайте, как [собирать, обрабатывать и отправлять данные логов](/community/guides/logging/rsyslog-explained/).

Спасибо за чтение, и удачного логирования!
