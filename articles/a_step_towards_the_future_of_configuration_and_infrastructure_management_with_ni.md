Maarten Hoogendoorn · 8 июня 2016 · 19 мин

Недавно я экспериментировал с экосистемой Nix. Она предлагает интересную и более интегрированную альтернативу традиционным системам управления конфигурацией и инфраструктурой, таким как Puppet, (Docker) контейнеры и Terraform. Я изучил Nix, nixpkgs, NixOS и NixOps. Nix — это чистый функциональный язык управления пакетами, цель которого — сделать процесс упаковки воспроизводимым. Nixpkgs — это набор курируемых пакетов, которые можно установить, описанных на языке Nix. Nixpkgs можно поверх любого современного дистрибутива Linux. На OS X его можно использовать как [альтернативу homebrew](http://ariya.ofilabs.com/2016/05/nix-as-os-x-package-manager.html). [Документация Nix](https://nixos.org/nix/download.html) содержит инструкции по установке на любой дистрибутив Linux и OS X. NixOS — это дистрибутив Linux, основанный на nixpkgs, а NixOps — инструмент для развертывания NixOS на других (виртуальных) машинах.

Мы начнём со сравнения Nix с некоторыми альтернативами, после чего я разберу пример того, как настроить локальный кластер marathon. Завершим пост выводами.

### Nix против конвергентных систем управления конфигурацией против Docker

Конвергентные системы управления конфигурацией (Converging Configuration Management Systems, CCMS), такие как Puppet, Chef и Ansible, работают, изменяя систему до соответствия желаемому состоянию, например, добавляя или удаляя пакеты или файлы. Типичная проблема, с которой я сталкивался в прошлом, — удаление пакетов или файлов не происходит автоматически, когда вы убираете инструкцию «установи этот пакет» из кода CCMS. Вам нужно явно сказать CCMS удалить пакет, привести систему к конвергентному состоянию, а затем удалить команду удаления из кода CCMS. К другим проблемам относится то, что идентичные машины, на которых CCMS запускался в два разных момента времени, вполне могут оказаться в разном состоянии, если вы не позаботились о предотвращении этого, например, фиксацией (pinning) номеров версий. Заметьте, что предотвратить это возможно — просто требуется дополнительная дисциплина и усилия.

![Модель сборки CCMS — Шаг в будущее управления конфигурацией и инфраструктурой с Nix](/images/049d6449c9f191f92d6aaa69e2f59514.png)

_Начните с базового образа, запустите CCMS, чтобы применить изменения на каждой VM. Если не принять особых мер для предотвращения расхождения, машины со временем могут разойтись и прийти в разные состояния._

Это не только делает подготовку (provisioning) потенциально расходящейся — откат к предыдущей версии нетривиален: вам нужно отменить изменения, написав ещё больше кода.

![Модель развёртывания CCMS — Шаг в будущее управления конфигурацией и инфраструктурой с Nix](/images/bbf52b00a3c7c0288b2ed248e15cd8af.png)

_Развёртывание CCMS состоит из запуска CCMS на машинах с внесением в них изменений. После внесения изменения откат к предыдущей версии нетривиален._

Существуют различные обходные пути, например использование «золотых образов» (golden images), которые вы собираете один раз с помощью CCMS. Когда захотите обновить машины, вы снова начнёте с этого золотого образа и снова запустите CCMS.

Docker решает эти проблемы, используя «золотой образ» как свой modus operandi по умолчанию и слои файловой системы. Рассмотрим следующий Dockerfile:

```dockerfile
FROM ubuntu
# ...
RUN apt-get install -yq gcc
RUN apt-get install -yq vim mc
RUN apt-get install -yq big package
RUN some-expensive-operation
# ...
```

Каждая строка в этом Dockerfile создаёт новый слой файловой системы. Если вы больше не хотите, чтобы пакет `mc` был установлен, вы можете просто изменить строку, в которой устанавливается этот пакет, пересобрать образ — и его нет! Недостаток в том, что при изменении слоя файловой системы все зависящие слои должны быть пересобраны, хотя вы как человек знаете, что изменение вообще не должно влиять на зависящие слои.

Новый docker-файл выглядит так:

```dockerfile
FROM ubuntu
# ...
RUN apt-get install -yq gcc
RUN apt-get install -yq vim
RUN apt-get install -yq big package
RUN some-expensive-operation
```

![Модель сборки Docker — Шаг в будущее управления конфигурацией и инфраструктурой с Nix](/images/373edae72e2c06de12e756dd42b8f438.png)

_Docker предлагает модель с ветвлением, но без слияний. Если вы измените Dockerfile посередине, все зависящие слои придётся пересобрать._

Развёртывание состоит из скачивания (pull) правильного образа контейнера из registry и запуска контейнера. Откат к предыдущей версии — это просто вопрос скачивания и запуска корректно помеченной версией вашего образа контейнера.

![Модель развёртывания Docker — Шаг в будущее управления конфигурацией и инфраструктурой с Nix](/images/a86bc4b5096e869f3edf426dc0d126d6.png)

_Docker обеспечивает идентичные среды выполнения, разделяя сборку сервиса и его развёртывание. Сначала контейнер собирается из `Dockerfile`, после чего разные машины могут скачать его из registry. В итоге обе запускают ровно ту же версию ПО._

NixOS делает вещи иначе. Вы можете настроить состояние системы, написав «nix-выражение» (nix expression) — описание того, как система должна выглядеть.

Как я упоминал во введении, в Nix есть только чистые функции. Это означает, что функция всегда возвращает один и тот же результат для одинаковых параметров. Функция `f(x) = x+1` чистая, а `g(x)=x+time_of_day()` — нет.

Пакеты в nixpkgs и ваша конфигурация системы реализованы как чистые функции. Следовательно, сборка системы дважды из одного и того же входа даёт ровно то же состояние.

![Модель сборки Nix — Шаг в будущее управления конфигурацией и инфраструктурой с Nix](/images/894b6eba15b150c8dba30a24ca1698c9.png)

_Выражения в Nix — чистые функции. Поэтому сборка одного и того же выражения на двух разных машинах даёт идентичное состояние._

Из этого следуют интересные последствия! Пусть есть два определения на рисунке ниже: если вы соберёте `Expression 1`, а затем `Expression 2`, которые зависят от одного общего пакета `P2`, то можно просто переиспользовать пакет `P2`; его пересборка дала бы ровно тот же пакет.

![Модель развёртывания Nix — Шаг в будущее управления конфигурацией и инфраструктурой с Nix](/images/c665c00c6fcb84bc051763e2e6034000.png)

_Развёртывание в Nix состоит из написания выражения, порождающего граф зависимостей. Любая уже присутствующая зависимость может и будет использоваться совместно._

Здесь два `P3`. Они представляют разные версии одного пакета. `P3`, на который ссылается `Expression 1`, — более старая версия, чем та, на которую ссылается `Expression 2`.

Nix предлагает атомарное развёртывание новой версии конфигурации системы, используя тот факт, что обновление симлинков — атомарная операция в UNIX. Есть глобальный симлинк, указывающий на некоторое выражение, моделирующее конфигурацию системы. Мы разберём детали этого далее в посте.

Суть всего этого в том, что Nix делает откаты тривиальными: это просто вопрос обновления одного симлинка. В нашем примере это означает, что откат к `Expression 1` сделает `P1` недоступным (но не удалит его!) и откатит `P3` на старую версию.

Если спустя какое-то время `Expression 1` сочтут больше не нужным, его корень сборки мусора (Garbage Collection root) можно удалить. Запустив nix-collect-garbage после удаления этого GC-корня, все ненужные зависимости — в нашем примере `P1` и старый `P3` — будут собраны и удалены.

### NixOps против Terraform

NixOps строится поверх NixOS и предлагает полностью интегрированную среду для определения (виртуальных) машин и ПО, которое должно быть на них установлено.

Документация Terraform гласит:

> _«Terraform — это не инструмент управления конфигурацией, и он позволяет существующим инструментам сосредоточиться на их сильных сторонах: начальной загрузке и инициализации ресурсов»_ [(источник)](https://www.terraform.io/intro/vs/chef-puppet.html)

NixOps предлагает это — и больше. Он управляет изменениями как в инфраструктуре, так и в установленном ПО. Это комбинация инструмента управления конфигурацией и инструмента управления инфраструктурой.

Мы покажем пример того, как работает NixOps, в примере ниже.

### Дополнительные компоненты

Когда вы управляете системой с помощью CCMS, ваша инфраструктура обычно состоит из VM с каким-то дистрибутивом Linux и репозиторием ваших CCM, использующим внешние библиотеки для управления ПО на VM.

Если вы используете Docker, вы меньше зависите от возможностей, предоставляемых дистрибутивом ОС. Как показывает, например, CoreOS, достаточно небольшой базовой операционной системы с базовыми утилитами. Rancher доводит это до ещё более экстремального уровня: единственное назначение дистрибутива Linux — запускать Docker-контейнеры, которые управляют самой системой. Однако инструмент для управления самими контейнерами всё равно нужен.

Используя Nix, nixpkgs и NixOps, мы можем использовать тот же механизм абстракции для работы одновременно с инфраструктурой, установленным ПО и его конфигурацией.

### Сравнение CCMS, Docker и Nix

Таблица ниже содержит грубое сравнение CCMS, Docker и Nix.

  | CCMS | Docker | Nix
---|---|---|---
Нет расхождения между машинами | С усилиями | Безопасно | Безопасно
Воспроизводимые сборки | С усилиями | С усилиями | Да
Откат | С усилиями | Да | Да
Компоненты | ОС + CCMS | ОС + Docker + менеджер контейнеров | Nix
Инкрементальные сборки | «Золотой образ» | Линейная история | Граф зависимостей
Сложность использования | Сложнее | Просто | Сложнее

### Пример: развёртывание кластера Mesos и Marathon

Если вы хотите запустить примеры сами (как на Linux, так и на OS X), сначала установите Nix с [их страницы загрузки](https://nixos.org/nix/download.html). Учтите, что Nix трогает файлы только в /nix, поэтому удаление Nix — это просто вопрос удаления всех этих файлов.

Для подготовки нескольких машин с помощью Nix мы можем использовать NixOps. После установки Nix NixOps можно установить, выполнив nix-env -i nixops. Убедитесь, что у вас установлен VirtualBox и создана host-only-сеть с именем `vboxnet0`, а также сеть NAT по умолчанию. Инструкции по тому, как сделать это на OSX, можно найти [здесь](http://christophermaier.name/blog/2010/09/01/host-only-networking-with-virtualbox).

_Замечание: в следующем посте мы глубже погрузимся в язык Nix и препарируем код ниже. Пока просто бегло взгляните на код._

```nix
let
  # Двоеточие означает, что это функция с аргументом с именем id.
  makeMaster = id: {
    name = "mesos-master-${toString id}";
    value = { config, pkgs, lib, nodes, ... }: {
      deployment.targetEnv = "virtualbox";
      deployment.virtualbox.memorySize = 512;
      deployment.virtualbox.headless = true;
      networking.firewall.enable = false;
      services.zookeeper = {
        enable = true;
        id = id;
        servers = let
            zk_servers = map zk_server_line masterServers;
            zk_server_line = zk: (let
                zkId = toString nodes.${zk.name}.config.services.zookeeper.id;
              in "server.${zkId}=${zk.name}:2888:3888");
          in
            builtins.concatStringsSep "\n"  zk_servers;
      };
      services.mesos.master = {
        enable = true;
        zk = mesosZkString;
        quorum = (nrMasterServers / 2 ) + 1; # Гарантировать кворум не менее половины + 1.
      };

      services.marathon = {
        enable = true;
        zookeeperHosts = builtins.map (s: s.name + ":2181") masterServers;
        user = "root";
      };
    };
  };
  makeSlave = id: {
    name = "mesos-slave-${toString id}";
    # Итак, 'value' — это функция, принимающая на вход набор атрибутов (Dictionary в терминах python) и возвращающая новый набор атрибутов.
    value = { config, pkgs, lib, ... }: {
      deployment.targetEnv = "virtualbox";
      deployment.virtualbox.memorySize = 1024 * 2;
      deployment.virtualbox.headless = true;
      networking.firewall.enable = false;
      virtualisation.docker.enable = true;
      services.mesos.slave = {
        enable = true;
        withDocker = true;
        master = mesosZkString;
      };
    };
  };
  nrMasterServers = 3;
  nrSlaveServers = 2;
  # Это порождает список [ { name = "mesos-master-0", value =  } { name = "mesos-master-1”; value =  } ]
  masterServers = builtins.genList makeMaster nrMasterServers;
  slaveServers = builtins.genList makeSlave nrSlaveServers;
  mesosZkString = let
                   zkServers = builtins.concatStringsSep "," (builtins.map (s: s.name + ":2181") masterServers);
                  in
                    "zk://${zkServers}/mesos";
in
  { network.description = "Marathon test"; }
    // builtins.listToAttrs masterServers
    // builtins.listToAttrs slaveServers
# Функция listToAttrs строит набор атрибутов из списка наборов атрибутов вида { name = "attr_name"; value = "attr_value"; }. Она возвращает набор { attr_name = "attr_value" }
```

Каждый master-сервер использует 512 МБ RAM, каждый slave — 2 ГБ. Текущая конфигурация — три master и два slave, то есть 5,5 ГБ. Минимальная конфигурация — один master и один slave, что займёт 2,5 ГБ RAM; вы можете установить nrMasterServers и nrSlaveServers равными 1 в файле `marathon.nix`, если у вас нет 5,5 ГБ.

Ваш `marathon.nix` готов? Создадим развёртывание с именем marathon, выполнив:

```text
nixops create -d marathon marathon.nix
(out) created deployment ‘b8393c45-2673-11e6-9e82-208984d3285c’
(out) B8393c45-2673-11e6-9e82-208984d3285c’
```

Это генерирует уникальный ID для идентификации созданного развёртывания / стека.

Чтобы реально создать VM VirtualBox и подготовить их, выполните:

```text
nixops deploy -d marathon
```

ЗАМЕЧАНИЕ: время от времени это падает с ошибкой «unable to active new configuration», вызванной некорректно запущенным гостевым драйвером virtualbox. Если это произошло, можно просто прервать (CTRL+C) nixops и попробовать развернуть снова. У меня всегда работало со второй попытки. Эти сообщения об ошибке я видел только с бэкендом virtualbox. С GCE проблем не было.

Если вы уничтожите это развёртывание (выполнив `nixops destroy -d marathon`) и развернёте заново, вы увидите, что пересобрать нужно лишь очень малую часть конфигурации системы: ту, что содержит динамические настройки вроде IP-адресов, а именно определения сервисов, зависящие от IP-адресов, и общую конфигурацию ОС, использующую эти определения сервисов.

```bash
export NGINX_IP=`nixops export | jq -r ".[].resources[\"$NGINX_HOST\"].privateIpv4"`
```

Отлично, теперь мы знаем, на каком slave и на каком порту работает экземпляр nginx. Посмотрим, сможем ли мы прочитать с него.

```text
curl $NGINX_IP:$NGINX_PORT
(out)    &lt;html&gt;
(out)        &lt;body&gt;
(out)        &lt;h1&gt; Hello brave new world! &lt;/h1&gt;
(out)        &lt;/body&gt;
(out)    &lt;/html&gt;
```

Ура, успех!

### Заключение

Как вы видели, всего 65 строк Nix-выражения достаточно, чтобы описать сколь угодно большие кластеры marathon. Это свидетельство силы абстракции, предлагаемой инструментами Nix. Однако у использования Nix есть недостатки: NixOS — относительно молодой дистрибутив, пока не поддерживаемый техническим гигантом. Впрочем, то же можно сказать о дистрибутивах вроде Gentoo или Debian. [Есть несколько компаний, использующих NixOS в продакшене](https://nixos.org/wiki/Nix\(OS\)_in_production). Кто-то на Reddit предполагает, что Nix [используется Intel](https://www.reddit.com/r/linux/comments/3uwjxq/anyone_using_nixos_in_production/cxiju3w) для проверки их SSD. Со временем NixOS имеет потенциал вырасти в один из больших дистрибутивов, и, полагаю, осталось лишь подождать, пока компании начнут предлагать поддержку Nix.

Сейчас я предлагаю взглянуть на Nix и его модель. Я верю, что это следующий шаг в эволюции управления компьютерными системами.
