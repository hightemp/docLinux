## Обзор

Как прелюдию к этой серии, в этой статье я исследую, как выполняется демультиплексирование на основе протокола OSI-уровня 4 (транспортного) для локально принятых сетевых пакетов в ядре Linux. Хотя этот механизм напрямую не связан с сокетами, он смежная тема, представляющая собой «клей» между OSI-уровнями 3 и 4 на пути приёма пакетов. Сообщение протокола 4-го уровня, инкапсулированное в сетевом пакете (например, _сегмент TCP_ или _дейтаграмма UDP_), задаётся полем в заголовке протокола 3-го уровня. В случае IPv4 это поле _Protocol_ (8 бит) в [заголовке IPv4](https://en.wikipedia.org/wiki/IPv4#Header "https://en.wikipedia.org/wiki/IPv4#Header"), а в случае IPv6 — поле _Next Header_ (8 бит) в [заголовке IPv6](https://en.wikipedia.org/wiki/IPv6_packet "https://en.wikipedia.org/wiki/IPv6_packet"). Фактические числа, используемые здесь для идентификации L4-протоколов, одинаковы в IPv4 и в IPv6¹), и поддерживаются _IANA_, которая предоставляет официальный список [номеров протоколов](https://www.iana.org/assignments/protocol-numbers/protocol-numbers.xhtml "https://www.iana.org/assignments/protocol-numbers/protocol-numbers.xhtml"). Википедия предоставляет тот же [список номеров IP-протоколов](https://en.wikipedia.org/wiki/List_of_IP_protocol_numbers "https://en.wikipedia.org/wiki/List_of_IP_protocol_numbers"). Этот список также можно найти в файле `/etc/protocols` в вашей Linux-системе, который используется такими программными компонентами, как _glibc_ и некоторые сетевые утилиты userspace. Ядро Linux реализует таблицы поиска, в которых регистрируются функции-обработчики приёма L4-протоколов, а номера L4-протоколов, указанные в L3-заголовках принятых сетевых пакетов, используются как индексы массивов в этих таблицах для выбора правильной функции-обработчика.

Как видите, вскоре после приёма сетевого пакета уже происходит некоторый шаг демультиплексирования на L2 на основе поля _EtherType_ в заголовке кадра Ethernet, который выбирает правильную функцию-обработчик приёма L3-протокола для пакета. Принципы этого шага демультиплексирования схожи с теми, что я описываю здесь, но не входят в рамки этой статьи. Рисунок 1 показывает только пути приёма L3 протоколов IPv4 и IPv6. В случае IPv4 вызывается либо функция-обработчик приёма `[ip_rcv()](https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/ip_input.c#L560 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/ip_input.c#L560")`, либо её list-аналог `[ip_list_rcv()](https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/ip_input.c#L642 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/ip_input.c#L642")`²), а в случае IPv6 — функция-обработчик приёма `[ipv6_rcv()](https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/ip6_input.c#L302 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/ip6_input.c#L302")` или её list-аналог `[ipv6_list_rcv()](https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/ip6_input.c#L323 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/ip6_input.c#L323")`. Таким образом, оба пути приёма — две независимые реализации, которые, однако, семантически примерно выполняют те же шаги: пропуск принимаемого пакета через _Netfilter Prerouting hook_³) и затем выполнение маршрутизационного поиска на основе IP-адреса назначения пакета. В описываемом здесь случае маршрутизационный поиск возвращает результат типа `[RTN_LOCAL](https://elixir.bootlin.com/linux/v6.12/source/include/uapi/linux/rtnetlink.h#L256 "https://elixir.bootlin.com/linux/v6.12/source/include/uapi/linux/rtnetlink.h#L256")`, который определяет, что пакет должен быть принят локально⁴). Поэтому в случае IPv4 вызывается функция `[ip_local_deliver()](https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/ip_input.c#L242 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/ip_input.c#L242")`, а в случае IPv6 — функция `[ip6_input()](https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/ip6_input.c#L488 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/ip6_input.c#L488")`. Тем самым пакет проходит через IPv4- или IPv6-вариант _Netfilter Input hook_. Затем в случае IPv4 вызывается функция `[ip_protocol_deliver_rcu()](https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/ip_input.c#L187 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/ip_input.c#L187")`, а в случае IPv6 — функция `[ip6_protocol_deliver_rcu()](https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/ip6_input.c#L361 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/ip6_input.c#L361")`. Именно здесь исследуется поле _protocol_ (заголовок IPv4) или поле _Next Header_ (заголовок IPv6) и происходит демультиплексирование L4-протоколов. Рисунок 1 здесь просто показывает функции-обработчики приёма L4 наиболее заметных L4-протоколов — TCP и UDP. В каждом из этих обработчиков приёма выполняется _поиск сокета_ (socket lookup), чтобы найти подходящий сокет назначения для принятого пакета. Я подробно описываю это во 2-й и 3-й статьях серии: [Сокеты в ядре Linux — Часть 2: поиск UDP-сокета на приёме](https://thermalcircle.de/doku.php?id=blog:linux:sockets_in_the_linux_kernel_2_udp_socket_lookup_on_rx#articles_of_the_series "blog:linux:sockets_in_the_linux_kernel_2_udp_socket_lookup_on_rx") и [Сокеты в ядре Linux — Часть 3: поиск TCP-сокета на приёме](https://thermalcircle.de/doku.php?id=blog:linux:sockets_in_the_linux_kernel_3_tcp_socket_lookup_on_rx "blog:linux:sockets_in_the_linux_kernel_3_tcp_socket_lookup_on_rx").

## Таблица L4-демультиплексирования IPv4

![](/images/5bb49953f6f786407841de326a003fa3.png) Рисунок 2: глобальная таблица демультиплексирования L4-протоколов для IPv4.

В ядре объявляется глобальный массив с именем `[inet_protos](https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/protocol.c#L27 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/protocol.c#L27")`, который представляет таблицу L4-демультиплексирования для IPv4 — см. рисунок 2. Это массив указателей на экземпляры `[struct net_protocol](https://elixir.bootlin.com/linux/v6.12/source/include/net/protocol.h#L37 "https://elixir.bootlin.com/linux/v6.12/source/include/net/protocol.h#L37")` фиксированного размера `[MAX_INET_PROTOS](https://elixir.bootlin.com/linux/v6.12/source/include/net/protocol.h#L34 "https://elixir.bootlin.com/linux/v6.12/source/include/net/protocol.h#L34")` (256) элементов. `[struct net_protocol](https://elixir.bootlin.com/linux/v6.12/source/include/net/protocol.h#L37 "https://elixir.bootlin.com/linux/v6.12/source/include/net/protocol.h#L37")` определена так:

```c
struct net_protocol {
   int            (*handler)(struct sk_buff *skb);
   int            (*err_handler)(struct sk_buff *skb, u32 info);
   unsigned int   no_policy:1,
                  icmp_strict_tag_validation:1;
   u32            secret;
};
```

Её член — указатель на функцию с именем `handler` — должен указывать на функцию-обработчик приёма L4-протокола. Второй указатель на функцию с именем `err_handler` должен указывать на функцию-обработчик ошибок L4-протокола, которая может, например, использоваться L4-протоколом для отправки ICMP-ответов об ошибках в определённых случаях. Каждая реализация L4-протокола обязана создать и держать экземпляр `struct net_protocol` для себя и инициализировать указатели на функции соответствующими функциями-обработчиками. Функция `[inet_add_protocol()](https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/protocol.c#L32 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/protocol.c#L32")` и её аналог `[inet_del_protocol()](https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/protocol.c#L46 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/protocol.c#L46")` предоставляются для регистрации/разрегистрации этих экземпляров `struct net_protocol` в таблице демультиплексирования `inet_protos`. Для регистрации L4-протокол должен вызвать `inet_add_protocol()`, передав уже инициализированный экземпляр `struct net_protocol` и номер L4-протокола в качестве аргументов. Номер протокола используется как индекс в массиве `inet_protos[]`, и этот элемент массива устанавливается так, чтобы указывать на данный экземпляр `struct net_protocol`. Обратное происходит при вызове `inet_del_protocol()`, где указатель по указанному индексу устанавливается обратно в `NULL`.

L4-протоколы вроде TCP, UDP, ICMP и IGMP выполняют этот шаг регистрации уже на ранней фазе загрузки в функции `[inet_init()](https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/af_inet.c#L1942 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/af_inet.c#L1942")`. Функция разрегистрации для них никогда не вызывается, потому что эти протоколы — обязательные части стека TCP/IP. Рисунок 2 показывает функции-обработчики приёма (_handler_) этих протоколов. Другие L4-протоколы могут регистрироваться/разрегистрироваться позже, во время работы ядра. Например, протокол GRE зарегистрирует/разрегистрирует себя с номером протокола `[47](https://elixir.bootlin.com/linux/v6.12/source/include/uapi/linux/in.h#L56 "https://elixir.bootlin.com/linux/v6.12/source/include/uapi/linux/in.h#L56")`, когда вы загрузите/выгрузите его модуль ядра `[net/ipv4/gre.ko](https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/gre_demux.c#L204 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/gre_demux.c#L204")`⁵). Но как всё это используется на пути приёма пакетов? Как упомянуто в секции выше, демультиплексирование L4-протоколов для IPv4 происходит в функции `[ip_protocol_deliver_rcu()](https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/ip_input.c#L187 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/ip_input.c#L187")`. Значение поля _Protocol_ уже извлекается из заголовка IPv4 в вызывающей функции `[ip_local_deliver_finish()](https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/ip_input.c#L233 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/ip_input.c#L233")` и используется как индекс в таблице демультиплексирования для получения правильного экземпляра `struct net_protocol`. Затем выполняется косвенный вызов функции через указатель `handler`. Так вызывается правильная функция-обработчик приёма L4-протокола:

```c
/* simplified pseudo code */
struct net_protocol *ipprot;
ipprot = inet_protos[protocol];
if (ipprot) {
   ipprot->handler();
} else {
   icmp_send(skb, ICMP_DEST_UNREACH, ICMP_PROT_UNREACH, 0);
}
```

Как видите, если значение поля _Protocol_ в заголовке IPv4 задаёт L4-протокол, не зарегистрированный в таблице демультиплексирования, отправляется ICMP-ответ об ошибке типа _destination unreachable_ (3) с кодом _destination protocol unreachable_ (2).

**Некоторые тонкие детали, ведущие глубже в кроличью нору:**

Если вы снова посмотрите на код функции _[ip_protocol_deliver_rcu()](https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/ip_input.c#L187 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/ip_input.c#L187")_, то увидите, что _[xfrm4_policy_check()](https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/ip_input.c#L198 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/ip_input.c#L198")_ вызывается здесь при определённых условиях. Это «input policy» IPsec. Она актуальна только при расшифровке IPsec-пакета. Моя статья [Nftables — поток пакетов Netfilter и VPN/IPsec](https://thermalcircle.de/doku.php?id=blog:linux:nftables_ipsec_packet_flow "blog:linux:nftables_ipsec_packet_flow") объясняет это подробно. Если снова посмотреть на определение _[struct net_protocol](https://elixir.bootlin.com/linux/v6.12/source/include/net/protocol.h#L37 "https://elixir.bootlin.com/linux/v6.12/source/include/net/protocol.h#L37")_, то видно, что она также содержит битовое поле с битом _no_policy_. Реализации L4-протоколов могут установить (1) или сбросить (0) этот бит (кажется, большинство устанавливает его в _1_). Если бит установлен, проверка «input policy» IPsec будет пропущена здесь в этой функции для соответствующего L4-протокола. Пропуск её здесь открывает L4-протоколам возможность либо делать, либо не делать эту проверку позже в своих собственных обработчиках приёма. Это особенно актуально для UDP, где дела обстоят несколько запутанно: «input policy» IPsec должна применяться только к уже расшифрованным пакетам, а не к зашифрованным. В случае IPsec _NAT-traversal_ зашифрованные IPsec (ESP) пакеты дополнительно инкапсулируются в UDP (порт 4500). Однако принятые UDP-пакеты, зашифрованные в IPsec с _NAT-t_, проходят здесь дважды: сначала в ещё зашифрованной форме, затем второй раз в расшифрованном (и декапсулированном → режим туннеля) виде. Поэтому обработчик приёма UDP должен сам выполнять проверку «input policy» IPsec в подходящий момент. Эти детали обрабатываются в _[udp_queue_rcv_one_skb()](https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/udp.c#L2096 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv4/udp.c#L2096")_, на несколько кадров стека вызовов ниже _udp_rcv()_.

## Таблица L4-демультиплексирования IPv6

![](/images/23996ad58752035aafed522db991d52c.png) Рисунок 3: глобальная таблица демультиплексирования L4-протоколов для IPv6.

Реализация демультиплексирования L4-протоколов в IPv6 семантически очень похожа на свой аналог в IPv4. Здесь в ядре объявляется глобальный массив с именем `[inet6_protos](https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/protocol.c#L25 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/protocol.c#L25")`, который представляет таблицу L4-демультиплексирования для IPv6 — см. рисунок 3. Это массив указателей на экземпляры `[struct inet6_protocol](https://elixir.bootlin.com/linux/v6.12/source/include/net/protocol.h#L53 "https://elixir.bootlin.com/linux/v6.12/source/include/net/protocol.h#L53")` фиксированного размера `[MAX_INET_PROTOS](https://elixir.bootlin.com/linux/v6.12/source/include/net/protocol.h#L34 "https://elixir.bootlin.com/linux/v6.12/source/include/net/protocol.h#L34")` (256) элементов. `[struct inet6_protocol](https://elixir.bootlin.com/linux/v6.12/source/include/net/protocol.h#L53 "https://elixir.bootlin.com/linux/v6.12/source/include/net/protocol.h#L53")` определена так:

```c
struct inet6_protocol {
   int	(*handler)(struct sk_buff *skb);
   int	(*err_handler)(struct sk_buff *skb,
   		       struct inet6_skb_parm *opt,
   		       u8 type, u8 code, int offset,
   		       __be32 info);
   unsigned int	flags;	/* INET6_PROTO_xxx */
   u32		secret;
};
```

Её член — указатель на функцию с именем `handler` — должен указывать на функцию-обработчик приёма L4-протокола. Второй указатель на функцию с именем `err_handler` должен указывать на функцию-обработчик ошибок L4-протокола, которая может, например, использоваться L4-протоколом для отправки ICMPv6-ответов об ошибках в определённых случаях. Каждая реализация L4-протокола обязана создать и держать экземпляр `struct inet6_protocol` для себя и инициализировать указатели на функции соответствующими функциями-обработчиками. Функция `[inet6_add_protocol()](https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/protocol.c#L28 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/protocol.c#L28")` и её аналог `[inet6_del_protocol()](https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/protocol.c#L35 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/protocol.c#L35")` предоставляются для регистрации/разрегистрации этих экземпляров `struct inet6_protocol` в таблице демультиплексирования `inet6_protos`. Для регистрации L4-протокол должен вызвать `inet6_add_protocol()`, передав уже инициализированный экземпляр `struct inet6_protocol` и номер L4-протокола в качестве аргументов. Номер протокола используется как индекс в массиве `inet6_protos[]`, и этот элемент массива устанавливается так, чтобы указывать на данный экземпляр `struct inet6_protocol`. Обратное происходит при вызове `inet6_del_protocol()`, где указатель по указанному индексу устанавливается обратно в `NULL`. Но как всё это используется на пути приёма пакетов? Как упомянуто в секции выше, демультиплексирование L4-протоколов для IPv6 происходит в функции `[ip6_protocol_deliver_rcu()](https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/ip6_input.c#L361 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/ip6_input.c#L361")`. Значение поля _Next Header_ [извлекается](https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/ip6_input.c#L380 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/ip6_input.c#L380") из заголовка IPv6 и [используется как индекс](https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/ip6_input.c#L385 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/ip6_input.c#L385") в таблице демультиплексирования для получения правильного экземпляра `struct inet6_protocol`. Затем выполняется косвенный вызов функции через указатель `handler`. Так вызывается правильная функция-обработчик приёма L4-протокола:

```c
/* simplified pseudo code */
struct inet6_protocol *ipprot;
ipprot = inet6_protos[nexthdr];
if (ipprot) {
   ipprot->handler();
} else {
   icmpv6_send(skb, ICMPV6_PARAMPROB, ICMPV6_UNK_NEXTHDR, nhoff);
}
```

Как видите, если значение поля _Next Header_ в заголовке IPv6 задаёт L4-протокол, не зарегистрированный в таблице демультиплексирования, отправляется ICMPv6-ответ об ошибке типа _parameter problem_ (4) с кодом _unrecognized next header type_ (1).

**Некоторые тонкие детали, ведущие глубже в кроличью нору:**

Если снова посмотреть на код функции _[ip6_protocol_deliver_rcu()](https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/ip6_input.c#L361 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/ip6_input.c#L361")_, то видно, что _[xfrm6_policy_check()](https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/ip6_input.c#L429 "https://elixir.bootlin.com/linux/v6.12/source/net/ipv6/ip6_input.c#L429")_ вызывается здесь при определённых условиях. Это IPv6-эквивалент возможности, которую я описал в информационной врезке для IPv4 выше. Здесь она реализована на основе флага _[INET6_PROTO_NOPOLICY](https://elixir.bootlin.com/linux/v6.12/source/include/net/protocol.h#L66 "https://elixir.bootlin.com/linux/v6.12/source/include/net/protocol.h#L66")_, назначаемого члену _flags_ структуры _[struct inet6_protocol](https://elixir.bootlin.com/linux/v6.12/source/include/net/protocol.h#L53 "https://elixir.bootlin.com/linux/v6.12/source/include/net/protocol.h#L53")_, тогда как для IPv4 она основана на бите _no_policy_.
