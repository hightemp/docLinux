Фрагментация уже давно является проблемой экосистемы Linux. Сегодня существует множество дистрибутивов со своими менеджерами пакетов и своими представлениями о том, из чего состоит «базовая система». Для разработчиков приложений это утомительно: собрав пакеты под конкретные дистрибутивы и поддерживая репозитории, им приходится исправлять специфические для каждого дистрибутива ошибки. Кроме того, в отличие от мобильных платформ вроде iOS и Android, приложения в Linux работают без песочницы и имеют доступ ко всей функциональности базовой системы.

Для решения этих проблем было предложено множество самых разных решений. В этой статье мы рассмотрим Flatpak — способ распространения приложений и их запуска в ограниченной песочнице.

## Что такое Flatpak?

Flatpak — это технология сборки, распространения, установки и запуска приложений, ориентированная прежде всего на Linux-десктоп. Она позволяет приложениям поставлять зависимости вместе с собой и включать среды выполнения (runtimes), чтобы приложения не зависели от особенностей конкретного дистрибутива. Кроме того, она повышает безопасность Linux-приложений, изолируя их в песочницы.

Архитектура Flatpak-приложения показана на диаграмме ниже:

![](/images/9e50ce709f99bf128643fe7f9e0884c6.png)

Каждое Flatpak-приложение опирается на «среду выполнения» (runtime), которая содержит базовые зависимости, используемые приложениями. Эти среды выполнения общие для приложений. Несколько сред — и даже разные версии одной и той же среды — могут одновременно сосуществовать в системе. Таким образом, приложениям достаётся вполне согласованное подобие базовой системы, на которое можно положиться.

Для сборки приложений под такую среду предоставляются специальные среды, называемые SDK (Software Development Kits, наборы для разработки программного обеспечения). Они содержат такие инструменты, как компиляторы и заголовочные файлы для разработки. Если ваше приложение зависит от библиотек, не входящих в среду выполнения, вам нужно скомпилировать их вместе с приложением, используя SDK.

Кроме того, существуют «расширения» (extensions) — необязательные дополнения к средам выполнения и приложениям. Чаще всего они используются, чтобы вынести переводы и отладочную информацию из исходной среды выполнения или приложения.

Одна из целей Flatpak — повысить безопасность приложений, изолировав их друг от друга. По умолчанию Flatpak даёт очень ограниченный доступ к ресурсам хост-системы. Если это явно не запрошено, приложениям запрещено пользоваться сетью, обращаться к файлам базовой системы или общаться с сервисами вроде X, DBus или Pulseaudio. Кроме того, «порталы» (portals) позволяют давать выборочный доступ к ресурсам через высокоуровневые API.

## Установка, команды Flatpak и соглашения об именовании

Flatpak доступен в репозиториях большинства дистрибутивов. На Arch Linux и Fedora нужно установить пакет `flatpak`, чтобы получить команду `flatpak`, которая помогает устанавливать и собирать приложения.

```bash
sudo dnf install flatpak # Fedora
sudo pacman -S flatpak # Arch
```

У пользователей Ubuntu его нет в репозиториях по умолчанию, поэтому установка чуть сложнее. Сначала нужно добавить [этот PPA](https://launchpad.net/~alexlarsson/+archive/ubuntu/flatpak) в систему:

```bash
sudo add-apt-repository ppa:alexlarsson/flatpak
```

Затем можно установить пакет:

```bash
sudo apt update
sudo apt install flatpak
```

Хотя команда `flatpak` вполне может помочь вам собирать приложения, это не самый удобный способ. Есть ещё один инструмент, `flatpak-builder`, который позволяет собирать Flatpak-приложения из JSON-файла. (Мы обсудим этот инструмент позже в статье.) Установить его можно так:

```bash
sudo dnf install flatpak-builder # Fedora
sudo pacman -S flatpak-builder # Arch
sudo apt install flatpak-builder # Ubuntu
```

Теперь, чтобы устанавливать приложения или среды выполнения, нужно добавить репозитории в список remotes Flatpak. Эти remotes могут располагаться в локальном каталоге или в сети. Среды выполнения и приложения идентифицируются обратным DNS-адресом вроде `com.booleanworld.foo`. В некоторых случаях может также понадобиться указать архитектуру и «ветку» (branch) среды выполнения. Это делается с помощью разделённого слэшами триплета, например `com.booleanworld.foo/x86_64/1.3`.

Команда `flatpak` обычно добавляет ПО и репозитории для всех пользователей. Однако для экспериментов это неподходяще, поэтому мы будем использовать флаг `--user`, чтобы ограничить такие изменения текущим пользователем.

Теперь, когда основы на месте, посмотрим на некоторую теорию сборки Flatpak-приложений.

## Структура Flatpak-приложения

Когда вы пакуете приложение с Flatpak, автоматически создаётся следующая структура каталогов:

* `metadata`: этот файл содержит сведения о SDK и среде выполнения, на которых будет работать приложение, а также список ресурсов базовой системы, к которым приложению нужен доступ.
* `files`: этот каталог содержит файлы, из которых состоит приложение, включая данные приложения. Подкаталог `bin` внутри него содержит исполняемые файлы приложения.
* `export`: этот каталог содержит файлы, к которым должна иметь доступ базовая система. Примеры: [данные AppStream](https://www.freedesktop.org/wiki/Distributions/AppStream/), файл `.desktop` и иконка приложения. Все файлы, которые вы сюда помещаете, должны иметь префикс-идентификатор. Например, desktop-файл может называться `com.booleanworld.foo.desktop`.

Хотя эту структуру можно построить вручную, в этом нет необходимости. У Flatpak есть инструменты, которые помогают создать её автоматически, и для типичного проекта на autotools требуется совсем немного настройки. С проектами не на autotools обычно нужно лишь установить «префиксный» каталог в `/app`, чтобы всё заработало.

## Предварительные требования

В следующих разделах статьи приводится несколько примеров сборки Flatpak-приложений. Как мы уже говорили, приложениям нужна среда выполнения для запуска и SDK для сборки. Поэтому первый шаг — добавить репозиторий, откуда их можно взять. Мы добавим для своих нужд репозиторий, доступный на [sdk.gnome.org](https://sdk.gnome.org/).

```bash
flatpak remote-add --from gnome https://sdk.gnome.org/gnome.flatpakrepo --user
```

Для сборки примеров ниже нам нужны две среды выполнения: `org.freedesktop.Platform` и `org.gnome.Platform`, и два SDK: `org.freedesktop.Sdk` и `org.gnome.Sdk`. Здесь мы используем версии 1.6 и 3.24 сред и SDK Freedesktop и Gnome.

```bash
flatpak install --user gnome org.freedesktop.Platform/x86_64/1.6 \
                             org.freedesktop.Sdk/x86_64/1.6 \
                             org.gnome.Plaform/x86_64/3.24 \
                             org.gnome.Sdk/x86_64/3.24
```

Далее склонируйте репозиторий [flatpak-resources](https://github.com/boolean-world/flatpak-resources), содержащий все ресурсы, необходимые для прохождения этой статьи.

```bash
git clone https://github.com/boolean-world/flatpak-resources
cd flatpak-resources
```

В следующих разделах мы рассмотрим два примера сборки приложений.

## Собираем «kitten» — лёгкий «cat»

В этом разделе мы научимся собирать базовое Flatpak-приложение. Приложение — крошечная версия команды `cat` с именем `kitten`.

Сначала нужно создать структуру каталогов, которую мы обсуждали ранее. Это может сделать команда `build-init`. Ей нужно передать каталог сборки, имя приложения, а также SDK и среду выполнения (именно в этом порядке). Можно добавить и необязательное «имя ветки», но в этом примере мы его опустим.

```bash
flatpak build-init kitten-build com.booleanworld.kitten  \
                                org.freedesktop.Sdk \
                                org.freedesktop.Platform
```

Как мы уже упоминали, префиксный каталог Flatpak-приложений — это `/app`, и в нём нужно создать каталог `bin`. Когда вы хотите выполнить команду внутри каталога сборки, используйте команду `build`:

```bash
flatpak build kitten-build mkdir -p /app/bin
```

Следующий шаг — скомпилировать `kitten.c` с помощью `gcc`:

```bash
flatpak build kitten-build gcc kitten.c -o /app/bin/kitten
```

Затем можно завершить сборку с помощью `build-finish`. Командой будет `kitten`, и ей нужен доступ к файловой системе хоста (чтобы вы могли просмотреть любой файл на хост-системе). Так что завершить сборку можно со следующими параметрами:

```bash
flatpak build-finish kitten-build --filesystem=host --command=kitten
```

Теперь, если вы хотите протестировать приложение, его нужно установить. Первый шаг — экспортировать приложение в локальный репозиторий. В нашем примере каталог репозитория — `my-repo`:

```bash
flatpak build-export my-repo kitten-build
```

Далее добавим репозиторий с именем `test-repo`. Поскольку мы не используем GPG-подписи, сообщим об этом Flatpak с помощью флага `--no-gpg-verify`.

```bash
flatpak remote-add --user --no-gpg-verify test-repo my-repo
```

И, наконец, установим приложение:

```bash
flatpak install --user test-repo com.booleanworld.kitten
```

Теперь можно проверить, что всё работает, запустив так:

```bash
flatpak run com.booleanworld.kitten ~/.bashrc
```

Если вы корректно выполнили все шаги до сих пор, должно отобразиться содержимое вашего файла `.bashrc`:

![](/images/26279fd49a8087b0cd07b109b467cfe8.png)

Поздравляем с первым собранным Flatpak-приложением!

Шаги пока были довольно простыми, но команда `build-finish` заслуживает более подробного рассмотрения. Этим мы и займёмся в следующем разделе.

## Подробнее о команде «build-finish»

Одна из главных целей Flatpak — изолировать приложения в песочнице и давать лишь минимальный доступ к ресурсам хост-системы. В предыдущем примере мы разрешили приложению «kitten» доступ к любому файлу системы через `build-finish`. Ключи, которые можно использовать для предоставления доступа к разным ресурсам, перечислены ниже:

* `--filesystem={path}`

Этот ключ разрешает доступ к определённым путям в системе. Можно указать конкретный путь (например, `/usr/share`). `home` разрешает доступ к домашнему каталогу пользователя, а `host` — ко всем файлам системы. Кроме того, путь можно сделать только для чтения с помощью `:ro`. Например, `--filesystem=/usr/share:ro --filesystem=home` разрешает доступ только для чтения к `/usr/share` и доступ на чтение-запись к домашнему каталогу пользователя.

* `--share={type}`

Этот ключ разрешает доступ к определённым ресурсам. Чаще всего используются типы `ipc` и `network`, разрешающие IPC и сетевой доступ. В большинстве GUI-приложений `--share=ipc` используется для работы разделяемой памяти X, что улучшает производительность.

* `--socket={type}`

Этот ключ позволяет использовать определённые socket'ы. Чаще всего используются типы `x11`, `wayland` и `pulseaudio`. Первые два используются приложениями для отрисовки GUI-элементов, а последний — для воспроизведения звука через демон Pulseaudio.

* `--device={device}`

Позволяет приложениям выборочно обращаться к некоторым устройствам. Чаще всего здесь используется `dri`, чтобы приложения могли задействовать рендеринг OpenGL.

* `--talk-name={name}` и `--system-talk-name={name}`

Эти ключи позволяют приложениям общаться с именованными сервисами через session bus и system bus DBus.

* `--env={varname}={value}`

Ключ `env` позволяет экспортировать переменные окружения. `{varname}` — имя переменной, которой присваивается указанное `{value}`.

Если приложение требует доступа к [dconf](https://en.wikipedia.org/wiki/Dconf), нужно использовать следующие ключи:

```text
--filesystem=xdg-run/dconf
--filesystem=~/.config/dconf:ro
--talk-name=ca.desrt.dconf
--env=DCONF_USER_CONFIG_DIR=.config/dconf
```

Практический пример с этими ключами мы увидим в одном из следующих разделов.

## Автоматическая сборка приложений: flatpak-builder

Хотя шаги сборки Flatpak-приложений довольно просты, собирать их по одному всё равно утомительно. `flatpak-builder` — инструмент, позволяющий собирать приложения декларативно с помощью JSON-манифеста. Пока исходный код организован согласно «[build API](https://github.com/cgwalters/build-api/)», builder может скомпилировать и установить приложения прямо из архивов исходников. Большинство ПО на autotools уже соответствует этому API, так что дополнительная настройка обычно не нужна.

Типичный файл манифеста обычно выглядит так:

```json
{
  "app-id": "com.booleanworld.kitten",
  "runtime": "org.freedesktop.Platform",
  "runtime-version": "1.6",
  "sdk": "org.freedesktop.Sdk",
  "command": "kitten",
  "finish-args": [
     "--filesystem=host"
  ],
  "modules": [
    {
      "name": "kitten",
      "sources": [
        {
          "type": "archive",
          "url": "https://opensource.example.com/kitten-0.0.1.tar.gz",
          "sha256": "38ecfd39b76a2505376f5a57ebcc7b19d35efaf9f8c724a24382c45aa1378018"
        }
      ]
    }
  ]
}
```

Как видите, файл содержит ту же информацию, которую мы ранее задавали разными командами. Кроме того, он содержит список модулей для сборки. В примере выше модуль только один. Если у вас сложное приложение, зависящее от нескольких модулей, придётся перечислить их все. Например, gnome-calculator зависит от mpc и mpfr, и его манифест выглядит [так](https://git.gnome.org/browse/gnome-apps-nightly/tree/org.gnome.Calculator.json).

Поддерживаются разные типы источников. Другой популярный тип — `git`: нужно указать URL репозитория и, по желанию, ветку, которую нужно извлечь.

Манифест очень мощный: он поддерживает задание CFLAGS/CXXFLAGS, переименование файлов для экспорта и удаление ненужных файлов. В следующем разделе мы разберём практическое приложение и научиться паковать его для Flatpak.

## Реальный пример: упаковка galculator

В этом разделе мы возьмём galculator — простое приложение-калькулятор — и соберём его с помощью `flatpak-builder`. Нам нужно немного проанализировать, какие файлы нужно переименовать или удалить. Поэтому первым шагом сделаем тестовую установку. Затем соберём манифест по мере необходимости.

Поскольку galculator — GTK-приложение, мы будем использовать среду выполнения и SDK Gnome. Установите их сейчас, если ещё не сделали этого. Кроме того, скачайте архив исходников [отсюда](http://galculator.mnim.org/downloads.html). (Мы использовали версию 2.1.4 — самую свежую на момент написания.)

### Поиск файлов, которые нужно экспортировать или удалить

Когда архив исходников скачан и распакован, попробуйте собрать его с помощью SDK. SDK Gnome также содержит инструменты вроде bash, так что его можно запустить так:

```bash
flatpak run --command=bash --filesystem=host --devel org.gnome.Sdk/x86_64/3.24
```

Теперь перейдите в каталог с исходниками galculator и используйте обычное заклинание для сборки. Префиксный каталог мы зададим как `~/galculator-test`.

```bash
./configure --prefix=$HOME/galculator-test
make install
```

Теперь можно изучить файлы в каталоге `galculator-test`. Как вы, вероятно, заметили, следующие файлы нужно экспортировать:

* Информация AppStream в `share/appdata/galculator.appdata.xml`
* Иконки в `share/icons`
* Desktop-запись в `share/applications/galculator.desktop`

К сожалению, у них нет префикса с именем приложения. Поэтому их нужно переименовать с помощью следующих свойств в манифесте:

```json
{
	"rename-appdata-file": "galculator.appdata.xml",
	"rename-icon": "galculator",
	"rename-desktop-file": "galculator.desktop"
}
```

После переименования этих файлов `flatpak-builder` автоматически экспортирует их. Когда Flatpak-пакет собран, это поможет создавать пункты меню в базовой системе.

Кроме того, каталоги `share/man` и `share/pixmaps` не нужны, так что их можно удалить:

```json
{
    "cleanup": [
        "/share/man",
        "/share/pixmaps"
    ]
}
```

### Настройка песочницы

Поскольку это GTK-приложение, нужно разрешить ему доступ к X11 и Wayland и разделить механизмы IPC. Также нужно разрешить рендеринг OpenGL. Кроме того, galculator нужен доступ к dconf — придётся добавить записи, которые мы обсуждали ранее. Ключи, которые передавались бы в `build-finish`, перечисляются в свойстве `finish-args` манифеста:

```json
{
    "finish-args": [
        "--share=ipc",
        "--socket=x11",
        "--socket=wayland",
        "--device=dri",
        "--filesystem=xdg-run/dconf",
        "--filesystem=~/.config/dconf:ro",
        "--talk-name=ca.desrt.dconf",
        "--env=DCONF_USER_CONFIG_DIR=.config/dconf"
    ]
}
```

### Завершение манифеста

К этому моменту вы настроили большинство важных частей манифеста. Настроить остальное будет несложно, а итоговый манифест, который мы использовали, лежит [здесь](https://github.com/boolean-world/flatpak-resources/blob/master/org.mnim.galculator.json). Мы добавили набор `build-options`, устанавливающий CFLAGS и CXXFLAGS в `-O3`.

### Сборка и тестирование приложения

Наконец, можно собрать приложение. Просто запустите `flatpak-builder` с каталогом сборки и манифестом. В этом примере `galculator` — каталог сборки, а `org.mnim.galculator.json` — файл манифеста.

```bash
flatpak-builder galculator org.mnim.galculator.json
```

Далее экспортируйте его в репозиторий, как мы делали ранее:

```bash
flatpak build-export my-repo galculator
```

Теперь можно протестировать приложение, установив его:

```bash
flatpak install --user test-repo org.mnim.galculator
```

Приложение устанавливается сразу, и вы даже получаете desktop-записи, как у обычного приложения! Запустить его можно из пункта меню или с помощью `flatpak run`, как мы делали раньше.

## Распространение приложений

Итак, вы собрали приложение — как заняться его распространением? Самый простой способ — перенести каталог репозитория на сервер и раздавать его через веб. Затем можно попросить пользователей добавить ваш репозиторий в их список и устанавливать приложения оттуда.

Многие предпочитают устанавливать ПО, подписанное GPG, поскольку это доказывает, что приложение действительно исходит от первоначального мейнтейнера. GPG-ключи легко создать командой `gpg2`:

```bash
gpg2 --quick-key-gen [email protected]
```

Обязательно запишите ID ключа — он понадобится позже. В нашем примере предположим, что ID ключа — `A318C188C20D410A`.

Затем можно создать GPG-подписанный репозиторий при запуске `build-export`:

```bash
flatpak build-export my-repo galculator --gpg-sign=A318C188C20D410A
```

Если у вас уже есть неподписанный репозиторий, его можно подписать так:

```bash
flatpak build-sign my-repo --gpg-sign=A318C188C20D410A
flatpak build-update-repo my-repo --gpg-sign=A318C188C20D410A
```

Когда захотите опубликовать репозиторий, обязательно передайте пользователям копию открытого ключа. Чтобы экспортировать открытый ключ, выполните:

```bash
gpg2 --export A318C188C20D410A > public.gpg
```

Этот ключ следует опубликовать на вашем сайте. Когда пользователи захотят добавить ваш репозиторий, они должны скачать открытый ключ. Если пользователь скачал ключ с именем `public.gpg`, он может добавить репозиторий, выполнив:

```bash
flatpak remote-add --gpg-import=public.gpg test-repo http://software.example.com/repo/
```

Впрочем, этот метод крайне неудобен для пользователей. К счастью, процесс можно упростить, создав файлы flatpakref и flatpakrepo, которые подробно описаны в [документации](http://docs.flatpak.org/en/latest/distributing-applications.html).
