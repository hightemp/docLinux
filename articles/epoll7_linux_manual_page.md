# epoll(7) — справочная страница Linux

EPOLL(7)          Справочник по разной информации          EPOLL(7)

## ИМЯ

```text
       epoll - I/O event notification facility
```

## ОБЗОР

```c
       **#include <sys/epoll.h>**
```

## ОПИСАНИЕ

API **epoll** выполняет задачу, аналогичную [poll(2)](../man2/poll.2.html): мониторинг нескольких файловых дескрипторов с целью определить, возможен ли на каком-либо из них ввод-вывод. API **epoll** может использоваться и как интерфейс, срабатывающий по фронту (edge-triggered), и как интерфейс, срабатывающий по уровню (level-triggered), и хорошо масштабируется на большое число отслеживаемых файловых дескрипторов.

Центральное понятие API **epoll** — _экземпляр_ (instance) **epoll** — структура данных в ядре, которая с точки зрения userspace может рассматриваться как контейнер для двух списков:

•  Список _интересов_ (interest list, иногда также называемый набором **epoll**): набор файловых дескрипторов, для мониторинга которых процесс зарегистрировал интерес.

•  Список _готовности_ (ready list): набор файловых дескрипторов, «готовых» к вводу-выводу. Список готовности — это подмножество (или, точнее, набор ссылок на) файловые дескрипторы из списка интересов. Список готовности динамически наполняется ядром в результате активности ввода-вывода на этих файловых дескрипторах.

Для создания экземпляра **epoll** и управления им предоставляются следующие системные вызовы:

•  [epoll_create(2)](../man2/epoll_create.2.html) создаёт новый экземпляр **epoll** и возвращает файловый дескриптор, ссылающийся на этот экземпляр. (Более новый [epoll_create1(2)](../man2/epoll_create1.2.html) расширяет функциональность [epoll_create(2)](../man2/epoll_create.2.html).)

•  Интерес к конкретным файловым дескрипторам затем регистрируется через [epoll_ctl(2)](../man2/epoll_ctl.2.html), который добавляет элементы в список интересов экземпляра **epoll**.

•  [epoll_wait(2)](../man2/epoll_wait.2.html) ожидает события ввода-вывода, блокируя вызывающий поток, если события в данный момент недоступны. (Этот системный вызов можно рассматривать как извлечение элементов из списка готовности экземпляра **epoll**.)

**Срабатывание по уровню и по фронту**

Интерфейс распространения событий **epoll** может вести себя и как edge-triggered (ET), и как level-triggered (LT). Разницу между двумя механизмами можно описать так. Предположим, происходит следующий сценарий:

(1)  Файловый дескриптор, представляющий читающую сторону канала (pipe) (_rfd_), регистрируется в экземпляре **epoll**.

(2)  Пишущий в канал пишет 2 КБ данных в пишущую сторону канала.

(3)  Выполняется вызов [epoll_wait(2)](../man2/epoll_wait.2.html), который вернёт _rfd_ как готовый файловый дескриптор.

(4)  Читатель канала читает 1 КБ данных из _rfd_.

(5)  Снова выполняется вызов [epoll_wait(2)](../man2/epoll_wait.2.html).

Если файловый дескриптор _rfd_ был добавлен в интерфейс **epoll** с флагом **EPOLLET** (edge-triggered), вызов [epoll_wait(2)](../man2/epoll_wait.2.html) в шаге **5**, вероятно, зависнет, несмотря на наличие доступных данных во входном буфере файла; тем временем удалённая сторона может ожидать ответа на уже отправленные ею данные. Причина в том, что режим edge-triggered доставляет события только при изменениях на отслеживаемом файловом дескрипторе, то есть событие генерируется при каждом получении порции данных. Поэтому в шаге **5** вызывающий может в итоге ждать данные, которые уже присутствуют во входном буфере. В примере выше событие на _rfd_ будет сгенерировано из-за записи, выполненной в **2**, и это событие потребляется в **3**. Поскольку операция чтения в **4** не потребляет все данные буфера, вызов [epoll_wait(2)](../man2/epoll_wait.2.html) в шаге **5** может блокироваться неограниченно долго.

Приложение, использующее флаг **EPOLLET**, должно применять неблокирующие файловые дескрипторы, чтобы избежать ситуации, когда блокирующее чтение или запись «уморит голодом» задачу, обрабатывающую несколько файловых дескрипторов. Рекомендуемый способ использовать **epoll** как интерфейс edge-triggered (**EPOLLET**) таков:

(1)  с неблокирующими файловыми дескрипторами; и

(2)  ожидать события только после того, как [read(2)](../man2/read.2.html) или [write(2)](../man2/write.2.html) вернут **EAGAIN**.

Напротив, при использовании в качестве level-triggered интерфейса (по умолчанию, когда **EPOLLET** не указан), **epoll** — это просто более быстрый [poll(2)](../man2/poll.2.html), и его можно использовать везде, где используется последний, поскольку он имеет ту же семантику.

Поскольку даже с edge-triggered **epoll** при получении нескольких порций данных может быть сгенерировано несколько событий, у вызывающего есть возможность указать флаг **EPOLLONESHOT**, чтобы сказать **epoll** отключить соответствующий файловый дескриптор после получения события через [epoll_wait(2)](../man2/epoll_wait.2.html). Когда флаг **EPOLLONESHOT** указан, ответственность за повторное взведение (rearm) файлового дескриптора лежит на вызывающем — с помощью [epoll_ctl(2)](../man2/epoll_ctl.2.html) с **EPOLL_CTL_MOD**.

Если несколько потоков (или процессов, если дочерние процессы унаследовали файловый дескриптор **epoll** через [fork(2)](../man2/fork.2.html)) заблокированы в [epoll_wait(2)](../man2/epoll_wait.2.html) в ожидании на одном и том же файловом дескрипторе epoll, и файловый дескриптор из списка интересов, помеченный для уведомления edge-triggered (**EPOLLET**), становится готов, из [epoll_wait(2)](../man2/epoll_wait.2.html) будет разбужен только один из потоков (или процессов). Это даёт полезную оптимизацию для избегания пробуждений «громового стада» в некоторых сценариях.

**Взаимодействие с autosleep**

Если система находится в режиме **autosleep** через _/sys/power/autosleep_ и происходит событие, будящее устройство из сна, драйвер устройства будет держать устройство бодрствующим только до момента постановки события в очередь. Чтобы держать устройство бодрствующим до обработки события, необходимо использовать флаг [epoll_ctl(2)](../man2/epoll_ctl.2.html) **EPOLLWAKEUP**.

Когда флаг **EPOLLWAKEUP** установлен в поле **events** структуры _struct epoll_event_, система будет удерживаться в бодрствующем состоянии с момента постановки события в очередь, через вызов [epoll_wait(2)](../man2/epoll_wait.2.html), возвращающий событие, и до последующего вызова [epoll_wait(2)](../man2/epoll_wait.2.html). Если событие должно удерживать систему бодрствующей дольше, отдельный _wake_lock_ следует взять до второго вызова [epoll_wait(2)](../man2/epoll_wait.2.html).

**Интерфейсы /proc**

Для ограничения объёма памяти ядра, потребляемой epoll, могут использоваться следующие интерфейсы:

_/proc/sys/fs/epoll/max_user_watches_ (начиная с Linux 2.6.28)
       Задаёт ограничение на общее число файловых дескрипторов, которые пользователь может зарегистрировать во всех экземплярах epoll в системе. Ограничение действует на реальный идентификатор пользователя (user ID). Каждый зарегистрированный файловый дескриптор стоит примерно 90 байт в 32-битном ядре и примерно 160 байт в 64-битном. В настоящее время значение по умолчанию для _max_user_watches_ — это 1/25 (4%) доступной low-памяти, делённая на стоимость регистрации в байтах.

**Пример рекомендуемого использования**

Хотя использование **epoll** как level-triggered интерфейса имеет ту же семантику, что и [poll(2)](../man2/poll.2.html), использование edge-triggered требует дополнительных пояснений, чтобы избежать застревания (stall) в цикле событий приложения. В этом примере listener — это неблокирующий сокет, на котором был вызван [listen(2)](../man2/listen.2.html). Функция _do_use_fd()_ использует новый готовый файловый дескриптор, пока **EAGAIN** не будет возвращено либо [read(2)](../man2/read.2.html), либо [write(2)](../man2/write.2.html). Приложение — событийная машина состояний — после получения **EAGAIN** должно записать своё текущее состояние, чтобы при следующем вызове _do_use_fd()_ продолжить [read(2)](../man2/read.2.html) или [write(2)](../man2/write.2.html) с того места, где оно остановилось.

```c
           #define MAX_EVENTS 10
           struct epoll_event ev, events[MAX_EVENTS];
           int listen_sock, conn_sock, nfds, epollfd;
```

```c
           /* Код настройки слушающего сокета, 'listen_sock',
              (socket(), bind(), listen()) опущен.  */
```

```c
           epollfd = epoll_create1(0);
           if (epollfd == -1) {
               perror("epoll_create1");
               exit(EXIT_FAILURE);
           }

           ev.events = EPOLLIN;
           ev.data.fd = listen_sock;
           if (epoll_ctl(epollfd, EPOLL_CTL_ADD, listen_sock, &ev) == -1) {
               perror("epoll_ctl: listen_sock");
               exit(EXIT_FAILURE);
           }

           for (;;) {
               nfds = epoll_wait(epollfd, events, MAX_EVENTS, -1);
               if (nfds == -1) {
                   perror("epoll_wait");
                   exit(EXIT_FAILURE);
               }
```

```c
               for (n = 0; n < nfds; ++n) {
                   if (events[n].data.fd == listen_sock) {
                       conn_sock = accept(listen_sock,
                                          (struct sockaddr *) &addr, &addrlen);
                       if (conn_sock == -1) {
                           perror("accept");
                           exit(EXIT_FAILURE);
                       }
                       setnonblocking(conn_sock);
                       ev.events = EPOLLIN | EPOLLET;
                       ev.data.fd = conn_sock;
                       if (epoll_ctl(epollfd, EPOLL_CTL_ADD, conn_sock,
                                   &ev) == -1) {
                           perror("epoll_ctl: conn_sock");
                           exit(EXIT_FAILURE);
                       }
                   } else {
                       do_use_fd(events[n].data.fd);
                   }
               }
           }
```

При использовании в качестве edge-triggered интерфейса по соображениям производительности можно добавить файловый дескриптор в интерфейс **epoll** (**EPOLL_CTL_ADD**) однократно, указав (**EPOLLIN** | **EPOLLOUT**). Это позволяет избежать постоянного переключения между **EPOLLIN** и **EPOLLOUT** вызовом [epoll_ctl(2)](../man2/epoll_ctl.2.html) с **EPOLL_CTL_MOD**.

**Вопросы и ответы**

•  Какой ключ используется для различения файловых дескрипторов, зарегистрированных в списке интересов?

   Ключ — это комбинация номера файлового дескриптора и открытого файлового описания (open file description, также известного как «open file handle» — внутреннее представление ядра об открытом файле).

•  Что произойдёт, если зарегистрировать один и тот же файловый дескриптор в экземпляре **epoll** дважды?

   Вероятно, вы получите **EEXIST**. Однако можно добавить дубликат ([dup(2)](../man2/dup.2.html), [dup2(2)](../man2/dup2.2.html), [fcntl(2)](../man2/fcntl.2.html) **F_DUPFD**) файлового дескриптора в тот же экземпляр **epoll**. Это может быть полезным приёмом фильтрации событий, если дубликаты файловых дескрипторов зарегистрированы с разными масками _events_.

•  Могут ли два экземпляра **epoll** ждать один и тот же файловый дескриптор? Если да, будут ли события сообщаться обоим файловым дескрипторам **epoll**?

   Да, и события будут сообщаться обоим. Однако для корректной реализации может потребоваться аккуратное программирование.

•  Можно ли опрашивать сам файловый дескриптор **epoll** через poll/epoll/select?

   Да. Если у файлового дескриптора **epoll** есть ожидающие события, он будет сообщать о себе как о читаемом.

•  Что произойдёт, если попытаться поместить файловый дескриптор **epoll** в его собственный набор файловых дескрипторов?

   Вызов [epoll_ctl(2)](../man2/epoll_ctl.2.html) завершится ошибкой (**EINVAL**). Однако можно добавить файловый дескриптор **epoll** внутрь набора другого файлового дескриптора **epoll**.

•  Можно ли передать файловый дескриптор **epoll** через сокет домена UNIX другому процессу?

   Да, но делать это не имеет смысла, поскольку у принимающего процесса не будет копий файловых дескрипторов из списка интересов.

•  Приведёт ли закрытие файлового дескриптора к его удалению из всех списков интересов **epoll**?

   Да, но имейте в виду следующее. Файловый дескриптор — это ссылка на открытое файловое описание (см. [open(2)](../man2/open.2.html)). Всякий раз, когда файловый дескриптор дублируется через [dup(2)](../man2/dup.2.html), [dup2(2)](../man2/dup2.2.html), [fcntl(2)](../man2/fcntl.2.html) **F_DUPFD** или [fork(2)](../man2/fork.2.html), создаётся новый файловый дескриптор, ссылающийся на то же открытое файловое описание. Открытое файловое описание существует, пока не будут закрыты все ссылающиеся на него файловые дескрипторы.

   Файловый дескриптор удаляется из списка интересов только после закрытия всех файловых дескрипторов, ссылающихся на нижележащее открытое файловое описание. Это значит, что даже после закрытия файлового дескриптора, входящего в список интересов, события для него могут продолжать поступать, если другие файловые дескрипторы, ссылающиеся на то же файловое описание, остаются открытыми. Чтобы этого избежать, файловый дескриптор должен быть явно удалён из списка интересов (с помощью [epoll_ctl(2)](../man2/epoll_ctl.2.html) **EPOLL_CTL_DEL**) до дублирования. Либо приложение должно гарантировать, что все файловые дескрипторы закрыты (что может быть сложно, если файловые дескрипторы дублировались за кулисами библиотечными функциями, использовавшими [dup(2)](../man2/dup.2.html) или [fork(2)](../man2/fork.2.html)).

•  Если между вызовами [epoll_wait(2)](../man2/epoll_wait.2.html) происходит более одного события, они объединяются или сообщаются по отдельности?

   Они будут объединены.

•  Влияет ли операция над файловым дескриптором на уже собранные, но ещё не сообщённые события?

   Над существующим файловым дескриптором можно выполнить две операции. Удаление в этом случае бессмысленно. Modify вызовет перечитывание доступного ввода-вывода.

•  Нужно ли непрерывно читать/писать файловый дескриптор до получения **EAGAIN** при использовании флага **EPOLLET** (поведение edge-triggered)?

   Получение события от [epoll_wait(2)](../man2/epoll_wait.2.html) должно подсказать вам, что файловый дескриптор готов для запрошенной операции ввода-вывода. Вы должны считать его готовым, пока следующий (неблокирующий) read/write не вернёт **EAGAIN**. Когда и как использовать файловый дескриптор — целиком на ваше усмотрение.

   Для файлов с ориентацией на пакеты/маркеры (например, сокет дейтаграмм, терминал в каноническом режиме) единственный способ обнаружить конец пространства ввода-вывода — продолжать читать/писать до **EAGAIN**.

   Для потоково-ориентированных файлов (например, pipe, FIFO, потоковый сокет) условие исчерпания пространства ввода-вывода можно также обнаружить, проверяя объём данных, прочитанных из целевого файлового дескриптора / записанных в него. Например, если вы вызываете [read(2)](../man2/read.2.html), прося прочитать определённое количество данных, а [read(2)](../man2/read.2.html) возвращает меньшее число байт, можно быть уверенным, что пространство ввода-вывода для чтения на файловом дескрипторе исчерпано. То же верно при записи через [write(2)](../man2/write.2.html). (Избегайте последнего приёма, если вы не можете гарантировать, что отслеживаемый файловый дескриптор всегда ссылается на потоково-ориентированный файл.)

**Возможные подводные камни и способы их избежать**

•  **Голодание (edge-triggered)**

   При наличии большого объёма пространства ввода-вывода возможно, что при попытке его вычитать другие файлы не будут обработаны, что вызовет голодание (starvation). (Эта проблема не специфична для **epoll**.)

   Решение — поддерживать список готовности и помечать файловый дескриптор как готовый в его связанной структуре данных, что позволит приложению запоминать, какие файлы нуждаются в обработке, но по-прежнему работать по кругу (round robin) среди всех готовых файлов. Это также позволяет игнорировать последующие события, получаемые для файловых дескрипторов, которые уже готовы.

•  **Если используете кеш событий...**

   Если вы используете кеш событий или храните все файловые дескрипторы, возвращённые из [epoll_wait(2)](../man2/epoll_wait.2.html), обязательно предусмотрите способ динамически помечать его закрытие (т. е. вызванное обработкой предыдущего события). Предположим, вы получили 100 событий от [epoll_wait(2)](../man2/epoll_wait.2.html), и в событии #47 условие приводит к закрытию события #13. Если вы удалите структуру и вызовете [close(2)](../man2/close.2.html) для файлового дескриптора события #13, ваш кеш событий может всё ещё сообщать, что для этого файлового дескриптора есть ожидающие события, что вносит путаницу.

   Одно из решений — при обработке события 47 вызвать **epoll_ctl**(**EPOLL_CTL_DEL**) для удаления файлового дескриптора 13 и [close(2)](../man2/close.2.html), затем пометить связанную структуру данных как удалённую и связать её со списком очистки. Если в вашей пакетной обработке найдётся другое событие для файлового дескриптора 13, вы обнаружите, что файловый дескриптор был ранее удалён, и никакой путаницы не возникнет.

## ВЕРСИИ

В других системах есть похожие механизмы; например, во FreeBSD есть _kqueue_, а в Solaris — _/dev/poll_.

## СТАНДАРТЫ

Linux.

## ИСТОРИЯ

Linux 2.5.44. glibc 2.3.2.

## ЗАМЕЧАНИЯ

Набор файловых дескрипторов, отслеживаемых через файловый дескриптор epoll, можно просмотреть через запись для файлового дескриптора epoll в каталоге _/proc/[pid]/fdinfo_ процесса. Подробнее см. [proc(5)](../man5/proc.5.html).

Операция [kcmp(2)](../man2/kcmp.2.html) **KCMP_EPOLL_TFD** может использоваться для проверки, присутствует ли файловый дескриптор в экземпляре epoll.
