# RFC 3484 в Linux: сортировка `getaddrinfo()` в glibc, выбор адреса источника в ядре, проблемы IPv6 site-local/ULA, таблицы `label`/`precedence` и `/etc/gai.conf`

Источник: [RFC 3484 on Linux — статья Ulrich Drepper о реализации выбора адресов в Linux: сортировка `getaddrinfo()` в glibc, выбор адреса источника в ядре, проблемы IPv6 site-local/ULA, таблицы `label`/`precedence` и `/etc/gai.conf`.](https://www.akkadia.org/drepper/linux-rfc3484.html)

[Ульрих Дреппер](mailto:drepper@gmail.com) · 4 сентября 2007

Создание сетевого соединения между двумя машинами — на самом деле довольно сложный процесс. Помимо самой передачи данных по сети в самом начале нужно принять два ключевых решения:

* Если у целевой машины больше одного сетевого адреса (IPv4, IPv6 или другие), необходимо решить, какой из них использовать.
* Если у машины-источника больше одного сетевого адреса и/или интерфейса, необходимо решить, какой из них использовать.

Большинство сайтов используют site-local IPv4-адреса, потому что назначенных IP-номеров не хватает. Для тех машин, у которых есть и официальные IP-номера, выбор правильного номера критически важен. С появлением IPv6 ситуация становится ещё сложнее. Каждый интерфейс может иметь несколько IPv6-адресов. Для реализации мобильного IPv6 и других подобных специальных целей сетевые адреса являются временными и перемещаются: создаются временные адреса (temporary addresses), а устаревшие адреса (deprecated addresses) остаются позади.

## Появление RFC 3484

Эта проблема, конечно, не нова. С тех самых пор, как у машины могло быть больше одного сетевого интерфейса, реализациям приходилось делать выбор. Однако всеобъемлющего документа, описывающего требования, не существовало.

[RFC 3484](http://www.rfc-editor.org/rfc/rfc3484.txt) определяет, как выбирать правильный адрес источника и назначения для соединения. Это имеет эффект в двух местах:

1. При установке соединения в ядре.
2. Во время разрешения имён.

Реализация `connect()` в ядре должна принять решения об адресах источника и назначения до того, как вернёт управление. Вызовы `getpeername()` и `getsockname()` после вызова `connect()` должны возвращать соответствующую информацию. В случае связи без установления соединения это решение должно принимать каждый `sendto()`.

Менее очевидное место для выбора адресов источника и назначения — функциональность разрешения имён. Традиционные интерфейсы (`gethostbyname()` и т.п.) просто возвращали найденные значения в том порядке, в котором их выдавали службы (DNS, файлы и т.д.). Возможно, значения сортировались или перемешивались. Ни одно из этих решений не было сколько-нибудь полезным.

С появлением интерфейса `getaddrinfo()` возникла возможность изменить это печальное положение дел. RFC 3484 определяет, в каком порядке должны возвращаться адреса, если их больше одного. Разбирать все подробности здесь нет смысла — для этого и существует сам RFC. Но вкратце: реализация `getaddrinfo()` определяет адрес источника для каждого из адресов назначения (или, точнее: она позволяет ядру принять решение, используя `connect()`). Затем она сортирует адреса назначения на основе относительных достоинств пар источник/назначение.

Детали сортировки требуют глубокого знания сетевой реализации. Стоит, пожалуй, упомянуть несколько моментов:

* Адрес назначения, для которого можно определить адрес источника, должен предпочитать адресу назначения, для которого адрес источника определить нельзя.
* Если у целевой машины есть внутренний и внешний адрес, а машина-источник находится во внутренней сети, лучше использовать внутренний адрес.

Идея всего этого в том, что вызывающий `getaddrinfo()` пытается использовать список возвращённых адресов в том порядке, в котором их возвращает реализация. То есть код должен выглядеть так:

```c
struct addrinfo *res = NULL;
if (getaddrinfo(hostname, NULL, NULL, &res;) == 0)
  {
    struct addrinfo *runp = res;
    while (runp != NULL)
      {
        ... use *runp ...
        runp = runp->ai_next;
      }
    freeaddrinfo(res);
  }
```

Таким образом сначала пробуются предпочитаемые адреса, у которых наибольшая вероятность корректной работы. Почему это важно? Просто посмотрите, как IPv6 «развёрнут» сегодня. В лучшем случае интерфейсы имеют link-local IPv6-адреса. Возможно, есть сайты с внутренними IPv6-сетями. Исходящие IPv6-интерфейсы встречаются редко. Но всё же находятся прогрессивные сайты, которые указывают IPv6-адреса в своих DNS-записях. Результат: если приложение попытается первым использовать рекламируемый IPv6, высока вероятность неудачной попытки соединения. Это может быть мгновенная ошибка, а может потребоваться таймаут. В любом случае попытка соединения займёт больше времени, чем следовало бы.

Сортируя результаты `getaddrinfo()`, можно избежать многих подобных проблем. И помните также: **всегда** используйте флаг `AI_ADDRCONFIG`.

## Состояние RFC 3484

На момент написания RFC 3484 не был заменён никаким другим RFC. И это проблема. [RFC 3879](http://www.rfc-editor.org/rfc/rfc3879.txt) объявляет site-local IPv6-адреса устаревшими. Это решение непопулярно во многих частях сообщества. Аргументация была такой: site-local IPv6-адресами слишком сложно пользоваться. Учитывая, что один из авторов RFC — из Microsoft, я полагаю: практически всё слишком сложно для людей из мира Windows. Но я отвлекаюсь. [RFC 4193](http://www.rfc-editor.org/rfc/rfc4193.txt) вводит новое понятие — уникальные локальные IPv6 unicast-адреса (Unique Local IPv6 Unicast Addresses, ULA). Возможно, это сработает.

Но: RFC 3484 явно определяет, как следует обращаться с site-local IPv6-адресами. Простое объявление всей специальной обработки site-local-адресов недействительной (как делает RFC 3879) не меняет того факта, что:

1. реализация RFC 3484 существовала до RFC 3879;
2. нет ревизии RFC 3484, объясняющей, как обращаться с адресами RFC 4193 (и нужна ли вообще какая-то специальная обработка).

Из-за первого пункта и потому, что RFC 3879 указывает не использовать прежний диапазон site-local-адресов повторно, многие реализации продолжат обрабатывать site-local-адреса так, как указано в RFC 3484.

Существует также [RFC 4429](http://www.rfc-editor.org/rfc/rfc4429.txt), вводящий оптимистичное обнаружение дублирующихся адресов (Optimistic Duplicate Address Detection). Хорошая новость в том, что этот RFC ссылается на RFC 3484, но полной ясности нет.

## БОЛЬШАЯ проблема

У текущей спецификации RFC 3484 есть несколько проблем. Вот самая большая. Рассмотрим типичную машину на крупном сайте (компания, университет). Это может происходить и в домашних сетях. Сегодня у каждой машины всё ещё есть IPv4-адрес, и поскольку крупным сайтам больше не выделяют большие блоки, локальные сети работают через NAT. То есть IPv4-адреса — это site-local-адреса: `10/8`, `172.16/12` или `192.168/16`.

В то же время у большинства сайтов нет официальных IPv6-адресов, потому что провайдеры всё ещё часто их не выдают. Поэтому многие сайты прибегают к site-local или ULA IPv6-адресам. Спецификация IPv6 не содержит ничего похожего на NAT для IPv6 — и на то есть веская причина. Расширенное адресное пространство как раз и призвано сделать трансляцию адресов ненужной.

Но что происходит, если на такой машине, у которой есть только IPv4- и IPv6 site-local-адреса, выполняется поиск хоста, имеющего глобальные IPv4- и IPv6-адреса? Согласно рекомендуемым настройкам RFC 3484 (т.е. предпочитать IPv6-адреса) сортировка ставит IPv6-адрес первым. Всегда.

Но это проблема. IPv6-адрес не находится за NAT, поэтому попытка соединиться с глобальным IPv6-адресом с site-local-адреса не сработает. С другой стороны, IPv4-адрес обычно находится за NAT, и поэтому соединение с глобальным IPv4-адресом с использованием site-local-адреса обычно сработает.

Проблема в том, что мечение адресов (address labelling) не делает различий между глобальными и site-local-адресами. Для IPv4 это пока нормально, потому что NAT используется повсеместно. Но глобальные и site-local/ULA IPv6-адреса не совпадают.

Решение проблемы — назначить разные метки (labels) в правиле 5 алгоритма сортировки для site-local и ULA IPv6-адресов. То есть таблица меток из раздела 2.1 расширяется:

```text
      Prefix       Label
      ::1/128          0
      ::/0             1
      2002::/16        2
      ::/96            3
      ::ffff:0:0/96    4
      fec0::/10        5
      fc00::/7         6
```

Именно так сделано в glibc. С этим изменением сортировка на описанной выше проблемной машине всегда ставит глобальный IPv4-адрес перед глобальным IPv6-адресом, потому что метки для site-local и глобального IPv4-адресов совпадают, а метки для site-local и глобального IPv6-адресов не совпадают. Ещё одна причина обновить RFC 3484.

## Проблема IPv4

Правило 9 в RFC 3484 гласит, что при сравнении двух адресов одного семейства выигрывает более длинный совпадающий префикс. Для IPv6 это имеет полный смысл. Но адресное пространство IPv4 не выделяется иерархически. Соседние адреса не означают, что соседними являются и сети.

IPv4-адреса можно осмысленно сравнивать, только если они в одной подсети. Поэтому glibc реализует изменённое правило 9:

```text
  If Netmask(DA) == Netmask(Source(DA))
    If CommonPrefixLen(DA, Source(DA)) > CommonPrefixLen(DB, Source(DB))
      Prefer DA
    Else If CommonPrefixLen(DA, Source(DA)) < CommonPrefixLen(DB, Source(DB))
      Prefer DB
```

## Состояние RFC 3484 в Linux

Ядро имеет полнофункциональную реализацию RFC 3484 для IPv6-адресов как минимум с первых дней ветки 2.6. Некоторые правила реализованы только при выборе определённых опций ядра. Не каждому бинарнику ядра нужна поддержка мобильного IPv6. Единственное непризнанное из RFC 3484 правило (подробности см. в тексте RFC) — правило номер 4.

На стороне пользователя реализация `getaddrinfo()` в glibc получила поддержку сортировки RFC 3484 в ноябре 2003 года. С тех пор было найдено несколько проблем, но в целом она работала. Поддержка правил 3 и 7 была добавлена только в апреле 2006 года, поддержка правила 4 — в сентябре 2006 года. Поскольку число сайтов, для которых это имеет значение, очень мало, особой роли это играть не должно. С правильными версиями ядра и glibc можно иметь полную реализацию `getaddrinfo`.

В наши дни реализация также поддерживает настройку со стороны системного администратора, как того требует RFC 3484. Информация, помещённая в файл `/etc/gai.conf`, может заменить таблицы меток и приоритетов (label и precedence), которые реализация использует по умолчанию. Это позволяет подстроить реализацию под локальные требования — например, под site-local-адреса и т.п. Пример конфигурации можно найти в `/usr/share/docs/glibc-common-*/gai.conf`. По умолчанию он не устанавливается в `/etc`, поскольку отсутствие файла означает, что реализация должна использовать значения по умолчанию. Конфигурационный файл с настройками RFC 3484 по умолчанию выглядел бы так:

```text
       label  ::1/128       0
       label  ::/0          1
       label  2002::/16     2
       label ::/96          3
       label ::ffff:0:0/96  4
       precedence  ::1/128       50
       precedence  ::/0          40
       precedence  2002::/16     30
       precedence ::/96          20
       precedence ::ffff:0:0/96  10
```

В устаревших интерфейсах разрешения имён (`gethostbyname()` и т.п.) нет поддержки чего-либо подобного RFC 3484 — и никогда не будет. Реализация RFC 3484 добавляет некоторые накладные расходы. Чтобы определить адрес источника для каждого адреса назначения, нужно создать socket и инициировать UDP-соединение. При отсутствии выделенного интерфейса ядра это лучшее решение. Эту работу нельзя кэшировать в `nscd`. Демон кэширует только сырую информацию. Сортировка должна выполняться всегда, потому что ситуация на машине (доступные интерфейсы и т.д.) может меняться со временем.

Многими сведениями, которые использует алгоритм сортировки, нелегко разжиться. Поэтому настоятельно рекомендуется, чтобы никакая программа не использовала самодельные реализации `getaddrinfo()`. Просто используйте системную реализацию.
