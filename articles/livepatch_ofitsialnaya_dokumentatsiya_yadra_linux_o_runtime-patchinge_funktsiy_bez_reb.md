# Livepatch: runtime-патчинг функций ядра без перезагрузки

Источник: [Livepatch — официальная документация ядра Linux о runtime-патчинге функций без reboot; объясняет связку `dynamic ftrace`/kprobes, consistency model, lifecycle livepatch-модуля, sysfs и ограничения.](https://docs.kernel.org/livepatch/livepatch.html)

Документация ядра Linux (docs.kernel.org) · версия 7.3.0-rc1

Этот документ описывает базовую информацию о лайвпатчинге ядра (kernel livepatching).

## 1. Мотивация

Существует множество ситуаций, когда пользователи неохотно перезагружают систему. Причиной может быть то, что система выполняет сложные научные вычисления или находится под высокой нагрузкой в пиковые часы. Помимо того, чтобы системы работали непрерывно, пользователи также хотят иметь стабильную и безопасную систему. Лайвпатчинг даёт пользователям и то и другое, позволяя перенаправлять вызовы функций; таким образом критические функции исправляются без перезагрузки системы.

## 2. Kprobes, Ftrace, Livepatching

В ядре Linux есть несколько механизмов, напрямую связанных с перенаправлением выполнения кода; а именно: зонды ядра (kernel probes), трассировка функций (function tracing) и лайвпатчинг:

* Зонды ядра — самые универсальные. Код можно перенаправить, поставив инструкцию точки останова вместо любой инструкции.

* Трассировщик функций вызывает код из предопределённого места, близкого к точке входа функции. Это место генерируется компилятором с помощью опции gcc ‘-pg’.

* Лайвпатчингу обычно нужно перенаправить код в самом начале входа функции, до того как параметры функции или стек будут как-либо изменены.

Все три подхода требуют изменения существующего кода во время выполнения. Поэтому они должны знать друг о друге и не наступать друг другу на пятки. Большинство этих проблем решается использованием фреймворка dynamic ftrace в качестве основы. Kprobe регистрируется как ftrace-обработчик, когда зондируется вход функции, см. CONFIG_KPROBES_ON_FTRACE. Также альтернативная функция из live-патча вызывается с помощью специального ftrace-обработчика. Но есть некоторые ограничения, см. ниже.

## 3. Модель согласованности

Функции существуют не просто так. Они принимают входные параметры, захватывают и освобождают блокировки, читают, обрабатывают и даже записывают данные определённым образом, имеют возвращаемые значения. Иначе говоря, у каждой функции есть определённая семантика.

Многие исправления не меняют семантику изменяемых функций. Например, они добавляют проверку указателя на NULL или границ, исправляют гонку добавлением недостающего барьера памяти или добавляют блокировку вокруг критической секции. Большинство таких изменений самодостаточны, и функция предстаёт перед остальной системой так же, как раньше. В этом случае функции можно обновлять независимо, по одной.

Но бывают и более сложные исправления. Например, патч может менять порядок блокировки в нескольких функциях одновременно. Или патч может менять смысл некоторых временных структур и обновлять все связанные функции. В этом случае затронутая единица (поток, всё ядро) должна начать использовать все новые версии функций одновременно. Кроме того, переключение должно происходить только тогда, когда это безопасно, например, когда затронутые блокировки освобождены или в изменяемых структурах в данный момент нет данных.

Теория о том, как безопасно применять функции, довольно сложна. Цель — определить так называемую модель согласованности (consistency model). Она пытается определить условия, при которых новую реализацию можно использовать так, чтобы система оставалась согласованной.

Livepatch использует модель согласованности, которая является гибридом kGraft и kpatch: он использует согласованность на уровне задач (per-task) и переключение через барьер системных вызовов из kGraft в сочетании с переключением по стековым трассировкам из kpatch. Есть также ряд запасных вариантов, что делает механизм довольно гибким.

Патчи применяются по каждой задаче отдельно, когда задача считается безопасной для переключения. Когда патч включается, livepatch переходит в переходное состояние, в котором задачи сходятся к пропатченному состоянию. Обычно это переходное состояние может завершиться за несколько секунд. Та же последовательность происходит при отключении патча, за исключением того, что задачи сходятся из пропатченного состояния в непропатченное.

Обработчик прерывания наследует пропатченное состояние задачи, которую он прерывает. То же верно для задач, созданных через fork: дочерняя задача наследует пропатченное состояние родителя.

Livepatch использует несколько взаимодополняющих подходов для определения момента, когда безопасно патчить задачи:

1. Первый и самый эффективный подход — проверка стека спящих задач. Если на стеке данной задачи нет затронутых функций, задача патчится. В большинстве случаев это позволит пропатчить большинство или все задачи с первой попытки. Иначе будут продолжаться периодические попытки. Этот вариант доступен, только если у архитектуры надёжные стеки (HAVE_RELIABLE_STACKTRACE).

2. Второй подход, если он нужен, — переключение при выходе из ядра. Задача переключается, когда возвращается в пространство пользователя из системного вызова, IRQ из пространства пользователя или сигнала. Это полезно в следующих случаях:

```text
1. Patching I/O-bound user tasks which are sleeping on an affected function.
   In this case you have to send SIGSTOP and SIGCONT to force it to exit
   the kernel and be patched.

2. Patching CPU-bound user tasks. If the task is highly CPU-bound then
   it will get patched the next time it gets interrupted by an IRQ.
```

3. Для бездействующих задач «swapper», поскольку они никогда не выходят из ядра, в idle-цикле есть вызов `klp_update_patch_state()`, позволяющий пропатчить их до того, как CPU войдёт в состояние простоя.

(Заметьте, что для kthreads такого подхода пока нет.)

Архитектуры без HAVE_RELIABLE_STACKTRACE полагаются исключительно на второй подход. Весьма вероятно, что некоторые задачи всё ещё могут работать со старой версией функции, пока она не вернёт управление. В этом случае придётся послать задачам сигналы. Это особенно касается kthreads. Они могут не просыпаться, и их нужно будет принудить. Подробнее см. ниже.

Пока мы не придумаем другой способ патчить kthreads, архитектуры без HAVE_RELIABLE_STACKTRACE не считаются полностью поддерживаемыми ядерным лайвпатчингом.

Файл /sys/kernel/livepatch/\<patch\>/transition показывает, находится ли патч в переходе. В данный момент времени в переходе может находиться только один патч. Патч может оставаться в переходе неограниченно долго, если какая-либо из задач застряла в исходном патч-состоянии.

Переход можно обратить и фактически отменить, записав противоположное значение в файл /sys/kernel/livepatch/\<patch\>/enabled, пока переход идёт. Тогда все задачи попытаются сойтись обратно к исходному патч-состоянию.

Есть также файл /proc/\<pid\>/patch_state, который можно использовать, чтобы определить, какие задачи блокируют завершение операции патчинга. Если патч в переходе, файл показывает 0 — задача не пропатчена, и 1 — пропатчена. Если же ни один патч не в переходе, показывается -1. Задачам, блокирующим переход, можно послать SIGSTOP и SIGCONT, чтобы принудить их сменить патч-состояние. Впрочем, это может быть вредно для системы. Лучшей альтернативой является отправка фальшивого сигнала всем оставшимся блокирующим задачам. Реальный сигнал при этом не доставляется (в структурах ожидания сигналов нет данных). Задачи прерываются или пробуждаются и принуждаются сменить патч-состояние. Фальшивый сигнал автоматически отправляется каждые 15 секунд.

Администратор также может повлиять на переход через атрибут /sys/kernel/livepatch/\<patch\>/force. Запись туда 1 сбрасывает флаг TIF_PATCH_PENDING у всех задач и, таким образом, принуждает задачи к пропатченному состоянию. Важное замечание! Атрибут force предназначен для случаев, когда переход надолго застревает из-за блокирующей задачи. От администратора ожидается, что он соберёт все необходимые данные (а именно стековые трассировки таких блокирующих задач) и запросит разрешение у распространителя патча, чтобы принудить переход. Несанкционированное использование может нанести вред системе. Всё зависит от природы патча, какие функции (не)патчатся и в каких функциях спят блокирующие задачи (здесь может помочь /proc/\<pid\>/stack). Удаление (rmmod) модулей патчей навсегда отключается, когда была использована функция force. Невозможно гарантировать, что ни одна задача не спит в таком модуле. Это влечёт неограниченный счётчик ссылок, если модуль патча отключать и включать в цикле.

Более того, использование force может также повлиять на будущие применения live-патчей и причинить системе ещё больший вред. Администратору следует сначала рассмотреть простую отмену перехода (см. выше). Если force был использован, следует запланировать перезагрузку и больше не применять live-патчи.

### 3.1. Добавление поддержки модели согласованности в новые архитектуры

Для добавления поддержки модели согласованности в новые архитектуры есть несколько вариантов:

1. Добавить CONFIG_HAVE_RELIABLE_STACKTRACE. Это означает портирование objtool, а для unwinder'ов без DWARF — также обеспечение способа, которым код трассировки стека сможет обнаруживать в стеке прерывания.

2. Альтернативно — гарантировать, что у каждого kthread есть вызов `klp_update_patch_state()` в безопасном месте. Kthreads обычно находятся в бесконечном цикле, повторяющем некоторое действие. Безопасным местом переключения патч-состояния kthread была бы обозначенная точка цикла, где не взято никаких блокировок и все структуры данных находятся в строго определённом состоянии.

Место очевидно при использовании workqueues или API kthread worker. Эти kthreads обрабатывают независимые действия в универсальном цикле.

С kthreads со своим кастомным циклом всё гораздо сложнее. Там безопасное место нужно тщательно подбирать в каждом случае отдельно.

В таком случае архитектуры без HAVE_RELIABLE_STACKTRACE всё равно смогли бы использовать не связанные с проверкой стека части модели согласованности:

```text
1. patching user tasks when they cross the kernel/user space boundary; and

2. patching kthreads and idle tasks at their designated patch points.
```

Этот вариант не так хорош, как вариант 1, потому что требует сигнализации пользовательских задач и пробуждения kthreads, чтобы их пропатчить. Но он всё равно может быть хорошим запасным вариантом для тех архитектур, у которых ещё нет надёжных стековых трассировок.

## 4. Модуль livepatch

Livepatch-модули распространяются как модули ядра, см. samples/livepatch/livepatch-sample.c.

Модуль содержит новую реализацию функций, которые мы хотим заменить. Кроме того, он определяет структуры, описывающие связь между оригинальной и новой реализацией. Затем идёт код, который заставляет ядро начать использовать новый код при загрузке модуля livepatch. Также есть код, выполняющий очистку перед удалением модуля livepatch. Всё это подробнее рассматривается в следующих разделах.

### 4.1. Новые функции

Новые версии функций обычно просто копируются из оригинальных исходников. Хорошей практикой является добавление префикса к именам, чтобы их можно было отличить от оригинальных, например, в backtrace. Также их можно объявить static, потому что они не вызываются напрямую и не нуждаются в глобальной видимости.

Патч содержит только реально изменённые функции. Но им может понадобиться доступ к функциям или данным из оригинального файла исходников, доступным только локально. Это решается специальной секцией релокаций в сгенерированном модуле livepatch, подробнее см. [Livepatch module ELF format](module-elf-format.html).

### 4.2. Метаданные

Патч описывается несколькими структурами, которые делят информацию на три уровня:

* [`struct klp_func`](api.html#c.klp_func "klp_func") определяется для каждой пропатченной функции. Она описывает связь между оригинальной и новой реализацией конкретной функции.

  Структура включает имя оригинальной функции в виде строки. Адрес функции находится через kallsyms во время выполнения.

  Затем она включает адрес новой функции. Он определяется напрямую присваиванием указателя на функцию. Заметьте, новая функция обычно определена в том же файле исходников.

  Как опциональный параметр можно использовать позицию символа в базе kallsyms, чтобы устранить неоднозначность функций с одинаковыми именами. Это не абсолютная позиция в базе, а лишь порядок, в котором символ был найден для конкретного объекта (vmlinux или модуля ядра). kallsyms позволяет искать символы по имени объекта.

* [`struct klp_object`](api.html#c.klp_object "klp_object") определяет массив пропатченных функций ([`struct klp_func`](api.html#c.klp_func "klp_func")) в одном объекте. Объектом является либо vmlinux (NULL), либо имя модуля.

  Структура помогает группировать функции каждого объекта и обрабатывать их вместе. Заметьте, что пропатчиваемые модули могут загружаться позже самого патча, и соответствующие функции могут быть пропатчены только тогда, когда станут доступны.

* [`struct klp_patch`](api.html#c.klp_patch "klp_patch") определяет массив пропатченных объектов ([`struct klp_object`](api.html#c.klp_object "klp_object")).

  Эта структура обрабатывает все пропатченные функции согласованно и, в конечном итоге, синхронно. Весь патч применяется, только когда найдены все пропатчиваемые символы. Единственное исключение — символы из объектов (модулей ядра), которые ещё не загружены.

  Подробнее о том, как патч применяется по каждой задаче, см. в разделе «Модель согласованности».

## 5. Жизненный цикл livepatch

Лайвпатчинг можно описать пятью базовыми операциями: загрузка (loading), включение (enabling), замена (replacing), отключение (disabling), удаление (removing).

Операции замены и отключения взаимоисключающие. У них одинаковый результат для данного патча, но не для системы.

### 5.1. Загрузка

Единственный разумный способ — включать патч при загрузке модуля livepatch. Для этого нужно вызвать [`klp_enable_patch()`](api.html#c.klp_enable_patch "klp_enable_patch") в колбэке [`module_init()`](../driver-api/basics.html#c.module_init "module_init"). Есть две главные причины:

Во-первых, только модуль имеет лёгкий доступ к соответствующей [`struct klp_patch`](api.html#c.klp_patch "klp_patch").

Во-вторых, код ошибки может использоваться, чтобы отказаться от загрузки модуля, когда патч не может быть включён.

### 5.2. Включение

Livepatch включается вызовом [`klp_enable_patch()`](api.html#c.klp_enable_patch "klp_enable_patch") из колбэка [`module_init()`](../driver-api/basics.html#c.module_init "module_init"). На этом этапе система начнёт использовать новую реализацию пропатченных функций.

Сначала находятся адреса пропатчиваемых функций по их именам. Применяются специальные релокации, упомянутые в разделе «Новые функции». Создаются соответствующие записи под /sys/kernel/livepatch/\<name\>. Патч отклоняется, если любая из вышеописанных операций не удалась.

Затем livepatch переходит в переходное состояние, где задачи сходятся к пропатченному состоянию. Если оригинальная функция патчится впервые, создаётся специфичная для функции `struct klp_ops` и регистрируется универсальный ftrace-обработчик [1]. Этот этап обозначается значением ‘1’ в /sys/kernel/livepatch/\<name\>/transition. Подробнее об этом процессе см. в разделе «Модель согласованности».

Наконец, когда все задачи пропатчены, значение ‘transition’ меняется на ‘0’.

[1] Заметьте, что функции могут патчиться многократно. Ftrace-обработчик регистрируется для данной функции только один раз. Последующие патчи лишь добавляют запись в список (см. поле func_stack) `struct klp_ops`. Правильная реализация выбирается ftrace-обработчиком, см. раздел «Модель согласованности».

При всём этом настоятельно рекомендуется использовать кумулятивные livepatch-модули, поскольку они помогают сохранять согласованность всех изменений. В этом случае функции могут быть пропатчены дважды только в течение переходного периода.

### 5.3. Замена

Все включённые патчи могут быть заменены кумулятивным патчем с установленным флагом .replace.

Как только новый патч включён и ‘transition’ завершается, все функции ([`struct klp_func`](api.html#c.klp_func "klp_func")), связанные с заменёнными патчами, удаляются из соответствующих `struct klp_ops`. Также ftrace-обработчик разрегистрируется, а `struct klp_ops` освобождается, когда соответствующая функция не изменена новым патчем и список func_stack становится пустым.

Подробнее см. [Atomic Replace & Cumulative Patches](cumulative-patches.html).

### 5.4. Отключение

Включённые патчи можно отключить, записав ‘0’ в /sys/kernel/livepatch/\<name\>/enabled.

Сначала livepatch переходит в переходное состояние, где задачи сходятся к непропатченному состоянию. Система начинает использовать либо код из ранее включённого патча, либо даже оригинальный. Этот этап обозначается значением ‘1’ в /sys/kernel/livepatch/\<name\>/transition. Подробнее об этом процессе см. в разделе «Модель согласованности».

Затем, когда все задачи распатчены, значение ‘transition’ меняется на ‘0’. Все функции ([`struct klp_func`](api.html#c.klp_func "klp_func")), связанные с отключаемым патчем, удаляются из соответствующих `struct klp_ops`. Ftrace-обработчик разрегистрируется, а `struct klp_ops` освобождается, когда список func_stack становится пустым.

В-третьих, уничтожается интерфейс sysfs.

### 5.5. Удаление

Удаление модуля безопасно, только если нет пользователей функций, предоставляемых модулем. Именно поэтому функция force навсегда отключает удаление. Только когда система успешно перешла в новое патч-состояние (пропатченное/непропатченное) без принуждения, гарантируется, что ни одна задача не спит и не работает в старом коде.

## 6. Sysfs

Информация о зарегистрированных патчах находится под /sys/kernel/livepatch. Патчи можно включать и отключать, записывая туда значения.

Атрибут /sys/kernel/livepatch/\<patch\>/force позволяет администратору влиять на операцию патчинга.

Подробнее см. [ABI file testing/sysfs-kernel-livepatch](../admin-guide/abi-testing-files.html#abi-file-testing-sysfs-kernel-livepatch).

## 7. Ограничения

Текущая реализация Livepatch имеет несколько ограничений:

* Патчить можно только функции, которые могут трассироваться.

  Livepatch основан на dynamic ftrace. В частности, не могут быть пропатчены функции, реализующие ftrace или livepatch-обработчик ftrace. Иначе код зациклится. Потенциальная ошибка предотвращается пометкой проблемных функций «notrace».

* Livepatch работает надёжно, только если dynamic ftrace находится в самом начале функции.

  Функция должна быть перенаправлена до какого-либо изменения стека или параметров функции. Например, livepatch требует использования опции компилятора gcc -fentry на x86_64.

  Одно исключение — порт PPC. Он использует относительную адресацию и TOC. Каждая функция должна обработать TOC и сохранить LR до вызова ftrace-обработчика. Эта операция должна быть обращена при возврате. К счастью, у универсального кода ftrace та же проблема, и всё это решается на уровне ftrace.

* Kretprobes, использующие фреймворк ftrace, конфликтуют с пропатченными функциями.

  И kretprobes, и livepatches используют ftrace-обработчик, модифицирующий адрес возврата. Побеждает первый пользователь. Зонд или патч отклоняется, если обработчик уже используется другим.

* Kprobes в оригинальной функции игнорируются, когда код перенаправляется в новую реализацию.

  Ведётся работа по добавлению предупреждений об этой ситуации.
